## Diagnosis summary

1. **Single-chunk send stall is the dominant new failure mode.** Voxle send 1 progressed cleanly through 600 chunks at 0.3-0.6s ACK RTT, then chunk 601 ACK-timed-out 6 consecutive times (8s gap each) with target=online, CTL.avail=3630, nacksThisChunk=0, and aborted. Voxle send 2 a few minutes later reproduced the same shape at chunk 277. At observed p_frag=0.6% and 3 fragments/chunk, the probability of one chunk failing 6 attempts by random wire loss is roughly 1.8 percent to the 6th power, i.e. ~3e-11. This is not random fragment drop. The receiver became unresponsive mid-stream while every sender-side health indicator (target online, CTL bandwidth, prior-chunk RTT, NACK count) stayed healthy. The outcome bucket that lit up was `aborted: 1 ackTimeout + 0 combat + 0 zone + 0 busy + 0 offline`, meaning none of the existing receiver-state abort categories captured the actual cause. Protocol behavior on stall: abort the entire send, next sync starts from chunk 1, losing 600 chunks of progress that the receiver may or may not have persisted.

2. **Receive direction never gets chunk 1 from Katorrí-Stormrage.** Five separate sync attempts across the session, each triggered by Katorrí's standard 4-minute HELLO. Every attempt followed the same arc: SYNC_REQUEST sent, 30s gap, NACK 1/3, 45s gap, NACK 2/3, 45s gap, NACK 3/3, 45s gap, abort with the error "NACK limit reached for chunk 1" after 140s. Zero chunks ever arrived. From the log it is ambiguous whether Katorrí processed the SYNC_REQUEST and started sending (in which case chunks 1-N were all dropped en route before reaching local) or whether Katorrí dropped the SYNC_REQUEST itself. Either way: 5 attempts x 140s equals 700s of failed-sync time, with no convergence and no backoff between attempts.

3. **Fxhp send is a third, distinct mode: bursty per-chunk timeouts then NACK abort.** Chunks 1-4 ACK normally in the first 3 seconds. Chunks 5-8 each ACK-timeout exactly once and recover cleanly on first retry. Chunk 9 ACK-times out twice, receives a NACK, retries four more times (all timeouts), and aborts. `chunkFail=50.0%, p_frag=20.6% (n=3.0 frags/chunk)`. Per-peer p_frag across this single session: Voxle 0.6%, Fxhp 20.6% (a 34x spread), qualitatively consistent with the per-peer-route-variance observation (two prior captures showed roughly 25x spread). The Fxhp cross-realm route is much worse than the Voxle route in the same session, same sender, same five-minute window.

4. **Bidirectional superset-skip is heuristic-wrong.** Local repeatedly logs `Bidirectional check: skipped — likely superset (local=6850 > remote=2648)` and skips initiating sync to Fxhp. When Fxhp later sends an unsolicited SYNC_REQUEST (21:44:12) the bucket filter reveals `143 local bucket(s), 114 remote bucket(s), 22 matching, 121 differing`. 121 differing buckets is the opposite of a strict superset; the two datasets are mostly disjoint. The count-based superset heuristic covers the symmetric pair (Fxhp also skips when it sees local's larger count) so neither side initiates sync until something else breaks the impasse. The sync-message-loss memory already flagged this as a candidate amplifier; this log is a concrete instance with quantified bucket overlap.

5. **HELLO replies are still sent to incompatible-version peers BEFORE the version check.** Pattern visible throughout: `Sent HELLO reply to Fluphyxd-Stormrage (tx: 6848, hash: 2947097223)` immediately followed on the next line by `[WARN] Fluphyxd-Stormrage on v0.31.1 (version mismatch; this build is v0.32.3)`. The reply went out on the wire, then the version mismatch was logged. Two incompatible-version peers (Fluphyxd v0.31.1 and Shawtybruh v0.32.1) broadcast every 2 minutes for 38 minutes, roughly 38 HELLO replies sent to peers that cannot use them.

6. **Compression has regressed since the v0.28.7 baseline.** Voxle send 1: 31% / 34% / 41% retained (min/med/max). Voxle send 2: 28% / 34% / 44%. Fxhp send: 34% / 36% / 38%. Versus the documented baseline of 23-26% retained. Combined with raw chunk size of ~1700 bytes for 4 records (~425 raw bytes/record vs the v0.28.7 estimate of ~287), the compressed chunk size is ~570 bytes, which crosses into 3 fragments. v0.28.7's stated goal was 1-fragment chunks as the reliability floor. Record growth is the bigger factor than the compression-ratio drift. Worth confirming whether records added fields (item-name strings, slot indices, new schema columns) since v0.28.7 before tuning chunk size further.

7. **No CTL stall in this log.** Every chunk transmission line shows CTL.avail in the 2900-3650 range; 0 CTL deferrals reported on every Send-complete line. The v0.28.8 CTL-stall recurrence pattern is NOT triggered by this session. Failure modes here are server-side throttle (Mode 1), route asymmetry (Mode 2), and per-peer route variance (Mode 3), not client-side CTL exhaustion.

8. **No per-peer abort-backoff beyond peer's HELLO cadence.** Five Katorrí receive failures in 38 minutes, each triggered by the standard 4-minute HELLO; effective retry rate is bounded by the peer's broadcast cadence, not by any "this peer has failed N times in a row, back off" rule on local. Two Voxle send failures within 10 minutes of each other. Consider an adaptive per-peer backoff (e.g. exponential with cap) that kicks in after K consecutive aborts from the same peer.

## Open questions for the next investigation pass

- Receiver-side telemetry would resolve Mode 1 conclusively. Is the receiver in combat, dead, zoning, holding a saved-variables write, or otherwise event-blocked when chunk 601 should ACK? The sender-side `target=online` checks the friend/guild API, not whether the receiver's addon event loop is processing AceComm messages. Adding a one-line receiver-side audit ("CHUNK N received at T") would let cross-peer log correlation close the loop.
- For Mode 2 (Katorrí 0 chunks), distinguish "Katorrí dropped our SYNC_REQUEST" from "Katorrí responded but chunks were lost." One sender-side instrumentation line on Katorrí ("SYNC_REQUEST from local received, sending N chunks") plus one receiver-side line on local ("first chunk arrival from Katorrí") would partition the cause.
- Should "send N chunks then chunk N+1 stalls" preserve progress instead of aborting? Currently a single stuck chunk discards the prior 600 successful transmissions, and the next sync starts from chunk 1. The skip-and-continue design note in memory captures the receiver-side gap-tracking work this would require; this log strengthens the case for it.
- The bidirectional superset-skip should compare bucket-filter overlap, not raw tx count. The 121-differing-buckets counter-example is in this log.
