# UI notes

Moved from CLAUDE.md on 2026-09-28 (#282). Edit here, not in CLAUDE.md, which keeps a one-line map entry for this file.

- **UI/UI.lua**: Main AceGUI frame, tab switching, minimap button. **`GBL:RecordsForView(guildData)` is the one place an access level decides which rows a tab renders (#222), and both the build and every re-render read it.** `SelectTab` filtered and `RefreshUI` did not, so in `own_transactions` mode the filtered list existed between two calls of `ToggleMainFrame` and was replaced before the frame was seen, under the banner "Showing your transactions only.", on every bank open, every storing scan and every completed sync receive since v0.15.0. Nothing in the suite rendered the mode for four years, and the reason is worth keeping: the AceGUI mock had no `widget.label`, so any spec that built one of the three history tabs threw on the first cell (`lbl.label:SetWordWrap(false)`); the mock grew the field with #222. The filter is `FilterToOwnRecords`, matching `ResolvePlayerName(record.player)` against `GBL:GetOwnCharacterNames()`, which is the account roster (`db.global.characters`, see `src/Core.lua` `RecordOwnCharacter`) plus the logged-in character, added the same way so its rows show before the first roster tick records it. Both skip the `UnknownRealm` sentinel, so a cold realm empties the set and the member sees nothing rather than someone else's rows. **Never a bare-name compare**: the retired `FilterByPlayer` tested `StripRealm(record.player)` against `UnitName("player")`, which passed a same-named character on another realm and failed the member's own alts. **A bare name `playerRealms` marks ambiguous (the `false` sentinel) is refused rather than resolved**, because the resolver falls back to the local realm on both sides and a stranger's rows would render as the member's own; the limit that stays is a bare name with no roster entry at all, which nothing here can tell from the member's. The roster fills as characters log in and is never backfilled, which is why the user-facing copy says "the characters you have logged in on since updating" rather than every character. `GBL:GuildRankIndex` caches the last rank read this session, because `GetGuildInfo` answers nothing for a few frames after a loading screen and reading that as a change flips `_AccessTabSignature`, rebuilds the tab bar, and in a `sync_only` guild parks the player on the Sync tab. `GetAccessLevel` fails closed when no rank has been read at all and defaults a threshold with no mode to `own_transactions`; it cannot close the window right after login, because the policy hangs off the guild name and `GetGuildInfo` returns name and rank together, so the guard above it has already answered `full`. Both are display-side, and the wire values are untouched because `AccessTabs` treats every level other than `sync_only` as the full tab set, so a new mode string would hand every member on an older client the whole ledger. **`GBL:AccessTabs()` is the one producer of the allowed tab list and `GBL:HasAccessTab(value)` is the one question asked of it (#244).** `RebuildTabs` puts that list in the bar; anything opening a tab by name asks `HasAccessTab` first, because the two access families are independent and a rank can hold sort access while the view family leaves it in `sync_only` (`docs/PLAN-views-and-access.md` section 3). `OpenRestockTab` was the caller #244 was filed against, and it got past the bar two ways: a shrunken bar keeps hidden frames carrying their old `value`, so AceGUI matched one and built Restock under the restricted banner, and a bar that never held it matched nothing, so the window opened on whatever tab the rank does get and nothing said why. **The check is computed, never read off `tabGroup.tablist`**, which would also be right about the stale frames (they sit past `#tablist`) but is only as fresh as the last `RefreshAccessTabsIfChanged`, so a player demoted over HELLO would keep opening the tab until the next roster tick. **Computing it makes the staleness cut both ways, which is why the select is retried**: `playerInTier` and `IsGuildMaster` read `GetGuildInfo` raw with no rank cache, so a rank crossing the sort threshold gains access instantly while the bar waits for a `GUILD_ROSTER_UPDATE` that nothing in the addon ever requests (there is no `GuildRoster()` call in `src/` or `UI/`). When the computed list is WIDER than the bar the select matches nothing and would go silent, so `OpenRestockTab` reads `activeTab` back after selecting and, on a miss, rebuilds the bar and selects again. **It also returns early when the tab is already active**, because `GBL:SelectTab` is a `ReleaseChildren` rebuild and real AceGUI `SelectTab` has no already-selected short-circuit: during the confirm-at-price pause that rebuild drops the focus the pause put on Confirm, since `st.focusConfirm` was consumed by the build that entered PRICED. **The cold-open shortcut was tried and withdrawn**: pre-setting `activeTab` so `CreateMainFrame`'s own `RebuildTabs` builds Restock directly does skip a throwaway Transactions build, but it makes that the first route that lays the tab out against a frame `CreateMainFrame` has already hidden, with no `RefreshUI`, `DoLayout` or `_RefillScrollContainers` after the `Show`, and `SetAutoWidth` and `AddFillChild` both resolve against frame metrics there. The suite cannot see it (the mock's `GetWidth` is a hardcoded 80 and `GetStringWidth` a hardcoded 40), so it needs an in-game reading first and is filed rather than shipped.
