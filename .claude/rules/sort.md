# Sort subsystem notes

Moved verbatim from CLAUDE.md on 2026-09-28. Edit here, not there; CLAUDE.md keeps a one-line map entry for each file.

- **src/Scanner.lua** — Guild bank slot scanning (inventory snapshots). Also owns bag scanning for the sort (#139): `ScanBags` reads bags 0-4 plus the reagent bag synchronously through `C_Container` into a bank-shaped snapshot keyed by NEGATIVE pseudo-tabs, skipping bound, locked and link-less slots with per-bag counters and warming the item cache once per distinct item. **Those counters are not scanner-local bookkeeping any more**: the planner reads `boundSkips`, `lockedSkips` and `noLink` off the snapshot and reports them on the plan line as `bound=`, `locked=` and `nolink=`, so a player whose bags looked full but deposited nothing gets the reason instead of a zero. Anything added to the skip set needs a counter and a term beside them or it becomes an invisible subtraction. **The bank half of that rule is half-kept on purpose.** `ScanTab` skips a slot two ways: locked, which it counts into `tabResult.lockedSkips` and which the plan line reports as `locked=` since v0.39.12 (#178; see the SortPlanner bullet), and link-less, which has no counter. Before that the locked count only ever reached the SYSTEM channel (`T5=12(event,locked=2)`), and a sort gets diagnosed from `/gbl sortlog`, so from the plan line's point of view it did not exist. A `nolink=` term beside it needs to know what `GetGuildBankItemInfo` returns for a slot with no link, which nothing had recorded, because `ScanTab` gates every read on `GetGuildBankItemLink`. v0.39.12 probed for it with a per-scan `Scan linkless:` line on the system channel; it read zero warm and zero again after a full client relaunch with the bank opened first (2026-09-19, on #178), a consumer-side zero of exactly the shape the 2026-08-29 lesson warns about, which proves nothing about the API. That closed the question as a decision to stop measuring rather than as a finding, so v0.39.15 removed the probe (#184) and put the info read back under the link test, where it costs one call per occupied slot rather than one per slot. **Admission never moved through either change**: the link gates it and a locked slot is counted only when it has a link, which is what keeps `lockedSkips` meaning what `locked=` says. `TabFromBagID` / `BagIDFromTab` are the encoding (bagID N is tab `-(N+1)`, so a pseudo-tab can never collide with bank tabs 1-8 nor enter `layout.tabs`, whose Validate rejects tabIndex < 1), and `FormatSlotRef` is the single render helper every sort-side site routes through so a negative tab can never surface as `T-1`. The reagent bag is admitted only when its client-supplied index round-trips through the encoding, and `BagIDFromTab` rejects a non-integer tab: both keep a tab the executor could not decode back into a bag index out of the pipeline. `ExtractItemID` and `GetMaxStack` are both existence-guarded because Scanner loads ahead of BankLayout and ItemCache in the .toc. **`FinalizeScan` also records what the scan could look at (#137)**: `lastScanCoverage = { viewableTabs = {...} }`, read back through `GetLastScanCoverage`, written in that one place beside `lastScanResults` so a snapshot and its coverage always describe the same scan. It cannot ride on the results table, and that is the whole reason it is a second record: `FinalizeScan` sums `itemCount` over every value and the planner formats every key as `T%d`, so a placeholder entry for a hidden tab breaks both, and `UI/LayoutEditor.lua` reads a present entry as "scanned, capture it" and would record an empty template for a tab it currently declines with an accurate message. Three states, not two: nil means no scan has finished and nothing may be concluded; an empty list means a scan ran and saw no tab, which the planner acts on; a populated list is the filter. The list is copied out of `scanState` rather than shared, which no mutation can currently observe (`resetScanState` allocates a fresh table) and is hygiene rather than a fix.
- **src/SortPlanner.lua**: Pure-function move planner: given a bank snapshot + layout, produces deterministic ordered op list (split/move) to reshape bank. Assign-then-schedule algorithm: Phase 0 pre-merges same-item partial stacks across the overflow space (#145: every usable overflow tab is one contiguous space in `OrderedOverflowTabs` routing order, the first tab being virtual slots 1 to 98, the next 99 to 196, and so on), walking it as virtual slots (two-pointer pour up to the per-item max stack size from ItemCache or an opts.maxStackByItem override) so the space is compacted to its minimum slot count BEFORE any routing happens; a pour crosses tabs when the run does, and `diag.phase0CrossTabPours` counts those. The receiver is the larger partial (the earlier one on a tie), not the earlier one outright, so a pour can carry stock backwards in the order and Phase 4 then brings the merged stack forward: one item pooled across the boundary can cost a cross pour and a cross pack move, which is why `merge=(cross=)` and `pack=(cross=)` are counted apart. Phase 1 builds demands (slotOrder-pinned + items.slots extensions that right-extend then left-extend to keep each item's group contiguous), assigns each demand to the best source (same-tab direct → overflow → cross-tab; largest-count first within each tier; keep-slot harvest protection), and routes leftover supply to overflow via a capacity-aware pickOverflowSlot that runs the four tiers once over the overflow space in routing order (#145 reversed #57's tab-major walk, which ran all four tiers in one tab before any tier in the next: now a same-item partial in a later tab is topped up before a fresh slot opens in an earlier one, and a run continues from the last slot of one tab into the first of the next, so tiers 2 and 3 read across the boundary), the tiers being (1) topping up an existing same-item partial slot, then (2) right-extend, (3) left-extend, (4) first-empty; a single supply may split across multiple destinations, tab boundaries included, until consumed or unplaced. **Tiers 2 to 4 hold a take to one stack (#151)**: tier 1 already capped at the destination's capacity, but the three that open a fresh slot returned the caller's whole remaining supply, so an oversized supply landed there as one illegal stack. The three share one exit now and the cap sits at it, with `m >= 1` as the test (a max stack of 0 or nil is unknown, and a cap of nothing would place nothing and call the tab full), and a deferred whole stack (#146) stops deferring once a clamped take has left a partial behind, or its remainder opens the second partial the deferral exists to prevent. No real bank or bag slot holds more than a stack, so the clamp is unreachable from live input; `diag.overflowClamps` counts each held take and a WARN `  overflow clamp: N take(s) held to max stack` continuation says so if a fixture or a scanner change ever produces one. **The clamp covers this one producer and no other.** The fresh-placement branch of `canExecute` and `applyOpToState` does not compare `op.count` to the max stack, so the same impossible input still lands whole through Phase 1A (a `perSlot` of two stacks or more, which is #150's ground), `findPivot` parking a blocker, and Phase 4 packing; that gap is recorded on #168 beside its siblings. `spec/sortplanner_spec.lua`'s `applyPlan` holds a fresh placement to the ceiling as well as a merge since this change, so any of those producers emitting one reds every fixture that runs its plan through the simulator. **Tier 1 is skipped for a whole stack while another whole stack of its item is still behind it in the walk, and within one source (all the bank tabs as one source, then each bag) whole stacks are walked before partials, so a whole stack in tab 5 spills before a partial in tab 3 (#146).** Topping up from a whole stack splits it and leaves a remainder that is itself a partial, so the next whole stack split into that one and the odd remainder walked through every stack of the item: eleven ops for six stacks in the 2026-09-07 capture. The LAST whole stack still tops up, which lands the remainder at the tail of the run in one split and leaves the run canonical for Phase 4. A deferred stack that no overflow tab can take whole tops up after all: with nothing free the remainder cannot open a new partial, so that cannot restart the cascade, and skipping it stranded the room a second tab's partial still had (Phase 0 merged within a tab then; since #145 it pools across the space, so that reason is gone and the second one keeps the branch) and spent a deposit on a top-up a bank stack should have made, both caught in review. The walk sort's final key is the supply index, which keeps the order total and the walk deterministic, and the old slot order between stacks of the same kind is pinned. Neither the pure form of fix (a) on the issue (a whole stack never tops up) nor a whole-first walk alone gets there: the first leaves a whole stack after the partial, which Phase 4 cannot reorder at all today (#147: a same-item destination refused for max stack is never classified as stuck, so both stacks come back `cycle-no-pivot` with zero ops and the residual repeats every pass), and the second still cascades into a partial that was already in the tab. Phase 2 schedules moves via a greedy feasibility loop and breaks swap cycles with a pivot slot (same-tab empty preferred, overflow fallback). **The stuck scan reads `canExecute`'s reason rather than comparing itemIDs, and a `max-stack-overflow` refusal counts as stuck only when the assignment carries `pack = true`, which only Phase 4 sets (#147).** The scope is the whole finding: on a Phase 4 packing assignment that refusal means two stacks of one item must exchange positions and a pivot settles it in three ops, while on any non-packing assignment (the guard is `a.pack`, so Phase 1B spills are covered by it too) it can only mean the layout's `perSlot` exceeds the item's max stack, since Phase 1A takes `min(perSlot - filled, available)` against a `filled` capped at `perSlot`, 1B spills are capacity-tracked, `findPivot` never adds to a demand slot, and `Validate` checks only `perSlot >= 1`. Pivoting there would empty the demand slot, fill it, and plan the identical pair again next pass. That case stays a zero-op residual and is spec-pinned as such. **The loop is bounded by `GBL.SORT_PIVOT_BUDGET` (500), overridable per plan by the test-only `opts.pivotBudget`, and the budget exit now records what it drops** as `cycle-budget-exhausted` and clears it (#138). **`diag.phase2CycleAborts` counts abort EVENTS and `diag.phase2StrandedAssignments` counts the assignments they gave up on (#165)**, rendered as `P2 pivot=%d(abort=%d,stranded=%d)`. They were one field under the first name, incremented once per remaining assignment at all three abort sites, so one cycle abandoning eight pending assignments reported itself as eight aborts. `scripts/audit-sessions.lua` parses the term without a closing paren so both forms still read, and its `phaseZeroAbort` measure means the same thing across the change, since the counter only moves inside an abort path and zero of either is the same event. Note the budget site was the only one of the three with a spec pinning its count: a mutation deleting the increment at either no-pivot site survived the whole suite, and a raise-probe proved both are reached, by four #147 and #143 fixtures that assert other things. Both halves are load-bearing: without the record the sources stay unflagged and Phase 3 sweeps to overflow the very stacks the plan gave up on, and without the clear Phase 4's own run of the loop picks the stale assignments up and moves stacks the plan already reported unplaced. A spec pins that no op ever sources from a reported slot. Phase 3 sweeps stragglers using the same multi-destination overflow routing. **`opLabel` is the only thing that writes `op.op`, and all three op producers route through it (#161).** The Phase 3 sweep used to hardcode `"move"` while its count came from tier 1, which caps a take at the destination partial's capacity, so a sweep into a same-item partial described itself as moving a stack it only took part of. The pivot hardcoded it too and was right by construction (its count IS `blockerSlot.count`); it goes through `opLabel` anyway, because the value is one writer rather than three sites that agree by inspection. Call it BEFORE `applyOpToState`, or the label inverts. Nothing on the execution path has read the field since #169, so what this protects is `UI/SortView.lua`'s preview and progress rows and the executor's per-op sort-log line. Reaching that sweep branch at all is a three-way squeeze, which is why it had no fixture for so long: Phase 1B hands every non-overflow supply either an assignment or a `recordUnplaced` at its own slot and every Phase 2 abort flags its source, so the only producer of an occupied, undemanded, unflagged display slot is `findPivot` priority 1 parking a blocker; that pivot needs the blocker's own spill to have failed, so overflow was full for its item; and the label is only wrong if tier 1 has capacity again by Phase 3 and less of it than the swept stack needs, which `rebuildOverflowSlotInfo` supplies by re-reading state after Phase 2 drained a slot of that item. The `op labels (#161)` fixture in `spec/sortplanner_spec.lua` is the only thing in the suite that gets there, and every `phases:` line in `docs/sort-logs/` still reads `P3 sweep=0`. Phase 4 packs the overflow space into one deterministic contiguous run from virtual slot 1 sorted by (itemID ASC, count DESC, virtual position ASC), so a stack moves between real tabs when its rank crosses a tab boundary (#145); partial-stack merging happens earlier in Phases 0/1B. **The space is internal to `PlanSort` (#145, v0.39.17).** `V = #overflowTabsOrdered * MAX_SLOTS`, `vToReal(v)` and `realToV(tab, slot)` sit beside the #181 walk; Phase 0, the tiers and Phase 4 run over `v`, `vToReal` is applied at every emit, and `pickOverflowSlot` and `notePlacement` keep their real-slot signatures, so nothing outside the function and no op, deficit, unplaced entry or log line ever sees a virtual index. `unplacedSlots` stays keyed by real slot and Phase 4 maps through it per virtual slot. `findPivot`, Phase 2, Phase 3 and `overflowStackOrder` did not change; the comparator's third key is the virtual position under its old name. **The cost model, settled at the re-audit against the 2026-09-16 estimate.** That estimate carried #140's 146-op figure forward and doubled it for a 196-slot space; the stay-put rule below means a run of interchangeable stacks whose target range shifts by one moves ONE stack, the one that fell outside the new range, so a stack inserted ahead of a run costs one move per later run, not per later stack, and the first sort after #145 costs one move per run whose range moves across the boundary. Pinned by the boundary-split spec (a 97-stack identical run plus one inserted stack packs in three moves, one pivot included) and measured by two new terms on the `phases:` line, `P0 merge=N(free=,cross=)` and `P4 pack=N(cross=)`, present at zero because the brackets are unconditional. Bounding Phase 4 beyond that is a contract change for the Sort rework design pass. **The full-space limit.** A space with no free slot cannot be reordered: every Phase 4 cycle needs a pivot, none exists, so the pack aborts as `cycle-no-pivot` and the residual repeats until a slot frees. A full tab had the same limit; one space widens the cases that hit it, since bringing a stack forward into a full earlier tab needs a free slot somewhere. The #146 two-tab spec pins it deliberately, with both tabs at 98/98 after its spill. The first converged bags-off sort after this lands is the after capture: its final replan should read `frag=0 extra=0 partials=51 items=53` on the baseline bank with no `overflow split:` line, and its `cross=` counts are the cost measurement. **A slot Phase 2 gave up on is excluded from the packing entirely (#143): it is skipped when the stack list is built, and the rank-to-slot target list skips it too, so the run closes around it and the stack the plan reported unplaced is never shoved aside.** The producer is a Phase 2 abort on any pending assignment whose source is an overflow slot, and note that both aborts and the budget exit record EVERY remaining assignment rather than only the stuck one: an ordinary overflow-sourced demand fill (source tier 2) that is merely still pending when an unrelated cycle gives up is flagged too. The reachable fixture is the over-stack refusal above, because it strands an overflow slot while the rest of the tab stays free; that is why the branch had no fixture for so long. The fix is skip-and-reserve rather than packing the slot like any other, since an idempotent `recordUnplaced` would change what `_BagStays` sums. **Within a run of stacks sharing an itemID AND a count the assignment minimises movement rather than following the comparator's origSlot rank (#140, v0.38.1): a stack already inside the run's slot range stays put** (the range being the run's target slots, which stopped being its rank indices at #143 and became virtual slots at #145, so a run straddling a tab boundary does not churn at it). Those stacks are interchangeable, so a move between two of them has no observable result, and ranking them by origSlot made the target depend on current positions, which executing the plan changes. A pass that ended early therefore re-aimed the rest of the plan instead of shortening it, the replan came back larger than the work that remained, and the executor's non-decreasing rule stopped the sort with a residual. The fixture shape is the whole finding: a tab of DISTINCT items never reproduces it, because the comparator settles on itemID or count and never reaches the origSlot tiebreak, so a repro needs many stacks sharing both. `count` in the run test is load-bearing and is pinned by three existing packing specs. Hard max-stack invariant: `canExecute` and `applyOpToState` refuse same-item merges that would exceed the per-item maxStack (looked up via the same getMaxStack closure as Phase 0/1B), so the planner cannot emit a plan that depends on illegal in-state over-stack accumulations (a merge; a fresh placement of a stack that is already over-sized is not checked there, see the #151 note below). Phase 4 cascades that would otherwise over-stack are reordered by the greedy drain or bailed via the existing pivot/cycle paths, the same-item two-cycle included since #147. Items with unknown max stack (cold cache after `/reload`) skip Phase 0 merging and Phase 1B top-ups for that item only, falling back to grouping; a follow-up sort completes the work once item info loads. Repeat sorts are idempotent. Existing stock crosses between overflow tabs only as the space's order requires (#145; before it, never). Reports deficits, unplaced items (with reason code), and the overflow tabs in routing order (`plan.overflowTabs`, with `plan.overflowTab` kept as a first-entry alias). **`opts.coverage` filters the overflow tabs by what the scan could see (#137).** It carries `{ viewableTabs = {...} }` from `GBL:GetLastScanCoverage()`; a declared overflow tab outside it leaves the routing order and lands in `plan.unviewableOverflowTabs` (ascending by index, always a table, present on the invalid-layout early return too), so `plan.overflowTabs` publishes only usable tabs. The seeding loop is what made this necessary: it hands any declared tab absent from the snapshot 98 free slots, and the scanner omits a hidden tab exactly as it omits an unscanned one. **Every production caller supplies it, `PrintDeviations` included** (`src/Core.lua`), and that last one is the trap: its own output reads `demandMap` only, so it looks exempt, but `PlanSort` writes its plan line to the sort log whatever the caller does with the result, and the Sort tab runs the command after every executed sort. Without coverage there, one capture carries the run's filtered plan and then an unfiltered one routing into the tab the run skipped. It passes coverage and deliberately not bags, since bags cannot change a line it prints and a bag scan is not free. **Absent coverage means no filter**, which is what keeps the fresh-layout case working and what every pre-#137 caller and spec relies on; an EMPTY `viewableTabs` is not absence, it is a scan that saw no tab, and reading it as absence puts a client with no visibility back on the seeding path. When a layout declares overflow tabs and none survives, the unplaced reason is `overflow-unviewable` rather than `no-overflow-defined`: the two need different actions from the player (a rank change against a layout edit), and both the Phase 1B spill and the Phase 3 sweep read one computed `noOverflowReason` so they cannot drift. The plan line gains ` unviewable:T5,T7` or ` unviewable:none`, present whenever coverage was handed in, on the #139 rule that a term's presence says the input was there. `SummarizeSortPlan` appends one line per hidden tab AFTER its "no moves needed" fallback, and `PrintSortPreview` skips its own empty-plan early return when a tab was hidden, or it would answer the case this exists for with "every demand is already satisfied". **Bags are an optional source-only input (#139)**: `opts.bagSnapshot` carries `ScanBags` output as negative pseudo-tabs and is deliberately NOT part of `snapshot`, so tab classification, the `perTabOccupied` breakdown and `BankLayout.Validate` never see one. Admitted slots are filtered to the union of display-tab `items` keys and merged into `bank` between the overflow-ensure loop and the state deep copy, which is `bank`'s only consumer. Bag supplies are appended AFTER the `tabOrder` walk rather than joining it (a negative key would sort to the front and put deposits ahead of bank leftovers in the spill), and `findBestSource` gives them tier `p = 4`, below every bank source, because shuffling inside the bank is free and a deposit is not. Both paths order bags by bagID, backpack first: the spill walk sorts `bagTabs` descending, and the tiebreak maps a bag onto `-tabIndex` so a raw negative compare cannot rank the reagent bag ahead of the backpack. Bags can never be a destination (findPivot walks the blocked tab plus overflow tabs, Phase 3 sweeps display tabs, Phase 4 packs overflow tabs), and `spec/sortplanner_spec.lua`'s `applyPlan` asserts `dstTab >= 1` on every op it is handed. That assert only covers plans actually run through `applyPlan`, which most bag-side tests do not do; the guard that catches a bag destination in the rest of them is the container mock, which raises on a drop into a bag. **The bank input term carries the same promise as the bag one, from #178.** `(input: %d slots / %d tabs)` became `(input: %d slots / %d tabs, locked=%d)`, summed from `tabResult.lockedSkips` in the same snapshot walk that produces `inputSlots` and `perTabOccupied`, published as `diag.bankLocked` and assigned across from a local because that walk runs ahead of the `diag` literal. The per-tab breakdown gains `T5:12(locked=2)`, and **that suffix is the one place in this file a term is allowed to stay quiet at zero**, because the total in the bracket is unconditional and already carries the zero; the total itself is present at zero on the #139 rule. The walk covers the WHOLE snapshot, **ignore tabs included, and that is a decision with a spec on it**: `inputSlots` already counts an ignore tab's slots (the walk runs before `ignoreSet` is built), so excluding their skips would make the two halves of one bracket mean different things. Watch the field-name collision: a bag snapshot carries `lockedSkips` per pseudo-tab too, and only the table it sits in separates the two, which is why a spec pins the bank total against a non-zero bag count rather than trusting the read. `scripts/audit-sessions.lua` needed no change, checked against all three of its plan-line reads (`^Sort plan:`, the literal `", 0 unplaced "`, the ms-stripped signature) rather than inferred from #165, where it did. **Two continuation lines say how fragmented the overflow tabs were on input (#181)**, the ruler #145 is measured against: `  overflow: items= frag= partials= extra= unknown=` and, when `frag` is above zero, `  overflow split: <item> T6x7 T7x6, ...` (ten named then `, and N more`, sharing `STAY_LINE_MAX_NAMED` with `bags stay:`; the item text is whatever `DescribeItem` gives, `Name (it:ID)` warm and `it:ID` cold). Read off `bank` right after `getMaxStack`, before any phase, over `overflowTabsOrdered` (coverage-filtered and positive-only, so hidden tabs and bag pseudo-tabs never enter) at `MAX_SLOTS` virtual slots per tab in ROUTING order, so `frag` counts runs of consecutive virtual slots: an empty slot or a foreign stack starts a run and T6/98 to T7/1 does not. That is the order Phase 4 packs to since #145, which is why the pre-#145 steady state read two runs for an item held in two tabs (Phase 4 packed each tab from slot 1) and the converged state now reads one, and why #145 left this walk untouched with its own arithmetic: it is the ruler, and a ruler that shares code with what it measures cannot catch that thing being wrong. `partials` uses #151's rule (`m >= 1`, else the item is `unknown` and contributes nothing to `partials` or `extra`) and `extra` is partials beyond the first per item **on the input**: on an unconverged bank that includes partials Phase 0 merges in the same plan, so the figure #145 is judged against is the final replan's, where Phase 0 and Phase 4 have already run and what is left is the cross-tab residue. The lines have their own gate (`#overflowTabsOrdered > 0`, present at zero on the #139 rule), sit after the `phases:`/`demands:` pair and before the `overflow clamp:` WARN, and a converged overflow-only layout writes `overflow:` directly under `Sort plan:` with no phases pair. Three overflow lines now share a prefix, so every needle and every `SUMMARY_PATTERNS` entry carries the colon (`"  overflow:"`, never `"  overflow"`); `scripts/audit-sessions.lua` keeps both lines and its `--md` skeleton prints every kept line, so it needed nothing else. `GetLog` is newest-first, so a spec asserting emission order reads descending indices while a saved session holds it ascending, and the reader's hand-built pins were desk-checked against the emit calls rather than trusted (2026-09-18 lesson). The five figures are on `plan.diag` as `overflowItems`, `overflowFragmented`, `overflowPartials`, `overflowExtraPartials` and `overflowUnknownStack`, and nothing in the planner reads them. Diagnostics: `plan.diag.bagSupplies/bagDemandFills/bagSpills/bagStay/bagIgnored/bagBound/bagLocked/bagNoLink` plus a `bags:<admitted>/<seen>(stay=,ignored=,bound=,locked=,nolink=,fillops=,spillops=)` term on the plan line, **whose two halves count different things and say so (#165)**: `admitted`, `seen` and the five terms inside the bracket count SLOTS, while `fillops` and `spillops` count ASSIGNMENTS, so one bag stack split across two overflow destinations reads as 2. They led the bracket as bare `fill=`/`spill=` until #165, where they read as slots like everything beside them; renaming puts the unit where it is read and moving them to the tail groups the bracket by unit. The `diag` field names (`bagDemandFills`, `bagSpills`) are unchanged, so only the rendered string moved. The term is emitted whenever a bag snapshot was handed in rather than only when something was admitted (a run where every bag stack was rejected is exactly the run whose term a reader needs). A `  bags stay: <item> x<n> at Bag2/18 (<reason>), ...` continuation names up to ten admitted stacks the plan could not place and then falls back to a count. **Both the term and the continuation fold `plan.unplaced` by slot** via `bagStays` (exported as `GBL._BagStays` for its spec): one bag slot can be recorded several times, because Phase 1B records the leftover and either Phase 2 abort records one entry per remaining assignment, several of which share a source when a stack was split across destinations. The portions are disjoint takes from one stack, so they are summed and the slot is named once; counting entries instead reported one stack as several and repeated its slot on the line, so the preview's promise and the log agree on which stacks are staying behind. Every slot ref on both lines routes through `GBL:FormatSlotRef`, so a pseudo-tab can never surface as `T-1`. **`GBL:OrderedDeficits(plan)` is the one place `plan.deficits` becomes an order (#165).** It returns `{ itemID, count }` ascending by itemID, and both renderers read it: this file's `SummarizeSortPlan` and the Sort tab's Deficits list. Both walked the map with `pairs`, the one unordered output in an otherwise fully ordered pipeline, so two runs on identical input could print the same deficits in a different order and two people reading one capture wrote different rows. A spec fixture for this needs itemIDs whose `pairs` order is not already ascending, or the sorted and unsorted implementations agree and the pin proves nothing; the specs assert that property of their own fixture rather than assuming it. **`GBL:SortReasonText(reason)` is the one place a reason code becomes words (#45).** The `REASON_TEXT` table sits beside the code constants, and the two surfaces that render `plan.unplaced` AS PROSE read it: `SummarizeSortPlan` below, whose lines `/gbl sortpreview` prints (its only production caller is `PrintSortPreview`, which is chat-only, and `src/Core.lua` never writes to the sort log), and the Sort tab Unplaced list. One table rather than a copy each, because #137 shipped with the preview and the tab formatting the same field separately and disagreeing about the same plan. **The sort log is a deliberate third renderer in a different register**: the `bags stay:` continuation prints the raw code, because a capture is searched by code and a reworded sentence would break that, so a maintainer who greps and finds three renderers is looking at a decision rather than at drift. An unknown code returns the code itself rather than nothing, so a sixth reason (#150 would add one) shows something searchable before its text lands, and a nil reason returns "reason not recorded"; a spec asserts every code IN THE `_sortPlannerReasons` EXPORT has prose of its own and that no two share a string, which catches an entry dropped from the table but not a constant that was never exported. The summary line reads `unplaced: N x item:ID at SLOT: <reason>` and keeps the ` (stays in bags)` tail, since the tail says what happens to the items and the reason says why.
- **src/SortExecutor.lua** — Executes a plan fire-and-forget on a self-rescheduling `C_Timer.After(CADENCE=1.0s, pumpOne)` loop: each tick clears a stuck cursor, issues the planner's next op via `issueOp` (the WoW-API-mandated `SplitGuildBankItem`/`PickupGuildBankItem` src + `PickupGuildBankItem` dst sequence), clears the cursor again if the place left an item on it, advances `state.opIndex`, and schedules the next tick. There is no per-op confirmation, no timeout cascade, and no `state.waiting`; correctness comes from convergence, not per-move proof. The two reads left are the source lift's own and the cursor check straight after it, and both look forward rather than back: `liftFromBank` and `liftFromBag` decide a partial take from what the slot holds and refuse an op the slot cannot satisfy, then the guard confirms something actually reached the cursor before the destination half runs. Nothing checks an op once it has completed. When the op list is exhausted, `state.pumping=false`, the executor waits `SETTLE_DELAY=3.5s` (above the worst observed 3.3s deposit latency) so the last deposits commit, then runs `endOfPass`: `StartFullScan` → poll `scanInProgress` (`SCAN_WAIT_TIMEOUT=10s`) → `GetLastScanResults` → `PlanSort(snapshot, state.layout)`. If the new plan is empty → finish (clean); if it is non-empty but ≥ the previous pass's op count → finish (converged, residual reported, no infinite loop); if `state.passes ≥ MAX_PASSES=5` → finish with the residual; otherwise `startPass(newPlan)`. `state.layout` is required for auto-rerun and is threaded by SortView via `opts.layout = self:GetBankLayout()`; if nil, the executor finishes after one pass rather than re-planning to nothing. Bank-close abort is driven by Core (not a self-registered event, which would shadow Core's handler under AceEvent's one-callback-per-object rule): `GBL:OnBankClosed` calls `GBL:_SortExecutorOnBankClosed` to abort a running sort; `pumpOne` also re-checks `IsBankOpen()` each tick as a backstop. The executor registers no bank events of its own (the pump issues no event-driven confirmation, so there is no `GUILDBANKBAGSLOTS_CHANGED` handler to misfire on our own moves). A frame-hitch sampler (a single reused OnUpdate frame; `recordHitch` is pure and unit-tested) records inter-frame gaps so a capture shows whether the pump kept the render loop responsive. A stall watchdog (`C_Timer.NewTicker(5s)` running `checkStall`) re-kicks `pumpOne` when `state.pumping` AND `now - state.lastProgressAt > CADENCE + STALL_SLACK=6s` (the lost-frame-timer mechanism behind the historical op-88 hang), bumping `state.pumpToken` so a late original timer no-ops rather than double-issues. `finish` emits a per-run summary (passes, ops issued, residual, avg s/op, cursorStuck, stalls, rescans, plus `skipped=N` and its histogram when any op was refused), a hitch summary line, and a final ping, then calls `ClearCursor` + `stopHitchSampler` + `stopStallWatchdog`, clears `state`, and invokes the onComplete callback with `result = { ok, reason, done, failed, total, replans, passes, ... }` — that result shape is the SortView contract along with the `GBL_SORT_PROGRESS` message phases `start`/`step`(opIndex)/`planupdated`(plan)/`finish`. **Every field on that message means what it says, which took #162 to make true.** `issued` (not `done`) is `state.totalIssued`, because the pump cannot prove a move landed and only `finish` knows the residual, so `finish` attaches the real `done`/`failed` itself from the same two locals the `result` table uses; before that the tab's completion line and the chat print reported two different numbers under one word. `refused` is `state.skippedOps` and used to be `state.cursorStuck`, which counts destination pickups that SWAPPED rather than placed and is therefore a successful move; `cursorStuck` is still on the payload under its own name. **A `step` carries the PREVIOUS op's outcome** as `issuedOpIndex` or `failedOpIndex`+`failedReason`+`failedDetail`, stashed on `state.lastOutcome*`. The emit fires before `issueOp`, so this op's outcome is not knowable yet, and a second emit after it would have to mark one index both current and settled; riding it one tick forward costs no extra message and leaves exactly one row current with the settled run behind it. Three consequences to keep. `finish` carries the stash out, because the last op has no following step. `startPass` clears it and the `planupdated` emit carries no outcome field, both needed, because a new plan renumbers every row. And reason and detail stay apart on the wire, because the sort log's own `why` string already brackets the detail and a row rendering that would nest parentheses. The producer guarantees `opIndex` never equals either outcome index, which is what makes the consumer's mark order free; it is spec-pinned, because a mutation reversing that order survived. **`src/Ledger.lua` `RescanTransactionLogs` calls `GBL:_sortNoteRescanTick` while a sort runs, and until #165 the bullet here claimed that made the summary count rescans that competed with the pump.** It could not: `ExecuteSortPlan` stops the periodic rescan for the run's duration, so the only remaining caller is the executor's own 15-op flush, which then notes itself, and `rescans=N` was `floor(totalIssued / 15)` in every capture this repo holds. The term is `flushes=` now and the note is the one place either figure is counted, **deliberately in the callee rather than at the flush call site**: `RescanTransactionLogs` returns early on a closed bank and on missing guild data before it reaches the note, so a counter at the call site records an intent, which is #90's `reply=sent` under another name. A genuinely competing rescan is still reachable through one path the stop cannot cover, the Auto re-scan checkbox ticked mid-sort on a run that began with the rescan already off (there was nothing to stop, so `rescanWasActive` is false and no flush fires either); `state.inOwnFlush` tells the two apart, the first external tick is named once at WARN, and `extrescans=N` rides the summary only when non-zero. The old code logged the first 40 and every one of them was the sort's own flush. To stop the periodic rescan from starving the pump (its `numTabs+1` synchronous `QueryGuildBankLog` burst hitches the main thread every ~3s and stretched per-op time from 1s to 3-4s in-game), `ExecuteSortPlan` captures `state.rescanWasActive = GBL:IsPeriodicRescanActive()`, stops Ledger's rescan via `GBL:StopPeriodicRescan()`, and `finish` restarts it via `GBL:StartPeriodicRescan()`, which self-guards on `bankOpen`, `_initialScanComplete`, `rescanEnabled` and already-active, so a bank-close exit safely no-ops. **The `Sort: resumed the periodic rescan` line reports the outcome and not the attempt (#165)**: `OnBankClosed` clears `bankOpen` before aborting the sort, so on that path the restart does nothing and the old unconditional line claimed a resume that never happened. It reads `IsPeriodicRescanActive()` after the call, which covers all four guards without restating any of them, and stays silent otherwise because the abort reason is already on the summary line above. To keep capturing without overflowing the bank's ~25-entry per-tab log, `pumpOne` calls `GBL:RescanTransactionLogs(function() end)` every `TRANSACTION_LOG_FLUSH_OPS=15` issued ops (gated on `state.rescanWasActive` so a user-disabled rescan stays off). **Bag deposits (#139)**: an op with a negative `srcTab` has its source half lifted by `liftFromBag` through `C_Container` instead of `PickupGuildBankItem`; the destination half is unchanged. `liftFromBag` refuses a slot that is gone, locked, holds a different item, or holds too little, takes exactly `op.count` by splitting whenever the slot holds more than that (decided from what the slot holds NOW, not from the plan-time `op.op`, because a stack the player topped up between Preview and Execute would otherwise be deposited whole and the destination was sized for `op.count`), refuses as `no-api` rather than falling through to a whole-stack pickup when a partial take is needed and `SplitContainerItem` is absent, and `issueOp` returns false and stops **before** the destination pickup, which is the load-bearing ordering: `PickupGuildBankItem` on an empty cursor does not place, it picks the destination slot up, so falling through after a refused source would harvest an innocent bank stack. **The source-lift guard is the bank half of #169's fix and it took three releases to land right.** The bank branch had no equivalent of `liftFromBag`'s refusals: a bank source that was gone, locked, or read stale-empty put nothing on the cursor, fell through, and the destination pickup harvested a stack the plan never named. So `issueOp` checks the cursor after either lift and returns `false, "lift-failed"` before the destination, which also covers the failures no pre-check can see: a split the server refuses, a slot locked between the read and the call. A client that cannot answer keeps the old behaviour rather than refusing every op, because an unreadable cursor is not evidence that the lift failed. **The predicate is `GetCursorInfo()`, never `CursorHasItem()`, and that is a measurement rather than a preference.** v0.39.5 gated it on `CursorHasItem()` without once watching it run against a guild bank cursor; in game it refused every op attempted (30 then 5, across two hand-cancelled runs of a 207-op plan, 0 issued either time), and v0.39.6 withdrew it and shipped `probeAfterLift` in its place. The 2026-09-17 capture (`docs/sort-logs/2026-09-17-cursor-predicate-outage-and-probe.md`) then ran 238 bank lifts that all demonstrably succeeded, since the bank converged and the replan came back empty, and read `GetCursorInfo [item:238], CursorHasItem true=0 false=238`. **The same capture refuted the signal this project had twice written down as authoritative.** The probe deliberately led with source drain, on the standing finding that `PickupGuildBankItem` updates the client's slot view optimistically; it read `src drained=0 not-drained=238`, and 162 of those lifts had their source tab selected at the time, so the view-gating caveat does not cover it. The slot API does not see a lift within the same frame, and the optimistic update is at the display layer. Drain stays authoritative read across frames, which is what `endOfPass` relies on; the counter is gone from the probe and must not come back. **The guard carries a fuse, which is what the outage bought.** `LIFT_GUARD_FUSE = 5`, exported as `GBL.SORT_LIFT_GUARD_FUSE`: once the guard has refused that many ops in a run **without ever once passing**, it disables itself for the rest of the run, logs a WARN, and the probe line gains ` guard=disabled`. The arming condition is "never passed" and not the count alone, because a guard that has demonstrably worked and then starts refusing is seeing real failures, and standing down there would be the harvest bug under another name. It trades a harvest no capture has ever recorded against an outage that has. #191's ledger inherits that trade: under a blown guard a fallen-through op's destination is recorded like any other write, so a later bypassed lift from it can fall through again, and the accepted harvest can chain; gating the write on the fuse was considered and declined on the same reasoning, since a blown guard is a blind predicate whose lifts are in fact landing, and the ledger is what keeps those runs converging. The probe line's ` guard=disabled` is the flag either way. **The rule the outage produced: never gate a safety action on a predicate whose real behaviour has not been observed**, with the corollary that a verification expires, which is the whole reason the fuse exists. **The pre-op `ClearCursor()` is unconditional**, the second casualty of the same blind spot: it and `cursorStuck` were both gated on `CursorHasItem`, so for a bank item neither ever fired, and the `cursorStuck=0` in every capture this repo holds was never evidence of a clean cursor. Both read `cursorLoaded()` now. The unconditional clear is also the recovery path for the op before it, since a client will not pick a second item up while one is held. **`bagOpsIssued` is incremented past the guard rather than at `liftFromBag`'s return**, because a bag source can now be refused at two places and counting at the first makes `Sort bags: N deposit(s) issued` count deposits that never reached a tab. Refusals from both source kinds count into `state.skippedOps` and `state.skipReasons`, surfaced on the run summary as `skipped=N` with a sorted reason histogram, absent at zero; the bag counters stay separate so the `Sort bags:` line keeps its meaning and the run total sits at or above it. **`liftFromBank` is the bank half of that pair (#169), and it reads like `liftFromBag` on purpose.** No slot refuses as `empty`, a slot holding less than `op.count` as `short-stack` with the count as detail, more than `op.count` splits for exactly `op.count`, and exactly `op.count` is taken whole (what a real client does with a split whose count equals the stack is not recorded anywhere here, so the pickup is the branch whose shape we know). **It reads `op.op` in exactly one case** (the stale-source bypass below, #191); everywhere else the slot decides, which is what makes a mislabelled partial harmless at execution and demotes #161 to a correctness-of-plan issue outside that case. Two checks `liftFromBag` has are deliberately absent: `locked` and `item-mismatch`. A bank slot's locked flag and item link come through the same view-gated cache as its count, and a stale-locked read would refuse an op that would have worked while the cursor guard already covers a slot that is genuinely locked. **The count had the same exposure in the low direction and it took #191 to see it**: the guard compensates for a read that is stale HIGH (the lift finds nothing), and nothing compensated for one that is stale LOW (the pre-check refuses a lift that would have worked). **The stale-low producer is the run itself (#191, v0.39.16).** A tab the client is not viewing answers a slot read as of that tab's last query, so a slot the run wrote earlier in the pass on a tab that is off screen reads whatever it held when that tab was last queried or viewed: the 2026-09-19 capture (`docs/sort-logs/2026-09-19-overflow-baseline-and-unviewed-tab-refusals.md`) refused eight ops in that shape and none outside it, every one a pivot on the overflow tab with another tab on screen, so a three-op pivot cycle lost its third op every time, the replan planned the same cycle, and run A's non-decreasing rule stopped it with 23 ops remaining. The executor keeps `state.wroteThisPass`, a set of `T/S` keys written in `issueOp` PAST the cursor guard (the `bagOpsIssued` rule: a refused op reached no destination) and reset in `startPass`, because every pass follows a full scan that re-queries every tab. `liftFromBank` hands a source in that set whose tab is not `GetCurrentGuildBankTab()` to `liftPerPlan`, which does not judge the count: `op.op == "split"` takes `op.count` through `SplitGuildBankItem` and anything else takes the stack whole, the read is logged beside it (`Sort op N/M: stale source T7/69 (written this pass, viewing T6) reads 1, lifting 14 per plan as move`, INFO because it is the fix working), `state.staleSourceLifts` counts the attempt, ahead of the lift and the guard, so a bypassed lift the guard then refuses sits in both `stalesrc=` and `skipped=` (that pairing is the reading, not a double count), and the summary carries ` stalesrc=N`, absent at zero like `skipped=`. Two conditions on purpose: a written slot on the VIEWED tab reads live and keeps the pre-check (the player can take from it mid-run), and an unwritten slot off screen keeps it too (nothing can tell a slot the player filled from one the last query missed, and the refusal is what a capture reader wants named). A client whose `GetCurrentGuildBankTab` is absent or answers nil treats every written slot as off screen, in production as in the spec, and the guard bounds that. The proxy is nearly tight: `src/Scanner.lua` is the only production caller of `QueryGuildBankTab`, inside a scan, so mid-run a tab's cache moves only with the view, with the end-of-pass scan, or with a scan the player starts by hand (the Sort tab's Scan bank button, `/gbl scan` and the Layout tab's capture all call `StartFullScan` with no gate on a running sort), after which the ledger over-fires for the rest of that pass and the bypass lifts per plan on a read that would have agreed with it. **This re-couples execution to the label in that one case**, so #161's single writer is load-bearing at execution again and `applyPlan`'s assertion in `spec/sortplanner_spec.lua` is the pin; a `want` of zero stays with the pre-check. The mechanism rests on the mock's `viewGatedReads` model and the capture's pattern, not on a same-slot read both ways: the next capture reads `stalesrc=` against zero `short-stack`/`empty` refusals on written slots, and a `lift-failed` on one of them is the plan being wrong about its own write. In the executor spec `currentTab` is nil (`before_each` queries no tab), so every self-written bank source in a non-gated multi-op fixture takes the bypass; the 2026-09-19 survey found none besides the #191 fixtures. A refusal is ordinary rather than an error (the plan is a snapshot and the player can move things mid-run), so it is counted, named at WARN with its slot, and left to convergence. **The refusal vocabulary is source-agnostic where it can be**: `empty`, `short-stack` and `no-api` come from either lift and `lift-failed` from the guard that covers both, while `no-bag`, `locked` and `item-mismatch` come only from `liftFromBag` for the reason above: `liftFromBag` returns `false, reason[, detail]`, the WARN reads `Sort op N/M skipped: Bag1/25 <reason>, wanted <count> x <item>` with `short-stack (have 12)` and `item-mismatch (holds it:999)` carrying the detail, and `state.bagSkipReasons[reason]` counts each. A reason is what makes a capture actionable: "skipped" alone cannot tell a player who moved a stack mid-run from a client whose container API is missing. **A refused op is not an issued op**: `state.totalIssued` and the transaction-log flush counter both live under the issued branch, so a run of refusals cannot re-fire the flush and cannot inflate the summary's ops-issued count or its average seconds per op. Only the abort path adjusts `result.done`; the normal path stays `total - residual`. `opts.includeBags` is kept for the whole run in `state.includeBags` and `endOfPass` re-reads the bags via `ScanBags()` for its replan: before this, `ExecuteSortPlan` stored only `opts.layout` and `endOfPass` re-planned with no third argument, so pass 2 would silently revert to bank-only and strand the rest. The snapshot is re-read rather than cached, or it would still show the stacks the pass just deposited. **`endOfPass` rebuilds every opts field the run needs, never carrying one from the opening plan (#137 generalises #139's trap).** It now also passes `coverage = GBL:GetLastScanCoverage()`, from the scan that pass just ran, so a tab that became visible mid-run is picked up on the next pass and a bank-only run is filtered too. Any future opts field belongs in that same block; one added only at `BuildSortPlanOpts` (which builds opts for the Core callers and is never consulted by the executor) is silently dropped from pass 2 onward, which is the exact defect `includeBags` had. `result.bagOpsIssued` / `bagOpsSkipped` and a `Sort bags: N deposit(s) issued, M skipped [locked:1 short-stack:1], still in bags: K (U unplaceable)` summary line report the split, plus `result.bagSkipReasons`, `bagsStillInBags` and `bagsUnplaceable`. The line is written whenever `state.includeBags` is set, including a run that issued no bag ops at all, and is absent entirely when bags are off. The histogram appears only when something was skipped and its keys are sorted, so two captures of the same run read identically rather than in `pairs` order. **K and U come from the LAST replan's `diag.bagSupplies`/`bagStay`, not the first plan's**, stamped into `state.lastBagSupplies`/`lastBagStay` in `endOfPass`: the first plan describes what was in the bags before the run, which is the one number the summary must not report. A run that aborted before any replan says `still in bags: unknown (no replan)` rather than guessing. The start line carries `bags=on|off` from the same flag, so a capture says which mode produced everything below it. **Two limits to read the tail with.** `still in bags` counts only stacks the layout names, so it can say 0 while the player's bags are full of items the layout never mentioned; the plan line's `ignored=` term is where those are counted. And `ScanBags` skips a locked slot, so a bag slot still locked from the pass's own deposit activity is neither planned nor counted by the `endOfPass` rescan: `SETTLE_DELAY` plus the full scan makes that unlikely and a follow-up sort clears it, but a run can in principle report 0 with a stack left behind.
