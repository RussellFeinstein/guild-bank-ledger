# Sync subsystem notes

Moved from CLAUDE.md on 2026-09-28 (#282). Edit here, not in CLAUDE.md, which keeps a one-line map entry for this file.

### Protocol / transport

- Sync transport stack is **AceSerializer → LibDeflate → AceComm → ChatThrottleLib → `C_ChatInfo.SendAddonMessage`**. AceComm splits payloads into 255 B wire fragments; a 980 B compressed chunk is ~4 fragments. Whole-chunk loss compounds: at per-fragment drop probability `p`, chunk loss is `1 - (1-p)^n`. Moving from 3 to 4 fragments at p=5% raises chunk loss from 14% to 19%.
- AceComm WHISPER has an empirically ~2000 B reliability ceiling (`WHISPER_SAFE_BYTES` in `src/Sync.lua`). Staying under it is necessary but not sufficient — fragment *count* is an independent reliability factor.
- `ChatThrottleLib.avail` is the **client-side** bandwidth meter only. It does not model server-side per-recipient addon-message throttling that Blizzard's chat server applies to `SendAddonMessage` independent of CTL. A healthy `CTL.avail` can still coincide with server-dropped messages when chunks are issued <1s apart.
- `C_ChatInfo.SendAddonMessage` via `AceComm:SendCommMessage` does not return a useful delivery status — reliability is observed only via ACK/NACK/timeout at the protocol layer. Do not branch on its return value.
- AceComm's progress callback fires per CTL piece; only `sent == totalBytes` indicates "handed to the wire," and only then should the ACK timer start. This is the v0.23.0 contract codified in `SendNextChunk`. **And only for the session that issued the chunk (#273).** Nothing can cancel the callback, so a chunk still queued in ChatThrottleLib when its session is torn down completes afterwards, and unguarded it stamped the wire anchor and started an ACK ticker for whatever came next: after a bare teardown an orphan ticker, inside a new session a phantom retry that resent that session's chunk and booked an `ackTimeout` into its `chunkFail` and `p_frag`, and during a new session's preparation a `Send complete ... -1/0 chunks` block that freed the slot under the running preparation. The callback captures `syncState.prepToken` at issue and returns when `sending` is false or the token has moved, writing `Chunk N to <peer> transmitted after its session ended` instead. Two things not to undo. **The token is `prepToken`, deliberately not a second counter**: the accept in `HandleSyncRequest` bumps it once per session and nothing moves it while a send is live (`_AbortSyncPrep` returns first unless a preparation is live, and a request arriving while `sending` returns before the bump), so a counter of its own would be a second copy of one number. **Both halves are needed and neither is written at a teardown**: `sending` covers a teardown with nothing new started and the token covers a new accept, which is what keeps every teardown site out of it (#122 is about how those sites drift; #281 folded their chunk tag into one writer). The late line stays rather than being dropped because it is the only trace that a queue outlived a teardown. Both it and the live `Chunk N transmitted` line measure queue-to-wire from the issue time captured with the token, never from `sendChunkSentAt`: a teardown zeroes that field, and a NACK resend queued behind an attempt rewrites it, which made the first attempt's line report the resend's queue time. Out of scope here: a NACK can move the send index while an attempt is still queued, and that attempt's callback then sets the ticker for its own chunk, because the guard is per session and not per chunk. This was recorded as benign until the code review of #281 showed otherwise: the ticker's retry branch acts on the send index, so it can resend an acked chunk, discard a genuine late ACK, or step the index below 1 (#296). **And never while sync is paused (#284).** A loading screen cancels the chunk's ACK timer and the resume resends the chunk (#295), so the callback of a chunk that completes inside the pause stamps the wire anchor, writes its `Chunk N transmitted` line with `paused, no ACK timer` inside the parentheses, and returns. A timer armed there could only book a retry and an `ackTimeout` for the pause, or fire while the resume waits on ChatThrottleLib and step the index below a chunk whose genuine ACK is then discarded as stale. Three things not to undo. The anchor is still stamped, because the ACK can arrive inside the pause. The rider sits after the existing fields, because the #273 specs read the line's prefix and its `(N.NNs queue-to-wire` figure. And there is no second pause check inside the ticker body: the pause cancels every timer armed before it and nothing arms one during it, so the check would be dead code. The check reads `isSyncPaused()` to match `SendNextChunk`'s own deferral, though only the zone half can be true here, since a combat start ends a live send and the serve gate refuses a request during the combat cooldown; a mutation narrowing it to `zonePaused` survives for that reason, and the rider names no reason because only one can occur (the `Loading screen detected` line sits above it). A callback that completes after the pause clears, while the resume waits on ChatThrottleLib, still arms a timer, which is #296. **The callback is not the only thing a dead session leaves scheduled, and the code review of the #273 branch caught its first cut treating the rest as benign.** The inter-chunk delay `HandleAck` sets, a NACK's 0.5s resend, the gap-floor timer and the CTL backoff all call `SendNextChunk` later with no session of their own. During the next session's preparation such a call found the empty chunk list the accept installed, answered it with `FinishSending`, and freed the slot under the preparation, the same consequence as the callback route. **`SendNextChunk` returns while `syncState.prep` is live**, which closes that window for every route at once: nothing legitimately issues a chunk mid-preparation, because stage 7 calls it itself after `_ClearSyncPrep`. Inside a new session that is already sending, such a call still issues that session's next chunk early; that is the timer-chain overlap `overlapTotal` counts, unchanged here.

### Name forms quick reference

GBL handles three distinct name forms. Mixing them is a collision risk; each has a dedicated producer and a fixed set of consumers:

| Form | Example | Where it lives | Producer |
|---|---|---|---|
| Qualified `Name-Realm` | `Katorriwl-Stormrage` | `record.player`, `record.scannedBy` (after the `sync:` prefix), all migrations | `GBL:ResolvePlayerName` |
| Canonical peer key | bare for same-realm, qualified for cross-realm | keys of `syncState.peers`, `guildData.knownPeers`, `syncState.peerBusyUntil` | `GBL:CanonicalPeerKey` |
| Bare name | `Bob` | `recentWhisperTargets` keys (chat-system suppression), UI filter inputs | `GBL:StripRealm` |
| Raw network sender | whatever AceComm passes | runtime only; must never be stored without canonicalization | always wrap in `GBL:CanonicalPeerKey` before keying any peer-state table |

Helpers:

- `GBL:NormalizeRealm(realm)`: strips whitespace from a realm portion (e.g. `"Aerie Peak"` → `"AeriePeak"`). Always normalize before equality comparison or persistence.
- `GBL:GetLocalRealm()`: normalized local realm, or `"UnknownRealm"` sentinel when realm APIs are cold.
- `GBL:_isLocalRealm(realm)`: `true` iff realm matches local (raw or normalized). Used by `CanonicalPeerKey` to decide whether to strip.
- `GBL:BuildRosterCache()`: populates `guildData.playerRealms[bareName] → realm`. Two-pass: detects bare-name ambiguity and writes the `false` sentinel when a bare name maps to multiple distinct realms in the roster (so `CanonicalPeerKey` can refuse to guess and keep ambiguous bare arrivals bare).
- `GBL:RepairCorruptedPlayerRealms(t)`: trims hyphen-corrupted realm strings carried forward from a long-fixed code path; called from `BuildRosterCache` on each invocation. Leaves `false` sentinels untouched.

`ResolvePlayerName` priority order: **explicit `playerRealms` arg → current guild's playerRealms → local realm fallback**. There is no cross-guild fallback. Bare names from the bank log are assumed to belong to the current guild, not a guild the user previously belonged to. Migrations pass the per-guild table explicitly via the `playerRealms` arg.

### Code invariants to preserve

- Logging is split across four channels owned by `src/Logger.lua`, listed in `GBL.LOG_CHANNELS`. Sync code calls `GBL:SyncInfo / SyncWarn / SyncError / SyncDebug`; sort code calls `GBL:Sort*`; system events call `GBL:System*`; transaction recording calls `GBL:Ledger*` (#85). The lower-level form `GBL:LogSync(level, fmt, ...)` exists for runtime-computed levels. Each channel is a session-only ring buffer (sync 2000 / sort 3000 / system 500 / ledger 500, FIFO from tail; sort is largest so a full sort run stays in the on-demand view). DEBUG entries are dropped entirely unless `db.profile.<channel>.debugChat` is on, which preserves the prior `chatOnly=true` "do not pollute the buffer with per-chunk noise" property without a separate side channel. Chat mirroring is gated by `chatLog` (INFO/WARN/ERROR) and `debugChat` (DEBUG). `GBL:AddAuditEntry(msg, chatOnly?)` is a deprecated shim that routes plain calls to `SyncInfo` and `chatOnly=true` calls to `SyncDebug`. `GBL:GetAuditTrail()` is a permanent alias for `GetLog("sync")` that also exposes a legacy `entry.timestamp` field; new readers should use `GetLog(channel)` or `GetMasterLog(opts)` directly. Slash commands: `/gbl synclog`, `/gbl sortlog`, `/gbl systemlog`, `/gbl ledgerlog`, `/gbl logs` (master pop-up), `/gbl logs dump [N]`, `/gbl logs clear sync|sort|system|ledger|all`, `/gbl logs debug sync|sort|system|ledger on|off`. The Sync tab no longer carries an always-visible audit panel; logs surface only on demand via slash command.
- **An event count goes on the wire no later than the first record of any bucket whose records can use it, and nothing may reorder that (#114 v0.41.8, widened by #270 v0.41.10).** `PrepareChunks` indexes each entry under every bucket in its **ride set** and emits it when the record walk reaches the first record of whichever of them comes up first, so per bucket `max(usable entry chunk) <= first-record chunk <= last-record chunk`, and therefore **any prefix of the chunk list that completes a bucket's records carries every count those records can use**. That prefix property is the whole fix, because an abort is exactly a prefix. **It holds by construction, not by luck:** `emitBucketEntries` runs for every record in both lists, so an entry reaches the leftover pass exactly when no record produced any of its ride buckets, and a leftover entry therefore has no first-record chunk it could be late for. The emission chunk is the minimum over the ride set of the first-record chunk, which is at or before every member's, so nothing rests on which ride bucket the walk reaches first. **The ride set is `GBL:EventCountRideBuckets` (`src/Dedup.lua`), and it exists because "usable" is not "in the same bucket" (#270).** `CleanupWithEventCounts` reaches a count `GBL.EVENT_COUNT_SLOT_RADIUS` (1) hourly slots either side of a record's own slot, because two scans of one transaction can round its hour differently, so a count on the edge of a bucket is owed to the neighbouring bucket as well as its own: one bucket for a slot inside a bucket, two for a slot on either edge. That radius is one exported field, read only through `GBL:EventCountWindow` (`src/Core.lua`), which is the one writer of the window's shape and returns it as offsets from a record's slot; its three consumers are this function, the cleanup loop it mirrors, and since #275 the count filter, with the two count-side ones walking the span reflected. The first cut of #275 copied the loop bounds inline in all three and the code review caught it, which is #270's two-copies defect one level down: a local in any of them leaves two windows with one name to show for it. It deliberately does **not** govern the three other slot-drift windows in `src/Dedup.lua` (`CountFromRecordIndex`, `CountStoredForHash`, `FindDriftedCount`), which share the number and answer how many records exist under a prefix. **The packer indexes every entry under its whole ride set, and the filter may admit an entry only for a bucket inside it.** `EventCountRidesWithBuckets` admitting a boundary count without `PrepareChunks` indexing it under the neighbour puts it back in the trailing carriers this ordering exists to empty, because its own bucket has no records in the send and so no first record to ride ahead of, which is #114 reopened. **What #270 measured:** all 46 of the counts that were usable locally and unsendable forever became offered, 22 more of the 104 empty-bucket counts became reachable through a neighbour populated by another prefix, and 36 stay unreachable because no bucket in their ride set holds any record, which is the inert population #270 put out of scope. **#275 (v0.41.14) narrowed the filter to what a neighbour can use.** A count rides with its own bucket, as before #270, and through a neighbouring bucket only when the send carries a record of its prefix whose id slot is within the radius of the count's: the cleanup's own `prefix .. s` lookup, run from the count's side. Stage 5 builds `prep.sentBaseHashes` from the stripped copies through `GBL:BaseHashForRecord` (`src/Fingerprint.lua`), which reads an id with the same file-local `RECORD_ID_SLOT` pattern `bucketKeyForRecord` files the record by, in one scan, and that one reading is what keeps every admission inside the ride set: a record at slot Y in the window sits in `BucketKeyForTimeSlot(Y)`, a member by construction. No record index means no neighbour admission. **Measured on the live store (19,262 records, 16,883 counts):** per bucket taken alone, #270 admitted 4,328 counts through a neighbour (+25.8% over the own-bucket rule, +262 on the worst bucket), and the prefix rule keeps 998 (+5.9%, +160), keeps all 46 and drops all 22. The slot-only reading #275 was filed with would have kept 3,870, because most hours on a bucket edge hold some record, which is why the test matches the prefix. **Read those figures per bucket, not per session, which #270 and the first #275 comment both got wrong.** A session takes a contiguous run of buckets, so a count on an edge between two selected buckets rides with its own bucket under every rule and only the run's outer edges differ: a ~480-record backfill slice carries about 26 fewer entries (about 7 chunks, roughly 1%), one isolated differing bucket about 8 fewer (about 2 chunks, roughly 4% of that small session), and the newest one to three buckets 0 or 1. **The filter no longer allocates per key.** `EventCountRideBuckets` built a table for every key the stage 6 walk crossed; the predicate now reads the own bucket and at most three index keys, and over one serve's 16,883 keys the garbage fell from 886 KB to 21 KB and the time from 50-55 ms to 46-47 ms across two runs (desktop Lua 5.1, one harness for both; the garbage figure is the steady one). The bucket test ahead of each index lookup is a cost guard, not a correctness one. The index holds records of carried buckets, so the test changes no answer except when a sync chunk arriving mid-preparation has rewritten a selected record's id across a bucket edge (`NormalizeRecordId`, sender wins), and there it withholds a count the moved record could have carried, which is as safe as admitting it. Without it the predicate builds the `prefix .. s` string for every key, which measured 82-84 ms and 92 KB, so a mutation that drops it survives by design. **The accepted limit:** a receiver that already holds copies in the neighbouring hour which we do not have loses our count for them through the neighbour route, which is where it stood before #270. Its own bank scans mint their own counts (`StoreBatchRecords` in `src/Dedup.lua`), so what stays exposed is duplicates it got by sync from a holder that lacked their count. Since #114 (v0.41.8) a copy's own-slot count goes out ahead of it in every session that sends its bucket, so such a holder is debris from before that ordering. The code review raised this limit as re-exposing the #114 trap and it was declined on that reasoning. **A second limit, from the same review:** the filter reads a record's prefix and slot from its id, while the receiver's cleanup groups by `BuildTxPrefix` over the fields and takes the slot from the timestamp. They agree for every record the builders produce; where they do not (the roughly 17 corrupt-type records in `docs/DATA-MODEL.md`, and 0 id-versus-timestamp slot disagreements measured), a count can go out that the receiver cannot apply, or not go out through the neighbour. The id is the reading on purpose, because #114's guarantee is over the packer's reading, and the packer reads the id. **One window the own-bucket half never closed:** stage 3 groups records by the id they had then and the packer reads the id stage 5 copied, so a chunk rewriting a selected record's id across a bucket edge in between can leave a count admitted on its own bucket with no record of it left in the send, and that count rides a trailing carrier for the session. It predates #275; the neighbour route cannot produce it, since its index is read off the copies. **The remaining limit is the fallback reading, and it measured zero.** The invariant is over bucket KEYS and the two sides reach a key by different readings: a count key always yields its trailing slot, while `bucketKeyForRecord` reads the slot out of the record id and falls back to `floor(timestamp / BUCKET_SECONDS)` for an id it cannot parse. #270's measurement put numbers on it for the first time: of 18,988 records, 0 carry an id the trailing `slot:occ` pattern cannot read, 0 have no timestamp, and 0 disagree between `floor(timestamp / 3600)` and the slot in their own id, so the divergence below is a latent shape rather than a live one. Those agree for every record the current builders produce, and on the fallback too while the timestamp matches the slot, since a slot is hours and the divisor is the same; they cannot agree when `tx.timestamp` is absent, where the fallback keys off `GetServerTime()` at packing time. Where they disagree the per-bucket promise still holds and what it buys does not, because that record's own count is filed under another bucket and travels with that one, and on the bucket path it rides only if that bucket is also in the send. That is a selection question in `EventCountRidesWithBuckets`, not a packing one, and no capture has shown a record arriving with an id the pattern cannot read, so it is recorded rather than fixed: changing that fallback moves bucket placement, which moves the fingerprint, which is wire-visible and costs a floor raise. Before it the packer filled records first and then swept entries forward into leftover room and trailing carriers, so every session's counts rode in a tail that was 12% of the 2026-08-18 capture and a quarter of 2026-08-13. Counts contribute nothing to the fingerprint (`ComputeBucketHashes` walks the two record arrays only), so a session that delivered all of a bucket's records and then aborted before that tail left both sides' hashes for the bucket **matching**: the diff never selected it again, the serve's count filter only offers counts for selected buckets, no third peer offered it either because they converge on the same hashes, and the receiver cannot re-derive counts locally because they are minted from live bank scans against a log holding about 25 entries per tab. `CleanupWithEventCounts` never trims a cluster with no count data by design, so that receiver keeps its duplicates permanently, the surplus inflates its own bucket hashes so it diverges from every correct peer, and once the surplus pushes its total past the sender's the superset skip blocks the very pull that would have carried the counts. A convergence trap, not a cosmetic count. Aborts in that window were never exotic: two of four sessions on 2026-08-13 were killed by BUSY. **Sender-local and additive: no wire change, no `PROTOCOL_VERSION` bump, no floor raise**, because `eventCounts` was already an optional per-chunk field, `estimateEnvelopeBytes` already reserves its wrapper on every chunk, and the receiver's merge is max-wins with no ordering or completeness assumption. Six things not to undo. **The seal test is emptiness, not "has it got a record in it"**: a chunk holding entries and no records is legal mid-stream and on the wire, and the old record-only test seals it away as empty and drops them; with `eventCounts` nil the new condition is exactly the old one, which is what keeps the record-only suite byte-identical. **The emission mark is per ENTRY and is shared by both record walks**, because one bucket can own records in the item list and in the money list and must emit once, and because since #270 one entry sits in two groups: clearing the group it was reached through leaves the other group holding it, so a group clear alone puts a boundary count on the wire twice. The group clear stays beside it, since a bucket once emitted has nothing left to walk. **The money walk's own emit call is load-bearing for a money-only bucket**, and a fixture with records in both lists cannot show that, because the item walk always reaches it first: dropping that call survived the both-lists test and is killed only by the money-only one. **Correctness does not rest on the send list being bucket-contiguous** the way `SortSendListNewestFirst` leaves it, nor on which of an entry's ride buckets the walk reaches first, since the entries go out at the first record of one of them either way and that chunk is at or before every other member's. **Both add helpers re-read the open chunk's tables after any seal**, because sealing hands the old ones to the sealed chunk and installs fresh ones. And **the forward-cursor leftover pass stays**, for entries none of whose ride buckets sends records and for keys whose slot cannot be read: that is the #92 behaviour, and the no-`bucketHashes` fallback path makes it the normal case rather than an edge, because that path filters by time and has no bucket keys to filter counts by. **It walks the entries and not the leftover groups**, which is load-bearing from #270: an entry indexed under two buckets appears in two groups, so a group walk hands it to the cursor twice and puts two copies of it on the wire. The unmarked set is exactly what the record walks did not emit, unreadable keys included, since those reach no group at all, which is why the separate orphan list is gone. Note that every fixture in the older #92 rider suite (`spec/sync_chunking_spec.lua`, "PrepareChunks with event counts") sits in **one** bucket, so that suite cannot see this property in either direction and stays green by construction rather than by luck; the interleaving specs beside it carry multi-bucket fixtures for exactly that reason. **And read `slotOf(bucket, offset)` in the interleaving describe before adding a fixture there.** Offset 0 is the FIRST hour of a bucket, so a count written at it also rides with the bucket below; 5 is the last hour and rides with the one above; 1 to 4 are interior and ride alone. Every fixture predating #270 was written at offset 0 and so exercised the boundary path without saying so, which is why the interior case had to be added by hand and why two of them were moved to offset 5, where the records really are within the window of the counts they ride with rather than six hours from them. **The rejected alternative stays rejected**: folding counts into the bucket hash would make the loss self-heal, but a fingerprint change is the class `MIN_SYNC_VERSION` exists for, so it costs a floor raise and a split guild for the adoption window, which is not worth paying when a packing reorder closes the window for free.
- `syncState.lastChunkBytes` is the canonical compressed chunk size. Reuse it for fragment-count estimates (`ceil(lastChunkBytes/255)`) rather than re-measuring.
- `HasSyncBandwidth()` uses a **dynamic** threshold `max(CTL_BANDWIDTH_MIN, lastChunkBytes)` — this is the v0.28.2 fix for the burst-stall regression from v0.28.0. Do not regress to a fixed threshold.
- The superset skip in `HandleHello` and again in the bidirectional check after `FinishSending` is load-bearing for convergence. The `HandleHello` superset case now re-nudges a behind peer past the hash-gated HELLO-reply suppression: when we are ahead, our data is stable, and the reply gate set `roundReply == "hash-suppressed"` (the round-local state #90 replaced `replyDecision` with; it rides out on the round line as `reply=`, so the correlation the old DEBUG-only detail line recorded is now readable in any capture), the superset branch re-sends a HELLO reply (an isReply HELLO drives the receiver's `shouldSync`/RequestSync path, so it is a real pull trigger) throttled per peer via `syncState.lastSupersetNudge[key]` + `SUPERSET_NUDGE_THROTTLE` (60s). This is the "tried and failed, back off" the v0.28.x note asked for, confirmed in-game (2026-06-09 capture: an ahead client at tx 10955 went idle and silently starved behind peers Fluphie/Fxh of the nudge, so they never requested). Wire-compatible (reuses the existing HELLO reply, no new message, no `DEV_BUILD`). The bidirectional-check site after `FinishSending` applies the same re-nudge: when we hold more it re-sends the HELLO reply through the shared `syncState.lastSupersetNudge[cleanTarget]` + `SUPERSET_NUDGE_THROTTLE` throttle, so a behind peer is driven to pull rather than skipped silently. The shared throttle means the `HandleHello` and bidirectional sites cannot double-nudge one peer inside the same 60s window. This closes the symmetric pure-skip gap the v0.28.x amplifier note flagged (previously the site short-circuited on "likely superset" with no back-off, so when sends failed both sides could mutually skip).
- Stale-ACK discard in `HandleAck` (v0.23.0) and `ScheduleReceiveTimeout` rescheduling (v0.25.3) are real defect fixes, not patches — do not remove during refactors.
- **The SYNC_REQUEST manifest is bounded, and the span fold must never become an XOR (#108, v0.37.11).** The request used to carry one entry per 6-hour bucket over the guild's whole history: ~2,500 B and 10 fragments at 273 buckets, over `WHISPER_SAFE_BYTES`, with no ACK and no retry, so on an ~18%-per-fragment route it arrived about one time in seven. That is what starved peers while the log on the serving side showed nothing at all. `BuildRequestManifest` now sends the newest `SYNC_REQUEST_DETAIL_BUCKETS` (50) buckets in `bucketHashes` plus up to `SYNC_REQUEST_SPAN_COUNT` (8) `spans` of `{ s, e, h }` covering everything older: 58 entries at any depth. **Measured size: 1,447 B serialized, 704 B deflated, 709 B encoded, so 3 AceComm fragments, and that figure does not move with history depth** (the bucket count is irrelevant once the manifest is bounded; ~580 of the raw bytes are near-random hash digits, which deflate cannot do much with). If the request ever has to fit in 2 fragments, the lever is `SYNC_REQUEST_DETAIL_BUCKETS`, not compression. Both constants are exported from `src/Fingerprint.lua` and specs read the exports. The requester logs its own request size (`Requesting sync from ... N bytes`), so a capture taken on the requesting side gives the figure directly rather than by reconstruction. Three things not to undo. **The fold is order-dependent djb2, not XOR**: bucket hashes are already XOR aggregates, so XORing them flattens to one XOR over every record in the range and two peers each missing records the other holds can fold identically over different data, which both sides then recompute the same way forever. It is the prefix-hash cancellation objection one level up. **Spans tile the older range** rather than hugging the keys the requester holds, so a serving peer's unknown bucket lands inside a declared span instead of an uncovered hole. **A key no span covers keeps the original comparison** (`localHash ~= (detail[key] or 0)`), which is what makes an old peer's full-table request take a byte-identical path and is why no floor raise was needed; the untouched bucket-diff and session-cap suites are that proof.
- **A receive timeout at zero chunks resends the request; after that a session we asked for NACKs and one we did not closes (#108, #309).** Nothing arriving means the request went missing, and a NACK for chunk 1 asks for a retransmit of a send that never began, which `HandleNack` discarded on arrival because it was not sending, so the signal crossed the wire three times per failed request and was thrown away. Since #320 `HandleNack` answers it with a `not-sending` BUSY instead, which would end the receive and hold the peer off for the 30s cooldown over a request that merely went missing, so the resend is the only right answer at zero chunks. The branch reuses `SendSyncRequestTo`, the stashed `syncState.receiveSinceTimestamp`, the existing `MAX_NACK_RETRIES` budget and the existing backoff ladder, and adds **no new timer**: it runs inside the timeout callback already scheduled. Keep the callback's check order (duration net, offline, budget, then the unrequested close, the zero-chunk resend and the NACK). The #280 watchdog spec pins the first, and `leaves a sender gone offline to the offline arm` in `spec/sync_receive_spec.lua` pins the second: the older offline-detection spec reads only the word `offline`, which the bootstrap's blocked ACK has already logged, so it passes under either order. Resending is only reasonable because the manifest made the request small and fixed-size, so do not keep the retry if the request ever grows again. **It is 3 fragments, not the 1-2 this bullet claimed before it was measured** (see the manifest bullet above), and the 2026-08-18 capture shows what that costs: four `Could not decompress` warnings, every one at exactly 459 B, which is 254+205 and therefore a 3-fragment message that lost its middle piece. Middle loss is the only single-fragment loss that is visible at all, since losing the first or the last delivers nothing, so each logged warning stands in for roughly two silent ones. That is the case *for* the retry rather than against it: the request loss it recovers is real and measured, and it starved a peer for 13 minutes in that same capture. Its necessary partner: `HandleSyncRequest` **ignores a repeat request from the peer it is already sending to** rather than answering BUSY, because `HandleBusy` would tear down the receive that send is feeding. BUSY still goes to third parties, with one exception in a loading screen: a request from the peer we are receiving from is dropped too (#318, the combat-policy bullet below). Outside a loading screen the already-sending decline still BUSYs that peer, and since #323 that peer reads `sending:` and `preparing:` as a refusal of its request: it ends the receive it opened and keeps its send to us (the BUSY bullet below). A peer older than #323 still ends both. **The ignore sits above the combat and pause serve gate (#308)**: a loading screen pauses our send rather than ending it, so with the gate first, its zone term answered this very resend with BUSY for the whole pause and tail. The ignore writes an INFO `Ignoring repeat SYNC_REQUEST from <peer>` line, because the pause's decline used to be the capture's only trace that the resend arrived, and a DEBUG line never reaches a capture.
- **A receive we did not ask for closes at its first timeout instead of NACKing (#309).** The auto-bootstrap opens one on any chunk that arrives with no receive open. When that chunk is a straggler from a sender that has stopped, the NACK ladder (20 + 30 + 45 + 45 = 140s) ran at a peer discarding every NACK, and each HELLO round in that window answered `verdict=receiving`, so the pull after a short fight was refused. The timer now closes it through `FinishReceiving`, with an INFO `Unrequested receive from <peer> went quiet after N chunk(s), closing` line and no BUSY. Two things not to undo. **No BUSY**: a sender still going, stalled past 20s by its own loading screen or by ChatThrottleLib, must not be told to stop. Its next chunk can open a fresh receive, and its own 33s ACK ladder outlasts the close, so a chunk lost on the wire is retried across it. **`FinishReceiving`, not `_ClearReceiveSession`**: when the leftover chunk stored records, the post-sync HELLO it schedules is what restarts the refused pull within a few seconds. When it stored nothing, the pull waits for an ahead peer's heartbeat, which #310 carries. **What the close costs a sender that had only stalled.** Russell accepted this when he chose the fix (2026-10-01), and the code review showed it is wider than first written. The post-sync HELLO draws replies, and an ahead peer's reply starts a pull from that peer, so by the time the stalled sender resumes we are often receiving from someone else. Its chunks are then dropped as `Ignored SYNC_DATA`, unacknowledged, and its send runs its ACK ladder out and ends `by ack timeout`, booking those retries into its `chunkFail` and `p_frag`. When no pull has started, it resumes into a fresh receive, and one stream is reported as several sessions, each with its own `Sync complete` and `Redundancy from` lines over a partial sample, its own cleanup walk and its own post-sync HELLO. A capture tells the cases apart: a close line followed within seconds by `Auto-bootstrap` from the same peer is a live sender; a close followed by nothing from that peer is the stopped sender this fix exists for; and a sender's session ending `by ack timeout` just after our close is the orphan. The `Auto-bootstrap` line names both of its causes since #309 (`no receive open: a missed abort, or a quiet stream we closed`); a capture from an earlier build reads `prior abort signal likely missed`, which was the only cause then. **Where the close sits in the chain:** after the duration net, the offline arm and the budget, and before the zero-chunk resend. The first two orders are pinned (the order line in the bullet above). Against the budget the order cannot be observed, because an unrequested receive never NACKs and so reaches its timer with `receiveNackCount` at 0. Against the zero-chunk resend it can, in one state: #293's receive, opened with no chunk counted, which gets a timer only through a loading screen's resume. A receive we did not ask for sent no request, so it has none to repeat, and with the resend first it whispered the sender one we never decided to make. `closes rather than resend a request it never sent` in `spec/sync_receive_spec.lua` pins that order through the real path. That state is still #293's to prevent: with no loading screen nothing arms a timer, and nothing ends it. The bootstrap route into #290's wrong NACK is gone, since a bootstrapped receive no longer NACKs. #321's route, a requested session that joined a live stream mid-way, is gone too: that session is marked unrequested at its first chunk and closes here as well (the position bullet below). #320 was this bullet's symptom on the requested path: a sender that stopped behind a receive we did ask for cost the whole ladder. Since #320 that sender answers the first NACK with a `not-sending` BUSY and the receive ends there, and since #334 that holds when we are its live receive source too (the not-sending bullet below). The fixes not taken (a bootstrap guard on `IsPeerBusy`, and giving way to a HELLO) are argued on #309.
- **`ACK_TIMEOUT` and `MAX_RETRIES` move together (#92).** What matters is the product: total patience per chunk before the send gives up. They are 3s x 11 attempts ≈ 33s, down from 8s x 6 ≈ 40s. Changing one alone breaks the property they were tuned for: 3s at the old 6 attempts is ~18s, short enough to abort sends that today survive a receiver's 20-30s loading screen. Both are exported (`GBL.SYNC_ACK_TIMEOUT`, `GBL.SYNC_MAX_RETRIES`) and specs must read them rather than matching a literal delay — a spec that hardcoded `timer.delay == 8` matched nothing after the change and passed vacuously instead of failing, which is why `fireAckTimeout` errors when it finds no timer.
- **Free-agent pairing: a peer that finishes a session becomes free and takes whatever the next HELLO offers.** There is no stored picture of other members' bucket hashes and no scored queue choosing a "best" next partner. Both were removed in the v0.37.6 release along with the MANIFEST message that fed them (~335 lines): `syncState.peerManifests` had exactly one reader, the scoring loop inside `PopPendingPeer`, so the message and the scoring were the same feature. Removing it is wire-compatible in both directions, because the dispatch chain in `OnSyncMessage` has no `else`: an older peer's MANIFEST reaches an updated client and costs nothing. No `PROTOCOL_VERSION` bump and no floor raise. **The reasoning, which matters more than the mechanism:** gossip's guarantee is eventual delivery, not optimal routing, so it does not matter whether data reaches the most convenient partner next. The bookkeeping was not only code: `PopPendingPeer` recomputed every bucket hash (a full walk over 10k+ records) once per queued peer per pop. Two jobs the queue was quietly carrying had to survive it, and both are now single-purpose. **BUSY backoff** is `syncState.peerBusyUntil[peerKey]` plus `GBL:IsPeerBusy`, checked at the two automatic initiation sites (`HandleHello`'s skip chain and the bidirectional check's behind-branch) and deliberately NOT inside `RequestSync`, so a manual or forced pull still works. There used to be a second check behind the HELLO one, inside a jitter callback, to catch a BUSY arriving during the 0-1s deferral; it went with the jitter in v0.37.10 (#105), and a request now crosses a late BUSY on the wire instead, which `HandleBusy` resolves by aborting the receive it just started. **Combat deferral** is `syncState.helloAfterCombat` plus a forced `BroadcastHello` on combat end, which re-drives both directions (behind peers request from us, ahead peers reply or nudge). It is gated on the flag so a raid leaving combat together does not produce one broadcast per member; `FORCED_HELLO_COOLDOWN` is per client and would not stop that. The `isSyncPaused()` check is the third thing the queue used to provide, since everything deferred used to drain through `ProcessPendingPeers`, which checked. It is now its own arm in `HandleHello`'s skip chain, placed after the combat-lockdown arm so a HELLO arriving in combat still sets `helloAfterCombat`, and it logs which pause it was. What it covers is the cooldown that outlives the pause trigger (2s combat, 5s zone), the window in which `InCombatLockdown()` already reads false. Staleness and offline filtering are gone with no replacement and that is correct: a sync is now only ever started off a HELLO that just arrived or a session that just ended, so there is no way to name a peer we have not heard from.
- **BUSY carries a `reason`, and it is a required builder argument rather than an optional field (#97).** `GBL:BuildBusyMessage(reason)` has six producers and one caller, the file-local `sendBusy` (#317), which the four senders reach it through (`GBL:_SendBusyToPartners`, `refuseForCombat`, the decline and `HandleNack`), and six shipped values: `"combat"` from `OnCombatStart` through the helper (one BUSY per partner, #291), from the serve gate's combat terms, and from the auto-bootstrap's refusal of a chunk nobody asked for (#289), `"loading"` from the serve gate's zone term (never to our live receive source, whose request that term drops since #318, with the costs named in the combat-policy bullet), a loading screen's pause or tail (#308), `"sending:<peer>"` from the already-sending decline, which names who holds the slot, `"preparing:<peer>"` from that same decline when `syncState.prep` is live (#115b, v0.37.17), `"disabled"` from `DisableSync` through `GBL:_SendBusyToPartners` (#279, below), and `"not-sending"` from `HandleNack`, answering a NACK for a send we are not making (#320, the next bullet). The prep/send split is the one a capture reader needs: preparing is sub-second and sending is minutes, so the two say very different things about how long the declined peer should expect to wait. `HandleBusy` logs it, `unknown` for a pre-#97 peer. Additive with unknown-key passthrough, so no `PROTOCOL_VERSION` bump and no floor raise, on the same reasoning as #108. Since #202 the send-target branch hands its teardown to `FinishSending` rather than clearing fields inline, so the reason now arrives with a full summary block behind it; see the `chunkOutcomes` bullet below for what that changed and what must not move. **The receiver acts on a value only if it is declared a refusal (#323).** `loading`, `sending:<peer>` and `preparing:<peer>` are produced only in answer to a SYNC_REQUEST (the serve gate's zone term and the decline, both reached from the request dispatch alone), and `not-sending` only in answer to a NACK (#320), so `BUSY_REFUSAL_WORDS` in `src/Sync.lua` declares all four, keyed on the part before the colon. From our send target, one of them ends our receive from that peer if one is open, leaves our send or our serve preparation running with an INFO `<peer> busy - refused our request, our send to them continues` line (`our serve preparation continues` mid-prep), and still sets the 30s cooldown. `combat`, `disabled`, an absent reason, a reason that is not a string, and any word not declared end both sessions, as every BUSY did before. That keeps a new value free on the wire: a later producer gets the ending behaviour unless it is declared, so a word that only answers a message of ours goes in the set and every other word stays out of it. Record new values in this bullet. The route it closes: a peer serving us asks us for records (two requests crossing, its zero-chunk resend landing while we serve someone else), our decline answers BUSY `sending:<peer>`, and that peer used to end its send to us as well. **What it costs.** A requester older than #323 still ends both until it updates, so the gain arrives per requester. And a refusal no longer ends, by accident, a send to a peer that had stopped taking it in: its receive closed quietly (#309) or went to another sender, so our chunks draw no ACK. The BUSY says nothing about that peer's receive, so such a send runs out its ACK ladder (about 33s) and ends `by ack timeout`, holding our send slot that long, like any other orphaned send; the code review of #323 found it, and it was accepted rather than reading a receive state into a word that does not carry one. The zone door keeps #318's drop for every requester rather than BUSYing an updated one. A BUSY would hold an updated requester off for the 30s cooldown, after which it asks again at its next HELLO or when its send to us ends (its bidirectional check); the drop leaves it to its own resend, answered after our tail, which is usually no later. `combat` from the serve gate and the bootstrap refuses too, but ending both is still right for it: no receive is open on a peer while a combat term holds, so the send it would keep has no receiver. Two things not to undo. **`BUSY_KEYS` in `spec/wire_contract_spec.lua` must list `reason`**: that absolute set is the maintenance cost #70 deliberately bought, and it is the only thing that catches a field dropped from the one builder every site reads from, since parity compares the decline's and the combat abort's emitted messages to each other and a shared builder drops from both at once. **The value asserts beside it are not redundant with parity either**: two sites passing the same wrong reason still agree, so the shipped values are pinned individually; both failures were proven by mutation. The vocabulary the 2026-08-12 capture needed is exactly this: a mid-send BUSY can only be a combat abort, a BUSY answering a fresh request can only be already-sending, and until the field shipped a capture could not tell them apart. (Since #279 a mid-send BUSY can also be `disabled`, since #289 one reading `combat` can also be a receiver refusing a chunk it never asked for, in combat or its combat tail, since #323 one reading `sending:` or `preparing:` from our send target ends only the receive our request opened, and since #320 one reading `not-sending` answers a NACK of ours for a send that peer is not making.) **Every BUSY goes at NORMAL, and `sendBusy` is where that rule lives (#279, #317).** AceComm files an addon's traffic in one ChatThrottleLib queue per priority (`queueName = prefix`, so one first-in-first-out pipe for everything GBL sends at NORMAL, whatever the destination), so at NORMAL the BUSY queues behind any chunk or SYNC_REQUEST we still have waiting for that peer, and at ALERT it can leave ahead of one: the peer then acts on whichever arrives second, reopening a receive through the auto-bootstrap on a late chunk, or serving a late request into a client that has stopped. ALERT buys speed only while something is queued: ChatThrottleLib sends at once at any priority while its whole queue is empty, and `bQueueing` is shared by every addon on the library, so once any of them has queued, each priority with something waiting gets its own share of the bandwidth and an ALERT message leaves ahead of the NORMAL ring. That is exactly when it reorders, and the trade still favours NORMAL. A NORMAL BUSY waits behind everything GBL has queued at NORMAL, not only what is queued for its own peer: with two partners, the second BUSY waits behind the first, behind a chunk still queued to the other peer, and behind any queued guild HELLO, on top of other addons' traffic sharing the ring. That delay costs the send target nothing, since it waits on a 20s receive timeout. It costs the receive source ACK retries, each refused at the #289 gate with another BUSY, so a slow BUSY ends the same way, later. A reordered one costs a 140s phantom receive or a serve preparation (#291's re-audit). **One consequence of the ordering, accepted:** a final chunk still queued when combat starts reaches the send target ahead of the BUSY, so that peer completes the session, ACKs into a send we have torn down (`HandleAck` returns silently with no send live) and may send a receipt, while our own block reads `session ended by combat at chunk N/N`. The two logs then disagree about one session, and the partner's `Sync complete` line and receipt are the reading, because our side stopped before it could know whether the chunk landed. What ties them on our side is the transport bullet's `Chunk N to <peer> transmitted after its session ended` line, written when that queued chunk's callback completes after the teardown. The helper takes its partners as arguments, read by the caller before its teardown clears them, and whispers after the teardown; it sends one message when one peer held both directions, and writes `Sent BUSY to ...` only when `sendBusy` returned true. The decline and `refuseForCombat` follow the same rule through the same sender, and two structural cases in `spec/sync_peers_spec.lua` hold that: `builds every BUSY in one sender` fails if the builder is called anywhere else, and `spells out a BUSY message only in the builder` fails if one is written out as a table literal, which passed every key, reason and priority case until the code review of #323 asked. `OnCombatStart` sends through it too since #291, so no BUSY goes at ALERT: ACK and NACK are the only messages that do. The disable's BUSY has its own case in `spec/wire_contract_spec.lua` with the absolute key set and its value, because the parity case ends its send with the combat abort and leaves nothing to disable. **Not every teardown sends one, and that is deliberate for now**: the ACK-ladder and stalled-send aborts, the three preparation aborts (timeout, guild change, loading screen) and the receive side's retry-limit and 30-minute aborts are all silent, and they do not share one answer (a BUSY on the loading-screen abort would put the requester on a 30s cooldown, longer than the 20s resend it already falls back on). They are named on #279 and not filed. Since #320 the requester of a send that ended in a sender-side one (the ACK ladder, the stall, or a `/reload`) learns of it at its first NACK, which draws a `not-sending` BUSY. Until #334 the sender's live receive source was the exception.
- **A NACK we cannot serve draws a `not-sending` BUSY (#320).** `HandleNack` used to return silently unless the NACK came from our live send target, so a requester whose sender had stopped but stayed online (a `/reload` mid-send, the 120s send-stall teardown, an ACK ladder run out on lost ACKs) NACKed into silence for the whole ladder, 20 + 30 + 45 + 45 = 140s, and answered every HELLO round `verdict=receiving`. A NACK for a send we are not making (idle, or serving or preparing for someone else) now gets a BUSY through `sendBusy` and an INFO `NACK from <peer> for chunk N, not sending to them - sent BUSY` line, which claims the BUSY only when the whisper went out. `HandleBusy` ends the receive from its sender on any word, on every build, so the requester stops at the first NACK that lands whatever version it runs. Our own send target's NACK for a chunk out of range stays silent, one past any chunk we have sent is ignored with a line (#290, the position bullet below), and one below the chunk owed is #296's. Additive, so no `PROTOCOL_VERSION` bump and no floor raise. Two things not to undo, and one that was removed on purpose. **The receive-source exemption is gone (#334).** Until then a NACK from our live receive source got no BUSY and an INFO `... - no BUSY: receiving from them, and a BUSY would end their send` line, because a build without the word (v0.41.28 and older) reads it as undeclared and ends both sessions, which would have ended its live send to us. The v0.43.0 floor keeps every such build out of a session with a current client, so the silence protected nobody and left an updated peer on its whole ladder. Every NACK we cannot serve gets the BUSY now, from the peer sending to us as well, and our own receive from that peer stays open: answering touches no receive state of ours, and that peer reads the word as a refusal and keeps its send. One route to an older receive source is left, and it was accepted: the auto-bootstrap checks no version, so a peer below the floor that was sending to a client when it reloaded into a floor build finishes that send, and a NACK from it in that window now draws a BUSY that ends that send. That is one session per upgrade. Do not put the exemption back unless a build inside the floor's range turns out to lack the word. A capture from a build before #334 still shows the `no BUSY` line. **The word is declared in `BUSY_REFUSAL_WORDS`**, because it only ever answers a NACK of the requester's, so an updated requester ends only that receive and keeps any send to us. That matters after our `/reload`: its next chunk bootstraps a fresh receive here, so its send is still live. **A BUSY that ends a receive which has taken chunks goes through `FinishReceiving`, for every word.** `HandleBusy` used `_ClearReceiveSession` alone, which skips the `lastSyncTimestamp` checkpoint, the `CleanupWithEventCounts` walk, the `Sync complete` line and the post-sync HELLO. It skipped the hash-cache reset after an in-place id normalization too, until #330 moved that reset to the rewrite itself (the sliced-serving bullet). The NACK ladder's abort, which this word replaces at the first NACK, goes through `FinishReceiving`, so the quiet clear would have traded a 140s abort that recovers for a 20s one that does not. A receive no chunk has reached keeps the quiet clear, since the BUSY refused the request itself. The abort line `<peer> busy - ending receive after N chunk(s)` comes before the block, as `OnCombatStart` orders its own. **And the receive branch runs last in `HandleBusy`**, after the send teardown and the cooldown: `FinishReceiving` walks the history and can raise on a record the corruption class reaches (#263), which the quiet clear could not, and the first cut, which ran it first, let such a raise skip both (the code review of #320). **What it costs, accepted when Russell chose the fix (2026-10-02).** The requester takes the 30s cooldown on the stopped sender. Until #334 there was a second cost: when both directions ran with one peer and its send to us had stopped, the exemption left that peer on the full 140s ladder, which was the issue's lost-ACKs route whenever the two sessions were concurrent, and it included a pull the stopped sender started from that peer after its `/reload`. A requester older than #320 ends its send to us as well, since the word is undeclared on its build; none can be in a session with a client at the v0.43.0 floor, apart from the one session at upgrade time named above. What the fix buys, as arithmetic: the receive ends at the first NACK that lands, 20s after the last chunk, or 50s if that NACK is lost; a pull from another peer that is ahead can start seconds after the post-sync HELLO; a pull from the stopped sender itself waits out the cooldown and then the next HELLO round, 50 to 140s, against 142s before. A NACK that crosses our final ACK draws a BUSY after the requester has finished, which only starts the cooldown. The BUSY names no chunk, so one could in principle land in a newer receive from us; the requester opens one only after its post-sync HELLO (0.5 to 2s) and a round, while the BUSY trails its NACK by one hop, so this is recorded rather than guarded. There is no throttle: the ladder bounds an honest requester's NACKs at three per session and the first BUSY that lands ends it, and a peer that floods NACKs gets one BUSY each, as the already-sending decline answers every request.
- **The receive keeps its position by chunk number, and a copy of the chunk just taken is acknowledged and skipped (#290).** `receiveGot` counts chunks taken. `receiveLastChunk` is the number of the last chunk taken, read from `data.chunk` (a chunk with no number steps it on, as the count did). The NACK names `receiveLastChunk + 1`, and the retry-limit line, the sync-disabled line and `receiveProgress` read the position too. The count was right only when every chunk arrived once from chunk 1: a copy put it one ahead and the sender jumped past a chunk it had not sent, and a receive that joined a stream counted from zero and rewound it. `receiveGot` stays for the readers that want a count: `HandleBusy`'s `> 0` test and its line, the zero-chunk resend, the quiet close's line and `Sync complete`. No wire change, so no `PROTOCOL_VERSION` bump and no floor raise. Four things not to undo. **A copy is a chunk whose number equals `receiveLastChunk` and whose total equals `receiveExpected`, once a chunk has been taken, nothing wider.** Both start at 0, so without the taken term a malformed chunk numbered 0 with a total of 0 matched (the code review of #290). In stop-and-wait the only copy a sender makes is of the chunk it is on, and "at or below the highest" would skip a new stream's chunks 1 to K after a straggler K from a dead one. The other order cannot happen: AceComm queues every message under our prefix in one ChatThrottleLib pipe, first in first out, so a chunk queued by a torn-down session leaves before the next session's chunk 1 and cannot land between its K-1 and K. A copy from further back is walked and the position follows it. #296's step-back sends those: in its wire order 1, 2, 1, 2 both copies are walked and counted as duped, and the progress shown steps back for a moment, until #296 removes that order. The total is what tells a restarted send with a different chunk count from a copy. **The copy is ACKed, re-arms the receive timer and zeroes `receiveNackCount`, and is not walked.** The sender's ladder waits on that ACK and the copy proves the sender alive, while walked its records counted as duped, so the `Redundancy from` line and the receipt read transport repeats as bucket waste. It writes an INFO `Repeated chunk N/M from <peer>, already taken - ACKed, records skipped` line and counts in `receiveRepeats`, which `Sync complete` names only when it is not zero. **A requested receive whose first chunk is not chunk 1 is marked unrequested (#321)**, with an INFO `Receive from <peer> opened at chunk K: joined a stream already running, not the one we asked for (no receipt)` line. A sender we asked waits for each ACK, so its stream starts at 1, and one that starts later is a send that ignored our request as a repeat. It sends no receipt for its tail and closes quietly (#309). Its cost, accepted: a dead-session straggler landing first costs the real session its receipt. A chunk 1 dropped at the guild-name check (#293's window) does not trip it, because the drop sends no ACK, so the sender's next chunk is chunk 1 again. **`HandleNack` ignores a NACK for chunk K when chunk K-1 was never issued**, with an INFO `NACK from <peer> for chunk K, but chunk K-1 was never sent - ignored` line. It sits after the range check and before the ACK timer is cancelled and the NACK counters move, so the ladder carries on with the chunk in flight and the NACK is not counted. Only a receiver from before this fix can send one. **It cannot catch a count one ahead while the chunk in flight is lost**: an older receiver holding J-1 with one copy counted NACKs J+1, and J was issued, so the guard passes and J is skipped this session. No sender-side rule tells that from a receiver that holds J and lost its ACK, which #295 follows on purpose, and #296's owed-chunk rule accepts it for the same reason. The guard covers a count two or more ahead, and a count one ahead while the send is still on the chunk the receiver holds. It reads `chunkOutcomes`, which gains an entry only when `SendNextChunk` issues a chunk and is reset at every send start, because the ACK ladder's step-back and a second send chain both move `sendChunkIndex` (#296, #306). #296 re-keys it on the chunk owed and adds the backward half: a NACK below the chunk owed still rewinds the send today.
- **SYNC_RECEIPT carries the receiver's redundancy figures back to the sender, and it is log-only on purpose (#237).** The receiver computes the `Redundancy from <peer>` figure in `FinishReceiving` and the sender is the side holding `capLastTranche`, which decides what the next session to that peer carries, so the number the v0.28.8 decision rule reads lived on the wrong client. `GBL:BuildReceiptMessage` is the one builder, the emit sits in `FinishReceiving`, `HandleReceipt` writes one INFO `Receipt from <peer>:` line on the sync channel, and nothing else reads it: the tranche-rotation change waits for two receipts to say the same thing. Additive with unknown-key passthrough, so no `PROTOCOL_VERSION` bump and no floor raise, on the #97 and #108 reasoning. Eight things not to undo. **A receipt goes out only for a session that completed AND that we asked for.** `FinishReceiving` takes a second argument and only the branch that runs when the last chunk arrived passes it, because that function is the single teardown for every abort too (the stuck-receive timeout, the sender-offline abort, the NACK budget, the close of a quiet receive we did not ask for (#309), a request that could not be sent, a BUSY ending a receive that has taken chunks (#320), and `OnCombatStart`): a partial session's percentage is a real number over an unrepresentative sample, and the combat abort would put a fresh whisper on the wire in the same frame as the BUSY it sends. Deriving it from `receiveGot >= receiveExpected` was written and rejected, because that reads true for the teardown of a session whose last chunk arrived with no `chunk` field, which never reaches the completion branch. `syncState.receiveRequested` is the second half and is not belt and braces: without it a retransmitted final chunk arriving after the session was torn down bootstraps a one-chunk session of pure duplicates through `HandleSyncData`'s auto-bootstrap, reaches the completion branch again, and whispers a SECOND receipt reading 100% duped for a session already reported. **The message is built where the counters still stand and sent after the teardown**, because `compressMessage` and `SendSyncWhisper` both reach code that can raise, and unwinding from inside `FinishReceiving` would leave `receiving` true with the timer armed, which blocks every future pull until the `MAX_RECEIVE_DURATION` watchdog; `OnCombatStart` already orders its own BUSY that way. **`stored` and `duped` on the wire are NOT the sums of the four halves beside them**, because `CleanupWithEventCounts` runs inside `FinishReceiving` and decrements the total alone, so `stored` is what the receiver kept and not what it took in; that is deliberate, since the receipt's whole purpose is that the two clients' logs describe one session identically. **`received` and the capped session's `remaining` are both absent from the wire.** `received` is derived by the reader on the #215 rule that two stored copies of one number can disagree with nothing to say which is right, and `remaining` is the same rule from the other side: the SENDER authored that count and attached it to the final SYNC_DATA, so echoing it back carries nothing it does not already hold. `rejectFields` is the opposite case and earns its bytes, because the peer holding the records is the only side that can act on which field failed and the only side that cannot see it. **Every remaining field is unconditional**, unlike SYNC_DATA's optional ones: that optionality exists to keep an uncapped session byte-identical to a build that predates the field, and a message type introduced whole has no predecessor to match, so the absolute key set in `spec/wire_contract_spec.lua` is worth more than the bytes. **A session in which every record was refused still sends a receipt** (the gate is `redundancy or rejected > 0`) and the handler renders it with no percentage, because a peer serving records nobody can accept is the peer that most needs telling, and that reading is why #68 gave rejects a counter of their own. **The handler refuses a figure that cannot be a measurement** (negative, NaN, infinite, non-integer; AceSerializer round-trips all of them) and names the drop, because rendered they read as readings, `200% duped` and `nan% duped`, on the one message type whose only job is to measure. A receipt from a peer `capLastTranche` has no record of serving is marked `(unsolicited...)` rather than dropped: dropping it would hide a real receipt if that record ever turns out narrower than the cases producing one, and that cannot be checked before release. **`redundancyText` and `rejectFieldText` are the one writer of each half of the prose**, read by the receiver's lines and the sender's, so the two cannot drift into describing one session two ways. Since #290 a copy of the chunk just taken is not walked, so `duped` counts only what the bucket filter sent twice. A receipt from a build before #290 also counts transport repeats, which matters when comparing the two receipts #96 and #110 wait on.
- **`clearReceiveCounters` is the one writer of every per-session receive counter, and it had to land with #237.** There were thirteen then; #290 added the position and the repeat count. There were four reset sites carrying four different subsets: `RequestSync` set all of them (three fields twice), `FinishReceiving`'s teardown set all of them, `HandleBusy` set four, and `HandleSyncData`'s auto-bootstrap set two. So a session ended by BUSY and then picked up by a bootstrapped one carried the first session's item, money and reject counts into the second session's `Redundancy from <peer>` line. **The two partial sites mask each other**, since `RequestSync` always cleared the lot, so reverting either one alone leaves the system correct and only the pair leaks; the spec pins the pair, and the two single-site mutants survive by construction rather than by a gap. It was tolerable while the figure stayed in one client's log. - **Every processed HELLO writes exactly one INFO round line, and that count is the design (#90).** `HELLO round <peer>: verdict=<v> reply=<r> peer=v<ver> remote=Ntx [local=Ntx hash=local/remote] [buckets=N] [extra]`, emitted at all 9 terminal exits of `HandleHello`. **Verdicts:** `refused-version` (`refusal=` rider), `no-guild-data`, `identical`, `superset-skip`, `superset-nudge`, `busy-cooldown`, `combat-deferred`, `paused-zone`, `paused-combat`, `requested` (`trigger=hash-mismatch` or `trigger=count-no-hash`), `no-sync-needed`, `receiving` (`from=` rider), `autosync-off`. **Reply gate:** `sent`, `send-failed`, `hash-suppressed`, `sync-active`, `suppressed` (repeat refusal), `n/a` (an isReply HELLO never runs the gate). It **replaced** rather than added: the three DEBUG diagnostics the issue named plus the per-round INFO chatter that duplicated them (the arrival line, the hash compare, the per-arm skip and trigger lines), so per-round capture cost fell from three entries to one. That is why folding beat the issue's literal "promote the three lines", which would have made it four against a 1000-entry cap one large send already eats 40% of. **Reasons not to undo any of it.** DEBUG cannot reach a shared capture at all (Logger drops it ahead of the capture tap, AuditCapture rejects it again unconditionally), which is the whole defect. `reply=` reports the **outcome**, not the intent: `SendHelloReply` returns a boolean because it gives up quietly on three paths and a line claiming a whisper that never left is worse than no line. The bucket count rides along only via `GBL:PeekBucketHashes` (`src/Fingerprint.lua`, cached map or nil, never computes, checks guildData identity but deliberately not the count) — the old unconditional `GetBucketHashes` call walked the whole history on every inbound HELLO, worst during a receive where the count moves per stored chunk so the cache missed every time. Do not point it back at `GetBucketHashes`. Every verdict emit is pinned by a spec and each was proven by mutation; the `roundLine()` helper asserts **exactly one** line per round, so a fall-through double-emit or a silent exit reds broadly. Note that `refused-version` and `no-guild-data` rounds carry no `hash=` (`roundStats` is built after the guild-data check), which is deliberate, not a gap.
- **The combat policy has four doors, and serving was the first found with no lock (#126, v0.37.15).** "Combat is no time to sync" is implemented separately at each: `HandleHello` defers *requesting* on live `InCombatLockdown()` plus an `isSyncPaused()` arm for the tail, a *live session* entering combat is aborted outright by `OnCombatStart` with BUSY to both partners, and `HandleSyncRequest` now declines with BUSY on the same two conditions. The fourth door, data nobody asked for, is the next bullet. Before #126 the serve gate checked neither, so a raider was handed a full synchronous serve mid-pull, which is the context of the #115 watchdog kills. **The trap that hid it: `combatPaused` is not the combat check and never was.** `OnCombatStart` returns early unless a session is in flight, so an idle client in a raid never sets the flag; reading it as "are we in combat" says no for exactly the client this bug hit. The flag is a post-abort debounce tail (2s combat, 5s zone) covering the window where the live API already reads false, which is why every door needs both terms and not just one. The request now gets no BUSY and an INFO `Ignoring SYNC_REQUEST from <peer> (zone cooldown), receiving from them: a BUSY would end their send` line, and that peer's own resend (20, 50 and 95s after its request) asks again after our tail. The check sits inside the gate and reads the gate's wire word, so it keys on the loading screen alone and live combat still answers first: no receive is open while a combat term holds (combat start closes any receive, and every way into one checks both combat terms), and the "answers live combat" case in `spec/sync_request_spec.lua` pins that keying. It has no `syncState.receiving` term, because `_ClearReceiveSession` is the one writer that clears `receiving` and it clears `receiveSource` with it, so the compare already implies a receive is open; the first cut carried the term, a mutation dropping it survived, and the code review had it removed. The stored `receiveSource` is still run through `CanonicalPeerKey`, as `HandleBusy` does, because a bare name stored while the roster was cold gains its realm once the roster is warm. **What it costs, accepted at #318's plan (2026-10-01).** That peer usually waits one resend interval past our tail, against the 30s cooldown a BUSY imposed, and its log reads the drop as an unanswered request (`No reply from <us>, resending the request`), which our INFO line is there to join in a whole-guild capture. When the drop eats its last resend, its receive from us ends at 140s with `Retry limit reached waiting on chunk 1`, though its send to us survives and it asks again at the next HELLO. A requester older than v0.37.11 has no resend, so it runs the 140s ladder where a BUSY stopped it in 30s; a BUSY to it would instead have ended its send to us, so neither answer is free for that peer. The drop also fires when our receive from that peer is one it never started, our own request having been lost, where a BUSY would have cost it nothing beyond the cooldown; we cannot tell that case apart, because in the crossing route the peer's chunks may not have reached us before the loading screen began. And when we also hold a paused send to a third peer, the resend after our tail reaches the already-sending decline instead, which still BUSYs our receive source with no loading screen involved. Since #323 an updated receive source reads that BUSY as a refusal and keeps its send to us; one older than #323 still ends it. The drop's own INFO line still reads `a BUSY would end their send`, which is true only of that older peer.
- **The fourth door is `HandleSyncData`'s auto-bootstrap, and it is locked for combat only (#289).** It opened a receive on any chunk that arrived with none open, so a chunk the sender issued before our combat BUSY reached it reopened a receive in combat, held `receiving` through the 140s NACK ladder, and had the post-combat HELLO round answered `verdict=receiving`. - **Serving prepares across frames, and the send slot is claimed synchronously before it starts (#115b, v0.37.17).** `HandleSyncRequest` keeps five things synchronous in this order: version gate, the same-peer ignore (above the gate since #308), combat/pause serve gate (whose zone term drops a request from our live receive source rather than BUSYing it, since #318), the already-sending decline, guildData check. Then it commits `sending`/`sendTarget`, inits the send fields every teardown path reads (`FinishSending` takes `#syncState.sendChunks`, which throws on nil), and starts a token-guarded `C_Timer.After(0)` chain of seven resumable stages. The synchronous commit is load-bearing and about ten specs depend on it: two peers requesting in the same frame must not both be accepted, and every caller asking `GetSyncStatus().sending` straight after the call must get a real answer. **The property that made the change cheap: the first `prepStep` runs synchronously, and a stage that finishes with budget left hands onward inside the same tick.** So a small dataset completes inside the accepting call with the first chunk already sent, which is why only 2 of ~113 existing serve call sites needed a drain and the rest call `HandleSyncRequest` bare and are none the wiser. `spec/sync_helpers.lua`'s `serveRequest` is for tests that seed past one tick's budget; `Helpers.drainZeroDelayTimers` (spec/helpers.lua) fires **only** `delay == 0` timers, because `MockWoW.fireTimers` empties the whole queue and would fire the 120s hard timer and the HELLO heartbeat, aborting the thing under test. **Five things not to undo.** `SYNC_PREP_RECORDS_PER_TICK = 1500` shipped on a measurement, not an estimate (5.25 us/record for the heaviest stage, 7.87 ms/tick); re-measure before moving it. The `SYNC_PREP_TIMEOUT = 30`s watchdog is what stops a chain that dies silently from holding the send slot until reload while BUSYing every request. The **tranche is stamped only once the preparation completes** (it used to be stamped before packing, so a serve that died partway told the next session it had handed those buckets over). Every teardown path must call `_AbortSyncPrep`: the chain is not reachable through the send state those paths clear, so an orphaned chain runs to completion and commits into the torn-down session. And a mid-prep **loading screen aborts rather than pauses**, unlike a live send: there is nothing prepared to come back to, and the requester's resend recovers the sub-second of work. The first reason recorded here was that the resume reached `SendNextChunk` against the empty chunk list the accept installed, which answered the absent chunk with `FinishSending` and wrote a "Send complete 0/0 chunks" block for a session that never sent a byte; since #273 `SendNextChunk` returns while a preparation is live (see the transport bullet), so that route is closed independently of the abort. **`OnCombatStart` checks the prep before `sending`**, because prep implies sending: reversed, the arm is unreachable and every live-send spec still passes. Ten mutations pin this, the reversal included. Mutation tolerance is deliberate at two points: a tail append lands after the walk and rides the next session, and an id normalization from a receive finishing mid-prep degrades to redundancy rather than divergence because the receiver dedups by id. **That tolerance is meant for this one serve's diff, not the shared cache (#330).** `NormalizeRecordId` resets the fingerprint caches at the rewrite, because the count they key on does not move, and `ResetHashCache` bumps a generation that `StartBucketHashScan` records. Stage 1's final `StepBucketHashScan` stamps its map only if no reset has landed since. Before that guard, a receive that rewrote a record the walk had already passed and then finished saw its reset land first, and the stamp then put the old id back for every later reader under the unchanged count. The serve still diffs on the map it walked, and records its hashes in `capLastTranche`, which can send the same tranche to that peer again. #342 holds that, and the second gap: `CleanupWithEventCounts` rewrites the storage arrays in a new order whenever `eventCounts` is non-empty, and resets only when it removed something, so a cleanup that removes nothing still reorders the records under a walk in flight, and the stamp lands a corrupt map. Do not move the reset back to `FinishReceiving`: a receive turned off by the Enable Sync checkbox ends through `_ClearReceiveSession`, and that is exactly the route that never reset. The `Prep complete for <peer>: N examined, M selected, K tick(s), T` line is how a capture verifies any of this on a real client.
- **Peer identity: always use `GBL:CanonicalPeerKey`** (src/Core.lua). The helper does its own local-realm-only strip via `GBL:_isLocalRealm`, NOT `Ambiguate("guild")`. Reason: retail's `Ambiguate("guild")` strips realm for ALL guildmates in a connected-realm group, which collapses two distinct same-name characters across connected realms (e.g. an Alice on Tichondrius and a different Alice on Stormrage in one guild) into one peer key. Custom strip rules: qualified `Name-Realm` keeps the suffix when realm differs from local (raw-or-normalized comparison), strips to bare when realm equals local. Bare input consults `guildData.playerRealms[name]` (built by `BuildRosterCache` on every `GUILD_ROSTER_UPDATE`, persistent across sessions); cross-realm bare names get re-realmed to `Name-Realm`, same-realm bare names stay bare. Both bare and qualified arrivals of the same character converge on the same canonical key in any realm topology, while two distinct same-name peers on different realms keep distinct keys. Bare names without a `playerRealms` entry (cold cache, departed peer, non-guildmate sender) pass through unchanged (best effort; the unresolvable case is two distinct same-name characters whose messages both arrive bare, which collide). **Defensive validation:** the helper rejects realm strings containing hyphens (corruption from a long-fixed code path; retail realm names never contain hyphens) and falls back to bare passthrough; `RepairCorruptedPlayerRealms` (called from `BuildRosterCache`) trims corrupt entries to their first segment so offline-peer corruption doesn't persist forever. `GBL:StripRealm` is reserved for true bare-name use cases where same-name on either realm should share state; the only current consumer is `recentWhisperTargets` for chat-system-message suppression (see comment near its declaration in `src/Sync.lua`). The test mock for `Ambiguate("guild")` is unused by `CanonicalPeerKey` now but still implements local-realm-only strip for any callers that legitimately want it. The `src/Sync.lua` `InitSync` knownPeers seed loop runs each persisted key through `CanonicalPeerKey` and consolidates `knownPeers` in place when a stale key collapses to a new canonical form. **Cold-roster gate:** `MigrateRecoverPeerRealms` returns 0 without bumping `schemaVersion` when `GetNumGuildMembers()` is 0 (cold roster); `GUILD_ROSTER_UPDATE` retriggers `MigrateAllGuilds` once per session via the `_migrationsRetried` flag so cold-roster short-circuits get a warm retry without waiting for the next login. Historical: v0.30.5 first patched the broken `Ambiguate(name, "none")` (identity in retail) with `StripRealm` (over-aggressive), then with `CanonicalPeerKey` wrapping `Ambiguate("guild")` (correct in tests but in-game collapsed all connected-realm guildmates to bare); the v0.30.5 follow-up replaced the `Ambiguate("guild")` delegation with custom local-realm-only logic, added the `playerRealms` fallback for bare arrivals, fixed the schema-11 cold-roster premature-bump, retriggered MigrateAllGuilds on first warm `GUILD_ROSTER_UPDATE`, and added `RepairCorruptedPlayerRealms`.
- **`chunkOutcomes[idx]` outcome vocabulary (v0.28.7):** `"pending"`, `"ok"`, `"aborted"` (ackTimeout), `"combatAbort"`, `"zoneAbort"`, `"busyAbort"`, `"sendFailed"` (target offline), `"disabledAbort"` (#272). **Every abort tag goes through `GBL:_TagInFlightChunk(outcome, idx)` (#281)**, which tags only a `"pending"` chunk. `HandleAck` writes `"ok"` with no guard, and it is final: the guard is what stops a later abort from counting a delivered chunk as lost. Until #281 each of the seven sites (the ACK ladder's give-up and the refused whisper in `SendNextChunk`, the `CHAT_MSG_SYSTEM` offline filter in `InitSync`, `DisableSync`, `HandleBusy`, `OnCombatStart`, `OnLoadingScreenStart`) held its own copy, the give-up's had no pending test, and the offline filter tagged nothing. Four things not to undo. **The give-up's guard is reachable from production**: a NACK moves the send index back and leaves `sendRetryCount` alone, so a NACK naming a chunk the peer already acked (#290's arrival count, after a mid-stream bootstrap) moves the send onto an `"ok"` chunk, and when that peer then went quiet the ladder overwrote it with `"aborted"`. **The give-up tags its own timer's `idx`, not the send index.** The first cut of #281 read the index, and its code review showed that wrong in the ordinary NACK: the receiver NACKs the chunk in flight, `HandleNack` moves the index below it, and that chunk's last attempt, still queued, completes afterwards and sets the timer. When the timer runs out before the NACK's resend goes out, the timer's chunk is the one that used up its attempts, and the index names a chunk acked long before. The same timer's retry branch still acts on the index, which is #296. **A chunk put back on the wire is `"pending"` again**, unless it is `"ok"` (`SendNextChunk`). `OnLoadingScreenStart`'s tag is the one that does not end the session, since a loading screen pauses a live send, and without the reset the guard kept `"zoneAbort"` on a chunk a NACK later resent and the ladder then ran out on, so an ACK timeout was counted as a loading screen. **And `"zoneAbort"` at the send index is what puts the paused chunk back on the wire (#295).** `SendNextChunk` re-issues the chunk at the index rather than advancing when it carries that tag, so the cooldown resume sends the chunk whose ACK timer the loading screen cancelled. Before #295 the resume moved on: the paused chunk never went out again unless the receiver NACKed it, and the next chunk ran on what was left of its retries. Both are visible in the 2026-09-02 record (chunk 6's first timeout reading `attempt 4/11`) and in the live audit store on 2026-09-27. Three things not to undo. **It is decided at issue time, and the resume never moves the index back.** Stepping the index back at the resume was the first proposal. But the resume's send usually defers on ChatThrottleLib straight after a loading screen, and during that deferral a stepped-back index sits one below the chunk owed, where a genuine ACK reads as stale and an armed timer's step-back lands on an acked chunk (#296's shape). The "accepts the paused chunk's ACK while the resume waits on ChatThrottleLib" pin kills that design. The ladder's own step-back could still reach a paused chunk until #284: a callback that completed inside the pause armed a timer, and if that timer fired while the resume waited on ChatThrottleLib, a genuine ACK for the chunk was discarded as stale, exactly as before #295. The callback arms no timer while sync is paused now (see the transport bullet). **A NACK wins over the tag.** `HandleNack` marks the chunk below the one it asks for `nackedPast`, the resend skips a marked chunk, and `SendNextChunk` clears the mark on the chunk it issues, so a mark covers one pass. Without it, a NACK for the chunk after the paused one (the receiver has it, and our loading screen ate its ACK) gets the paused chunk instead. The mark lives in `chunkOutcomes`, so every reset clears it, and it is not an outcome word. A NACK past an unresolved chunk at the index also resets `sendRetryCount`, because the receiver has that chunk, so its retries do not pass to the next. The first cut of #295 missed this path, and its code review caught it (`retrying chunk 3 (attempt 4/11)` on the NACK-past case). The rule covers a NACK past an in-flight chunk with no pause too, which carried the count the same way. A NACK that rewinds to an earlier chunk still leaves the count alone (#296). **What the histogram reads now.** A resumed pause leaves no `"zoneAbort"`, so `+ N zone` counts only chunks a pause left unresolved when the session ended. The resend is a transmission the ladder does not count. The chunk's histogram `attempts` include it, so a chunk delivered on its first send and resent after a pause reads "on 2nd" (or "on 3rd+" after earlier retries), with no `ackTimeout` or `nack` cause for that attempt. The ladder's `attempt N/11` and its give-up count do not include it. The `Resending chunk N to <peer> after the loading screen` line marks a resend this rule made. A paused chunk that a NACK naming it put back on the wire is resent without that line. **The loading screen zeroes the wire anchor, and the resend leaves it alone (#284).** #295 first zeroed it at the resend, because an ACK landing before the resend's own callback answered the transmission from before the loading screen, and timed from that anchor the pause went into the Wire-to-ACK figure (a 30s pause read 40s against a 3s timeout). Zeroing at the loading screen covers that ACK and one landing during the pause as well, and the summary skips the chunk. A chunk whose transmission completes inside the pause stamps the anchor again, and an ACK landing before the resend's callback answers that transmission, so the resend's zero, which the code review of #284 caught, was by then only throwing a valid reading away. **What resending costs, and why it is accepted.** When the receiver had the chunk and our loading screen ate its ACK, the resend is a duplicate, and no sender-side rule can tell that from a lost chunk. The duplicate counts in the receiver's arrival count (#290). A resent final chunk reaches a receiver that has finished: it bootstraps a one-chunk session of duplicates, or, if it is receiving from someone else by then, ignores it and lets our ladder run out. Both are what the ladder already does for a lost ACK, and the alternative is a chunk that may never arrive. A third answer since #289: a receiver in combat or its combat tail refuses it with BUSY, so the session ends `by busy` at its last chunk although the records arrived. One limit is stated and not fixed: after a NACK past the paused chunk, that chunk keeps its tag and counts `+ 1 zone`, though the NACK says the receiver had it. **The other six sites read the send index**, and where it sits below the chunk still owed (a NACK's resend, or a ladder retry that deferred, not yet issued) they tag nothing and the verdict clause says how the session ended. Such a chunk lands in no bucket, which is #298, along with the 120s send-stall teardown, which tags nothing. The "in-flight chunk tag (#281)" describe in `spec/sync_send_spec.lua` holds a structural case that reads `src/Sync.lua` with comments dropped: every literal outcome write, in either quote or the bracket spelling, is pinned to its function (`"ok"` in `HandleAck`, `"pending"` in `SendNextChunk`), only the helper writes a word it was handed, every helper call names its word literally, and each word named is a counter `FinishSending` keeps. **A tag is worth nothing without the path that renders it, which `"busyAbort"` proved by reading zero from v0.28.7 on 2026-04-22 until v0.41.9 (#202).** `HandleBusy`'s send-target branch tagged the chunk and then cleared eight send fields inline and returned, so it never reached `FinishSending`, the only renderer of the histogram, and `chunkOutcomes` was replaced wholesale at the next send. Every `+ N busy +` figure in every capture this repo holds reads `0 busy`, and that is an artefact rather than a reading: the counter existed, the tag was applied, and the number was zero by construction. The branch calls `FinishSending` now. **The tag alone still cannot answer it, which is the correction the code review of PR #271 made to the first cut of this fix, and it is the reason `FinishSending` takes an `abortCause`.** `sendChunkIndex` advances at ISSUE time and `HandleAck` marks the acked chunk `"ok"` without advancing it, so from the ACK until the next issue (at least the 1.0s `INTER_CHUNK_GAP_FLOOR`, against a measured 0.2 to 0.5s wire-to-ACK) the indexed chunk is already settled and nothing is on the wire. Every abort path tags under an `outcome == "pending"` guard, so through the majority of each chunk cycle it tags nothing, and a BUSY landing there would have printed `+ 0 busy +` under a `Send complete` heading, which is the by-construction zero again in a new costume. So the histogram stays a count of CHUNKS and the session's own verdict is a separate clause on the same line, `session complete` or `session ended by <cause> at chunk N/M`, passed in by the caller at all seven `FinishSending` sites (`busy`, `combat`, `ack timeout`, `peer offline` twice, `send stalled`, `sync disabled`). Note what this means for old captures: a `+ 0 combat +` or `+ 0 zone +` on a session that visibly aborted is the same blind spot, not evidence the cause was absent. **The six-field leak the first cut claimed does not exist and the claim was withdrawn**: four of them (`lastSendIssuedAt`, `sendChunkTransmittedAt`, `nacksForCurrentChunk`, `chunkOutcomes`) are reset at the start of every send in the final prep stage, and `chunkOutcomes` again at the accept, while the remaining two are unobservable (`sendChunkSentAt` is written before every chunk and read only after it, and `lastChunkBytes` is read through `math.max(CTL_BANDWIDTH_MIN, ...)` and through a fragment estimate taken after it is rewritten). The inline teardown was a divergent subset with no consequence anyone could see; it is still worth not having, and it is one site of the hand-copied teardown #122 covers. Three things to keep. The abort line is emitted **before** `FinishSending`, as `OnCombatStart` orders its own, so a capture reads the block as the consequence of the abort. `FinishSending` schedules the bidirectional check 0.5s out at a peer that has just declined, and **the branch it reaches is the superset one, not the behind one**, which the first cut had backwards: we were serving that peer because it was behind, so we still hold more 0.5s later and the `IsPeerBusy` arm is never reached. Unguarded that whispers a HELLO reply at a peer which just said it was busy and stamps `lastSupersetNudge`, and `SUPERSET_NUDGE_THROTTLE` (60s) outlives `BUSY_COOLDOWN` (30s), so the peer goes eligible at 30s with the `HandleHello` re-nudge suppressed for another 30 and starves longer than if nothing had been sent. The nudge is gated on `IsPeerBusy` now and says so in the log. `OnCombatStart` was never exposed to this, but only incidentally: it sets `combatPaused` before its own `FinishSending`, so the callback returns at `isSyncPaused()`. `HandleBusy` sets no such flag, which is why the gate has to be at the nudge. And the **mid-prep** branch above stays silent and must never reach `FinishSending`, or a preparation that never put a byte on the wire writes a full `Send complete 0/0 chunks` block plus four statistics lines; `assertChainIsDead` in `spec/sync_request_spec.lua` pins that for every mid-prep teardown at once, and a mutation that lets a mid-prep BUSY fall through to the live-send path is killed by it. **`retryReasons`** is a per-chunk array of `"ackTimeout"` / `"nack"` tags; only these two count toward the wire-loss `chunkFail` metric. Combat/zone/busy/offline aborts are bucketed separately, because mixing them into a single "aborted" count loses the ability to tell a noisy test session from a reliability issue. **`DisableSync` was the last live-send teardown that reported nothing, and #272 (v0.41.12) closed it on the same reasoning.** Turning sync off cleared the send fields by hand and returned, so the whole histogram went unrendered at the next accept, on the session most likely to have one worth reading: someone toggling sync off is usually doing it *because* a sync is behaving badly. A live send goes through `FinishSending("sync disabled")` now, and the inventory is complete, so a live send with no block in the capture is a defect rather than a known gap. Since #279 the block is followed by `Sent BUSY to send target: <peer>`, because the disable now tells both partners as its last statement (see the BUSY bullet). Two things not to undo. **The preparation arm is checked FIRST and the two are an `elseif`**, as in `OnCombatStart`: the slot is claimed before the prep chain starts, so testing `sending` first makes the prep arm unreachable while every live-send case still passes, and the `assertChainIsDead` pin is what kills that mutation. **The chunk is tagged AND the cause is still passed in**, because the tag lands only while a chunk is genuinely pending: the spec that ACKs the indexed chunk and only then disables is the one case here written from the issue rather than from the code. It was the only thing that redded a dropped `pending` guard until #281 moved the guard into `_TagInFlightChunk`, where the helper's own cases and the give-up's red it too. `DisableSync` used to cancel both send timers a second time, unconditionally, to collect a ticker a late AceComm send-completion callback could leave behind with `sending` already false. Since #273 the callback cannot install one outside its own live session (see the transport bullet above), the only writer of `sendTimer` is that callback, and `FinishSending` cancels both timers on the live-send path, so the second cancel had nothing left to collect and was removed.
- **`sortAccess` rides HELLO like `accessControl` (v0.32.10).** The two-tier sort-access policy (`guildData.sortAccess`: write/sort tiers with rank thresholds + delegate lists) is attached to both HELLO builders in `src/Sync.lua`, gated on `(sortAccess.updatedAt or 0) > 0` so unconfigured guilds keep HELLO lean. `HandleHello` accepts a newer remote copy (last-writer-wins on `updatedAt`), normalizes it via `GBL:MigrateSortAccessShape`, and fires `GBL_ACCESS_CONTROL_CHANGED`; `SaveSortAccess` forces a HELLO and signals the same message. This propagation is what makes a GM's grant reach the granted member's client (before it, `sortAccess` was Core-only and never synced). Watch the delegate name-form edge: delegate keys are stored verbatim from the LayoutEditor input but matched against `normalizedPlayerName()` (space-stripped realm), so a multi-word-realm delegate typed with a space will not match.
- **Bank layout syncs via advertise-and-pull, NOT by riding HELLO (v0.32.11).** Unlike `accessControl`/`sortAccess` (small scalars that ride the HELLO body), the bank layout template is several KB, so putting it on every broadcast would regress the one-fragment HELLO the v0.28.x reliability arc fought for. Instead HELLO carries only `layoutUpdatedAt` (one timestamp, gated on `bankLayout.version > 0`). A receiver requests the full template via `LAYOUT_REQUEST` only when it both `HasSortAccess()` AND sees a newer cursor; the holder replies with `LAYOUT_DATA` (full template + `stockReserves`) over a whisper. The layout block in `HandleHello` sits AFTER the `sortAccess` merge, so a grant and its layout pull converge in a single HELLO round. There is NO ACK: every HELLO re-advertises the cursor, so a dropped `LAYOUT_DATA` is re-pulled on the next ping until cursors match (convergence, not per-message proof); `syncState.lastLayoutRequestAt` + `LAYOUT_REQUEST_THROTTLE` keep one request in flight. `GBL:AdoptRemoteBankLayout` validates via `BankLayout.Validate`, applies last-writer-wins on `updatedAt`, and bypasses the `HasLayoutWrite` gate (sync intake, not a local edit), then fires `GBL_LAYOUT_CHANGED` → `OnBankLayoutChanged` refreshes an open Layout/Sort tab. `SaveBankLayout` and a cursor-bumping `SetStockReserve` (only when `version > 0`, preserving the "version > 0 ⇒ valid layout" invariant) force a HELLO so the change advertises promptly. Serving is NOT access-gated (any holder serves, for epidemic spread); only requesting is gated. Watch: `LAYOUT_DATA` is a single whisper; if a real layout compresses above `WHISPER_SAFE_BYTES` it logs a `SyncWarn` (chunking is the unbuilt fix; the `nchunks`/`chunk` envelope fields reserve room for it). The mock serializer is pass-through, so payload size and numeric-key survival are not exercised in tests — verify in-game.

### Chunk sizing — observed reality

- **Every compression figure in this section is compressed size as a percentage of raw**, which is also what `chunkOutcomes.ratio`, the per-chunk send line and the `Compression for <peer>` summary all report. Lower is better. The per-chunk line printed the complement (percent reduction) until v0.37.12, so a capture taken before that reads 31% where this section would say 69%; invert it before comparing.
- **Compression ratio is 23–49%, not 23–26%.** v0.28.6 assumed ~18% and missed; v0.28.7 assumed 26% worst case and also missed. Measured across every capture: 23–26% (v0.28.5/28.6, item-heavy), 27–49% (v0.28.7 Roxeau), 30–42% (2026-08-10 Aeglos). Money-heavy chunks compress worst. **Derive any byte budget from the max, never the median**: `raw_budget <= (N * 255) / max_ratio`. Three consecutive misses came from predicting ratios.
- **Per-fragment drop is ~18%.** Back-solved from v0.28.6's `p_frag_est=44.9%` with 3-fragment chunks: `1-(1-0.18)^3 ≈ 0.45`. Reconfirmed at 18.7% in the 2026-08-10 capture. Per-peer route variance is ~25x, so this is a mid-range figure, not a constant.
- **The 1-fragment target was never met before #92.** v0.28.7 shipped `MAX_RECORDS_PER_CHUNK = 4` with `CHUNK_BYTE_BUDGET = 900` and believed the budget was binding. It never was: 4 records estimate ~790, so the record cap always sealed first, and the budget never fired once in a 2,731-chunk send. Worse, it only ever weighed records. The eventCounts rider (10 entries, ~768 B) and the envelope (~133 B) attach at serialize time, after chunking. Measured on a real chunk: 1,637 raw bytes, of which 736 were counted and 901 were not. Every chunk shipped as 3 fragments for four months.
- **Shipped (#92):** `CHUNK_TARGET_BYTES = 510` governing the **whole serialized message**, with `MAX_RECORDS_PER_CHUNK = 4` kept as a backstop. `PrepareChunks` reserves the envelope estimate up front and fills records and eventCounts entries against what is left, opening carrier chunks for entries that have no record to ride with. Derivation: `255 / 0.50` at the worst measured ratio. **The order within that changed at #114**, which is a correctness fix rather than a sizing one: entries no longer all ride behind the records. See the interleaving invariant under Code invariants to preserve before touching the packer.
- **Density cost, measured:** at ~199 estimated bytes per record and a ~183-byte envelope allowance, the usable budget is ~327 bytes, which fits **one record per chunk** (two would need 398). A backfill therefore produces roughly one chunk per record instead of one per four. Per-record throughput is roughly a wash against the old 4-records-at-3-fragments arrangement; what improves is abort-resistance and the smoothness of partial progress. Do not expect a speedup from this change, and do not "fix" the density by raising the target without a compression measurement at the smaller size (see the open question below).
- **Open question: compression at small sizes.** Every ratio above was measured on ~1,600-byte messages. LibDeflate does worse on smaller inputs, and a 510-byte message may compress nearer 50–60% than 30–42%. That would put an encoded chunk back over 255 B. The runtime guard is the `over-255` counter in the FinishSending summary plus `syncState.lastChunkBytes`; read them on the first capture after this ships. This cannot be tested hermetically because LibDeflate is deliberately not vendored (see the wire-contract notes in `.claude/rules/testing.md`).
- **When a sync still aborts mid-stream:** the old advice ("do not shrink chunks, 1 fragment is the floor, raise `INTER_CHUNK_GAP_FLOOR` instead") assumed chunks were already 1 fragment. That precondition is only true from #92 on. Now that it holds, the gap floor is genuinely the next lever.
- **What NOT to do:** do not raise `CHUNK_TARGET_BYTES` without a fresh compression measurement at the new size, and do not re-derive it from a median ratio.

### Session cap — bounded slices (v0.37.7)

- **`SESSION_RECORD_CAP = 300`** (`src/Sync.lua`, exported as `GBL.SYNC_SESSION_RECORD_CAP`; specs must read the export, never the literal). A send stops at the first whole-bucket boundary at or past the cap. At the measured ~1 record per chunk and the 1.0s gap floor that is roughly 5 to 6 minutes per session, and about 2.5 minutes once the 708-byte budget (#96) lands. The number was chosen for session *length*, not byte count, so it moves when the per-chunk density does.
- **Whole buckets, never a partial one.** A half-sent 6-hour bucket hashes to something neither side holds, so it stays in the diff and comes back entire on the next request. Splitting a bucket to hit the cap exactly would mean a backfill that never converges. A single bucket larger than the whole cap still goes out whole, for the same reason.
- **`remaining` is how the receiver learns a session was capped.** Additive envelope field, final chunk only, omitted when zero, and attached in `SendNextChunk` at serialize time rather than baked into the chunk, so a NACK or ACK-timeout retransmit of the final chunk still carries it. `estimateEnvelopeBytes` reserves for it on **every** chunk: which chunk is final is not knowable while packing. An uncapped session therefore puts no new key on the wire at all, which is what keeps the wire-contract builder key-parity check green.
- **Tranche rotation is not partner selection.** `syncState.capLastTranche[peer]` records, per target, which buckets the last session carried and what their local hash was then. On the next request from that peer, buckets whose local hash has not moved since sort **last**. Without it, a receiver that already holds those buckets from a third peer pins the sender to the same all-duplicate tranche every session while older differing buckets starve. Session-only, self-expiring, and it does not choose who to sync with, so it is not the scored selection retired in v0.37.6. The bucket hashes are computed on **both** request paths for this: a request carrying no `bucketHashes` could otherwise never record a tranche and would loop on its first slice forever.
- **The continuation seam is the existing gossip, deliberately.** `FinishReceiving` reads `remaining` and `madeProgress` before teardown, logs "Partial session from `<peer>`: N bucket(s) remaining", and schedules nothing. The next request comes from the post-receive forced HELLO, the sender's superset nudge (60s throttle, shorter than a slice) and `shouldSync`. This is the ship-and-measure arm of a version-sequenced A/B, not an oversight: a spec pins that no continuation timer is scheduled. A direct 3s same-sender continuation is designed and held on file; build it only if a capture shows a median seam over ~30s or stalled backfills. Known edge: a zero-progress slice emits no forced HELLO and falls back to the 120s heartbeat, which tranche rotation should make rare. Measure it.

### Diagnosis discipline

- Do not lower a pacing constant without an independent reliability measurement — "more aggressive" is not the same as "better."
- Per-chunk audit outcomes (attempt count, wire-to-ACK latency, gap since prior chunk, estimated fragments) are the minimum signal needed to discriminate fragment loss from server throttle from callback-timing bugs. Add these before changing behavior.
- `sendChunkIndex` in the "Send complete X/Y chunks" line is the index of the **last attempted** chunk, not the count acknowledged. When writing future diagnostics or UI strings, prefer an explicit "N ok / M aborted" framing.
- **v0.28.7 FinishSending output is three per-peer lines:** `Sync outcomes for <peer>` (histogram + split abort causes), `Retry causes for <peer>` (ackTimeout / nack / chunkFail / p_frag with observed `n=` frags/chunk), `Compression for <peer>` (min/med/max compression percentage). `p_frag` is back-solved using observed average fragment count rather than `lastChunkBytes`, so A/B data across chunk-size changes is directly comparable. **Do not conflate `chunkFail` (raw retry rate) with `p_frag` (per-fragment loss)** — they are equal only at n=1 fragments.
- **Outcome vocabulary is load-bearing.** Any new abort/failure path should add a named outcome value, not reuse `"aborted"`, because the split between wire-loss and environmental aborts is what makes the histogram interpretable. Since #281 a new value goes in three places: the call to `_TagInFlightChunk`, a counter in `FinishSending`'s `outcomes` table with its words on the `Sync outcomes` line, and the word list in the structural case of the "in-flight chunk tag (#281)" describe, which fails until the call and the counter agree with that list. It cannot see the rendered line, so check that by hand.
- **v0.28.8 FinishReceiving emits a `Redundancy from <peer>` line** with total dupe rate + item-vs-money split (e.g. `78% duped (1023/1314 received) - items: 65% (412/635), money: 90% (611/679)`). Per-chunk audit also has a running `X% dup` annotation. This is the receiver-side complement to v0.28.7's three sender-side per-peer lines. Use it to decide whether bucket-granularity redundancy justifies designing a finer-grained exchange. Decision rule: `<30%` = bucket filter is doing most of the work, skip; `30–70%` = worth doing but not urgent; `>70%` = worth designing. **Note the cost moved:** that design used to be able to assume a periodic MANIFEST broadcast already existed to build on. It does not any more (see the free-agent pairing note above, under Code invariants to preserve), so it now has to price in either reintroducing a broadcast or carrying the finer manifest inside the SYNC_REQUEST/SYNC_DATA session itself. This is a separate concern from partner selection, which is why removing MANIFEST did not retire the rule. Item-vs-money split tells you whether items, money, or both are the redundancy source; money-heavy redundancy may be addressable by smaller money-only buckets instead of full manifest. Suppression: line omitted on empty syncs; segments omitted when the corresponding record type is absent. **Do not conflate redundancy % with sender-side `chunkFail`**: redundancy measures dedup waste at the application layer, not wire-loss retries. **The figure is only trustworthy from v0.37.0 on.** Before it, a record rejected by `reconstructSyncRecord` incremented the dupe counter, so a peer sending nothing but corrupt records read as 100% duped, which this very decision rule puts in its `>70%` band, worth designing a finer-grained exchange for, when the peer had sent nothing the receiver could store. #68 gave rejects their own counter and their own `Rejected N record(s) from <peer>` line. Any redundancy reading from a capture taken before v0.37.0 carries that inflation and should not be compared against a later one. **A second inflation window opens at v0.37.11 and closes when the guild finishes updating.** A v0.37.11 client's request describes only its recent window in detail, and a pre-v0.37.11 server does not read `spans`, so it treats all of old history as missing and offers it. That converges (whole buckets, bounded per session by `SESSION_RECORD_CAP` on any server from v0.37.7 on) but it is nearly all duplicate, so a mixed-version capture reads high for a transitional reason rather than a structural one. Do not compare a reading taken during guild adoption against one from a settled guild, and do not read it as evidence for a finer-grained exchange.
- **v0.37.11 logs the two silent decode failures in `OnSyncMessage`**, at WARN, with sender, channel and the raw byte count. They used to be bare returns, which is what made a damaged arrival indistinguishable from a peer that never spoke. They are the direct measurement the erasure-coding question turns on: AceComm's reassembly has no sequence numbers and no completeness check, so a lost middle fragment is delivered as a truncated payload and lands here, and the surviving byte count says how much of the message made it. Payloads a few hundred bytes short mean independent single-fragment loss; payloads mostly missing, or silence, mean bursts. Those want different fixes, and forward error correction is only worth reconsidering for the first (see the spike on #108, which declined it for now). Read this before proposing any redundancy or coding scheme.
