# GuildBankLedger — Project Instructions

## Overview

WoW addon that persistently logs guild bank transactions. Lua 5.1 + Ace3 stack. Tests via busted.

## Design Principles

**Accessibility first.** Accessibility is a blocking design requirement, not a retrofit. Every new UI feature lists its keyboard-navigation path, focus indicators, color-encoding fallbacks, font-scaling behavior, and screen-reader hooks during the design phase, alongside functional requirements. Implementation pairs with end-to-end verification: tabbing actually advances focus across all visible widgets, triple encoding actually distinguishes transactions without color, font scaling actually clamps without clipping, palettes actually auto-detect from WoW CVars. A claim in user-facing docs (CurseForge description, README, in-game About text, ChangelogView) requires end-to-end verification, not just confirmation that supporting functions exist somewhere in the codebase. See `~/.claude/accessibility.md` for the global standards checklist.

The May 2026 honest-status sweep discovered that `UI/Accessibility.lua` had defined `RegisterFocusable`, `AdvanceFocus`, and `SetFocusIndicator` since v0.3.0 but the functions were almost entirely unused outside `UI/ChangelogView.lua`. No AceGUI Tab key handler hooked into `AdvanceFocus`; no widget called `SetFocus`; no `TabIndex` attributes existed on the frame hierarchy. The README's "Full keyboard navigation (Tab/Shift+Tab)" claim was paper for multiple years. That regression is unacceptable; the audit pass and full widget wiring are a v1.0 release gate, codified in `docs/ROADMAP.md` Pre-1.0 readiness. Push accessibility left in every subsequent design discussion.

## Architecture

- **src/Core.lua** — AceAddon bootstrap, lifecycle, slash commands, bank open/close detection
- **src/Logger.lua**: Per-channel session log. Sync cap 2000, sort cap 3000, system cap 500. Severity levels DEBUG/INFO/WARN/ERROR; printf format with `pcall(string.format)` fallback so a bad format string never crashes. INFO/WARN/ERROR always record; DEBUG drops unless `db.profile.<channel>.debugChat` is on. Public API: `GBL:LogSync/LogSort/LogSystem(level, fmt, ...)` plus convenience wrappers (`SyncInfo`, `SortWarn`, etc.), `GetLog(channel)`, `GetMasterLog(opts)`, `ClearLog(channel)`. Surfaced on demand via `/gbl synclog`, `/gbl sortlog`, `/gbl logs` (master, interleaved by timestamp).
- **src/AuditCapture.lua** — Persistent capture of Logger entries into the `GuildBankLedgerAuditDB` SavedVariable (raw account-wide global, deliberately NOT AceDB; see Conventions). Taps Logger's `emit()` via `GBL:CaptureAuditEntry(channel, entry)`; captures INFO/WARN/ERROR from all three channels (never DEBUG) into lazily-created per-login sessions with version-stamped headers (`addonVersion` incl. dev suffix, `protocolVersion`, player/realm/guild), per-channel caps (sync 1000 / sort 1500 / system 300, oldest-out with `dropped` counters), 10-session rotation. ON by default (`db.profile.sync.auditCapture`; recording locally is not a privacy event, the opt-in boundary is the unbuilt uploader, see docs/PLAN-audit-log-upload.md); `/gbl audit on|off|status|clear` manages it (`off` = kill switch, `clear` wipes the whole account's captures). The capture path self-heals a malformed SavedVariable shape rather than throwing, because an error would unwind Logger's `emit()` and break the caller being observed.
- **src/Scanner.lua** — Guild bank slot scanning (inventory snapshots)
- **src/Categories.lua** — Item classification via WoW classID/subclassID
- **src/Dedup.lua** — Deduplication engine (occurrence-based hashing, fuzzy matching, event count metadata, count-based cleanup)
- **src/Ledger.lua** — Transaction recording from GetGuildBankTransaction API
- **src/Storage.lua** — Tiered storage, compaction (30d daily, 90d weekly), pruning. **None of it has ever run.** `RunCompaction` opens with `if self.scanInProgress then return end` and its only caller fires two `C_Timer.After(0)` levels inside the transaction-scan callback, while the async slot scan is still going, so the guard wins on every bank open. Full raw history is intact and the range filters have been answering correctly all along. Being retired rather than repaired (issue #62): compaction is incompatible with sync, and this file is also the only one in the addon calling `os.date`/`os.time`, which WoW's Lua sandbox does not provide. Do not read the code here as a description of runtime behaviour
- **src/Fingerprint.lua** — Dataset fingerprinting (djb2 hash, XOR aggregation, 6-hour bucket hashes); plus the bounded SYNC_REQUEST manifest (`BuildRequestManifest` splits a bucket table into the newest 50 buckets verbatim and up to 8 coarse spans, `FoldBucketRange` folds a span with order-dependent djb2 rather than XOR)
- **src/ItemCache.lua** — Lazy async item info cache (GetItemInfo + GET_ITEM_INFO_RECEIVED for synced records)
- **src/Sync.lua** — Guild-wide sync via AceComm (HELLO/SYNC_REQUEST/SYNC_DATA/ACK/BUSY/LAYOUT_REQUEST/LAYOUT_DATA protocol, epidemic gossip propagation, concurrent send+receive, free-agent pairing, hash-gated HELLO reply suppression, fingerprint-based delta sync, bounded sessions with whole-bucket slicing and per-target tranche rotation, per-peer BUSY cooldown, NACK backoff, combat/zone guards, bidirectional sync, bank-layout advertise-and-pull)
- **src/BankLayout.lua** — Per-guild saved bank layout templates (display/overflow/ignore tab modes with per-item slot counts and stack sizes); validation (exactly one overflow, no duplicate items across display tabs, ≤98 slots); capture-from-snapshot; stock reserves storage; guild-wide sync via `BuildLayoutPayload`/`AdoptRemoteBankLayout` (advertise-and-pull, last-writer-wins on `bankLayout.updatedAt`)
- **src/SortPlanner.lua** — Pure-function move planner: given a bank snapshot + layout, produces deterministic ordered op list (split/move) to reshape bank. Assign-then-schedule algorithm: Phase 0 pre-merges same-item partial stacks within the overflow tab (two-pointer pour up to the per-item max stack size from ItemCache or an opts.maxStackByItem override) so the overflow is compacted to its minimum slot count BEFORE any cross-tab routing happens. Phase 1 builds demands (slotOrder-pinned + items.slots extensions that right-extend then left-extend to keep each item's group contiguous), assigns each demand to the best source (same-tab direct → overflow → cross-tab; largest-count first within each tier; keep-slot harvest protection), and routes leftover supply to overflow via a capacity-aware pickOverflowSlot that prefers (1) topping up an existing same-item partial slot, then (2) right-extend, (3) left-extend, (4) first-empty; a single supply may split across multiple destinations until consumed or unplaced. Phase 2 schedules moves via a greedy feasibility loop and breaks swap cycles with a pivot slot (same-tab empty preferred, overflow fallback). Phase 3 sweeps stragglers using the same multi-destination overflow routing. Phase 4 packs overflow stacks into a deterministic contiguous run from slot 1 sorted by (itemID ASC, count DESC, origSlot ASC) — position-compaction only; partial-stack merging happens earlier in Phases 0/1B. Hard max-stack invariant: `canExecute` and `applyOpToState` refuse same-item merges that would exceed the per-item maxStack (looked up via the same getMaxStack closure as Phase 0/1B), so the planner cannot emit a plan that depends on illegal in-state over-stack accumulations — Phase 4 cascades that would otherwise over-stack are reordered by the greedy drain or bailed via the existing pivot/cycle paths. Items with unknown max stack (cold cache after `/reload`) skip Phase 0 merging and Phase 1B top-ups for that item only, falling back to grouping; a follow-up sort completes the work once item info loads. Repeat sorts are idempotent. Reports deficits, unplaced items (with reason code), and the overflow tab.
- **src/SortExecutor.lua** — Executes a plan fire-and-forget on a self-rescheduling `C_Timer.After(CADENCE=1.0s, pumpOne)` loop: each tick clears a stuck cursor, issues the planner's next op via `issueOp` (the WoW-API-mandated `SplitGuildBankItem`/`PickupGuildBankItem` src + `PickupGuildBankItem` dst sequence), clears the cursor again if the place left an item on it, advances `state.opIndex`, and schedules the next tick. There is no per-op confirmation, no re-query, no timeout cascade, and no `state.waiting`; correctness comes from convergence, not per-move proof. When the op list is exhausted, `state.pumping=false`, the executor waits `SETTLE_DELAY=3.5s` (above the worst observed 3.3s deposit latency) so the last deposits commit, then runs `endOfPass`: `StartFullScan` → poll `scanInProgress` (`SCAN_WAIT_TIMEOUT=10s`) → `GetLastScanResults` → `PlanSort(snapshot, state.layout)`. If the new plan is empty → finish (clean); if it is non-empty but ≥ the previous pass's op count → finish (converged, residual reported, no infinite loop); if `state.passes ≥ MAX_PASSES=5` → finish with the residual; otherwise `startPass(newPlan)`. `state.layout` is required for auto-rerun and is threaded by SortView via `opts.layout = self:GetBankLayout()`; if nil, the executor finishes after one pass rather than re-planning to nothing. Bank-close abort is driven by Core (not a self-registered event, which would shadow Core's handler under AceEvent's one-callback-per-object rule): `GBL:OnBankClosed` calls `GBL:_SortExecutorOnBankClosed` to abort a running sort; `pumpOne` also re-checks `IsBankOpen()` each tick as a backstop. The executor registers no bank events of its own (the pump issues no event-driven confirmation, so there is no `GUILDBANKBAGSLOTS_CHANGED` handler to misfire on our own moves). A frame-hitch sampler (a single reused OnUpdate frame; `recordHitch` is pure and unit-tested) records inter-frame gaps so a capture shows whether the pump kept the render loop responsive. A stall watchdog (`C_Timer.NewTicker(5s)` running `checkStall`) re-kicks `pumpOne` when `state.pumping` AND `now - state.lastProgressAt > CADENCE + STALL_SLACK=6s` (the lost-frame-timer mechanism behind the historical op-88 hang), bumping `state.pumpToken` so a late original timer no-ops rather than double-issues. `finish` emits a per-run summary (passes, ops issued, residual, avg s/op, cursorStuck, stalls, rescans), a hitch summary line, and a final ping, then calls `ClearCursor` + `stopHitchSampler` + `stopStallWatchdog`, clears `state`, and invokes the onComplete callback with `result = { ok, reason, done, failed, total, replans, passes, ... }` — that result shape is the SortView contract along with the `GBL_SORT_PROGRESS` message phases `start`/`step`(opIndex)/`planupdated`(plan)/`finish`. `src/Ledger.lua` `RescanTransactionLogs` calls `GBL:_sortNoteRescanTick` while a sort runs so the summary counts rescans that competed with the pump. To stop the periodic rescan from starving the pump (its `numTabs+1` synchronous `QueryGuildBankLog` burst hitches the main thread every ~3s and stretched per-op time from 1s to 3-4s in-game), `ExecuteSortPlan` captures `state.rescanWasActive = GBL:IsPeriodicRescanActive()`, stops Ledger's rescan via `GBL:StopPeriodicRescan()`, and `finish` restarts it via `GBL:StartPeriodicRescan()` (self-guards on `bankOpen` per Ledger.lua:472-475, so a bank-close exit safely no-ops). To keep capturing without overflowing the bank's ~25-entry per-tab log, `pumpOne` calls `GBL:RescanTransactionLogs(function() end)` every `TRANSACTION_LOG_FLUSH_OPS=15` issued ops (gated on `state.rescanWasActive` so a user-disabled rescan stays off).
- **src/Restock.lua** — Restock-to-target engine. Pure target math (Option C: per-item target = `max(layoutDemand, reserve)`, `toBuy = max(0, target - stock)`; demand summed over display-tab templates, reserve from `GetStockReserves` (dormant until a producer ships), stock aggregated from the latest scan). `_RestockBuildItemUniverse` builds the displayed rows from the bank layout grouped by display tab (slotOrder-then-itemID order), number-key-coerced so a synced string-keyed layout still matches number-keyed stock; reserve-only items append under a Reserves group. Per-guild-local settings (`restock.items` per-item overrides, `restock.budget`; NOT synced; guild-wide targets ride the synced bankLayout + stockReserves). Auctionator search+buy state machine (`IDLE`/`SEARCHING`/`READY`/`CONFIRMING` on `self._restock`): `StartRestockSearch` resolves item names async then fires `AuctionatorShoppingFrame:DoSearch`, maps results back by itemID on Auctionator's `SearchEnd`; per-item and Buy-all purchases spend real gold via `C_AuctionHouse` commodities driven by `AUCTION_HOUSE_THROTTLED_SYSTEM_READY` / `COMMODITY_PURCHASE_SUCCEEDED` / `COMMODITY_PURCHASE_FAILED`. Gold safety: affordability refusal using a lag-free spend estimate (GetMoney trails the purchase events), optional per-run budget cap, `confirmIssued` guard against double-confirm / duplicate-success mis-credit, Cancel escape from CONFIRMING. Every Auctionator/Item/C_AuctionHouse access is existence-guarded; pure helpers plus the fireEvent-driven state machine carry the unit coverage, live API paths verified in-game. (Catalog-free redesign: the earlier ported GBR catalog `src/RestockCategories.lua` was deleted in favor of the layout-driven list.)

## Critical WoW API Facts

- `GUILDBANKFRAME_OPENED/CLOSED` **removed in 10.0.2** — use `PLAYER_INTERACTION_MANAGER_FRAME_SHOW` with `Enum.PlayerInteractionType.GuildBanker`
- `GetGuildBankTransaction(tab, i)` returns **relative** time offsets — compute absolute via `GetServerTime() - offset`
- Must call `QueryGuildBankLog(tab)` before reading transactions; `QueryGuildBankTab(tab)` before reading slots
- Use `GetServerTime()` — never `time()` or `os.time()`
- Use numeric `classID`/`subclassID` via `C_Item.GetItemInfoInstant()` — never localized strings
- `MAX_GUILDBANK_SLOTS_PER_TAB = 98`
- `MAX_GUILDBANK_TABS = 8` (constant — max purchasable tabs)
- Money log tab index: `MAX_GUILDBANK_TABS + 1` (always 9, NOT `GetNumGuildBankTabs() + 1`)
- `GetGuildBankMoneyTransaction` returns type `"withdrawal"` (not `"withdraw"`) — normalize at record creation

### Wire-contract fixtures

`spec/wire_contract_spec.lua` is the one spec that does not use the serializer mock. `spec/wire_helpers.lua` loads a real AceSerializer via `dofile` (`require` cannot be used: the module names contain a dot, which `require` turns into a path separator), stashing and restoring `_G.LibStub` and `strmatch` around the load. Real LibStub reads the existing global and evaluates `LibStub.minor < 2`, which the suite's mock does not have, so skipping the stash either throws or leaves the mock registry replaced for whatever runs next in the same file. The addon's own mixed-in `Serialize`/`Deserialize` are never touched.

**The libraries come from `spec/vendor/`, not `Libs/`.** `Libs/` is gitignored and fetched by the packager from `.pkgmeta` externals, so it exists only on a machine that has run the packager: CI checks out a tree with none. Committing LibStub (51 lines, public domain) and AceSerializer (287 lines) under `spec/vendor/` is what makes the suite hermetic. `spec/vendor/README.md` carries the provenance. The generator additionally diffs those copies against `Libs/` when `Libs/` is present, so a developer still finds out when upstream moves while the test run stays deterministic everywhere.

**No compression in the harness.** LibDeflate is a pure byte-exact codec this addon neither configures nor extends, so pinning it would test LibDeflate rather than GBL, at the cost of vendoring 3,600 more lines. `estimateRecordBytes` is documented against AceSerializer output, and the compressed size that matters at runtime is measured live as `syncState.lastChunkBytes`.

**The golden strings in `spec/fixtures/wire/*.lua` are frozen and are not regenerated.** They are what a v0.36.x peer puts on the wire, and "an older peer's bytes still decode" is the contract the `MIN_SYNC_VERSION` floor (#74) rests on. A record-shape change (#67) adds cases beside them; it never rewrites them. `spec/fixtures/generate_wire_fixtures.lua` is an authoring aid for new cases plus a check that every committed string still decodes to its hand-written table; it is not a refresh tool.

Expectations are hand-written from `docs/DATA-MODEL.md`, never pasted from program output, because a characterization fixture built from what the code prints can only ever agree with the code. The `serialized` field records AceSerializer output rather than the compressed and encoded channel bytes, so a reviewer can read the diff. Field order inside those strings comes from `pairs()` and is not meaningful: the tests only ever decode them.

`src/Sync.lua` exposes `_StripForSync`, `_ReconstructSyncRecord` and `_EstimateRecordBytes` for this spec alone. They have no production callers and exist because the codec is otherwise file-local and unreachable.

Two format facts worth not rediscovering: AceSerializer escapes space (and control codes, `^`, `~`) to two bytes, and an **unescaped** space is silently dropped on decode, so a hand-typed payload containing `"Test Guild"` comes back `"TestGuild"`. Pipes and colons, which record ids are built from, pass through unescaped, which is why `estimateRecordBytes` holds as an upper bound for records.

## Conventions

- Addon object: `GBL` (local alias for the AceAddon instance)
- **In-game strings are ASCII.** Anything the addon can put on screen stays inside byte 127: chat output, labels, tooltips, audit lines, and `CHANGELOG_DATA`. WoW's default fonts carry Latin-1 and little past it, so an em dash, an arrow or a check mark draws as a blank or a box depending on the font and the client's locale. Symbols used as UI encoding fail worst, because a check mark that does not draw leaves a row whose state is carried by colour alone, which is the triple-encoding failure the accessibility rule exists to prevent. Code comments are exempt: they never reach a player. `spec/ascii_strings_spec.lua` enforces this over the file list in the `.toc`, stripping comments first and decoding decimal escapes, since `"\226\156\147"` is ASCII on disk and a check mark on screen.
- Module registration: use AceAddon modules, not standalone globals
- Events: always check interaction type before acting on `PLAYER_INTERACTION_MANAGER_FRAME_SHOW`
- Timestamps: always `GetServerTime()`, never `time()`
- Item IDs: use `C_Item.GetItemInfoInstant()` for classID/subclassID
- Guard `Enum.PlayerInteractionType.GuildBanker` existence for Classic compat
- Saved variables: `GuildBankLedgerDB` (AceDB), data keyed per guild name. Deliberate exception: `GuildBankLedgerAuditDB` (src/AuditCapture.lua) is a raw account-wide global, NOT AceDB and NOT guild-keyed — it is an append-only diagnostic capture store whose collection unit is the account's SavedVariables file; sessions carry player/realm/guild in their headers. Do not migrate it into AceDB (a second `AceDB:New` also breaks the `MockAce.dbInstance` single-instance assumption in specs).
- **`docs/DATA-MODEL.md` is the record of what is actually stored, and of what is being done about the places the code disagrees with itself.** Read it before answering any question about what is stored, and before changing records, dedup, or the sync payload. The defaults block, the record builders and the live SavedVariables all disagree; every disagreement in the doc now carries a verdict, and the issues are collected under the **Data model integrity** milestone. Two things to take from it before touching anything here. `schemaVersion` defaults to 8 while migrations run to 11, and that is correct: AceDB strips a value equal to its default and hands back the current default on load, so the default IS the stored version of every guild sitting at it, and raising it strands them past migrations 9 to 11 permanently. And **unknown keys on a synced record must pass through untouched**: that tolerance is what makes adding a record field free, and a whitelist at intake would turn every future field into a forced guild-wide update. The doc also carries the measured sync-corruption rate (11.66% of everything ever received) and the `syncState.peers` name collision, whose persisted half turns out to have no reader at all.
- **Sync is guild-wide** — all members participate in HELLO/sync, not just officers. Officer rank only gates UI visibility (settings, admin features). Never add rank checks to the sync protocol.
- **Public description sync**: `docs/CURSEFORGE-DESCRIPTION.md` is the source of truth for the CurseForge project page. When user-facing surface changes (slash commands, UI tabs, access control, sync features, planned-feature framing), update it in the same PR. CI emits a `::warning::` annotation on PRs that change feature-surface files (`README.md`, `docs/ROADMAP.md`, `src/**/*.lua`, `UI/**/*.lua`, `GuildBankLedger.toc`) without updating the description; treat it as a checklist prompt, not a blocking gate. Pasting the updated content into the CurseForge web UI is a manual release step until BigWigsMods/packager#187 lands.

## Branch Workflow

`main` is the integration target and is GitHub-protected (PR + `test-and-lint` CI required, merge commits only, force-push and deletion blocked). Auto branch deletion on merge is **on**: `main` is the only permanent branch in this repo, and every other branch is deleted when its PR merges.

### Branches

Every branch is single-purpose: cut from the latest `main`, scoped to one PR, deleted when that PR merges. Follow-up work gets a fresh branch. Branch names are never reused.

- `feat/<thing>` for new features
- `fix/<thing>` for bug fixes that are not urgent
- `chore/<thing>` for maintainer chores, repo-config changes, doc-only updates
- `infra/<thing>` for CI / build / tooling changes
- `hotfix/<thing>` for urgent production-impact fixes (see Hotfix rule below)

`feature/` is retired in favour of `feat/`.

**No long-lived branches.** From 2026-04-27 to 2026-08-07 this repo ran long-lived per-area topic branches: `ui`, `sync`, `layout-sort`, `restock`, plus an `accessibility` lane that was declared but never created. They worked. They are retired because the global rule now allows a long-lived branch only for release maintenance in a project shipping several versions in parallel, and GBL ships one version at a time to CurseForge. All of them were merged and deleted on 2026-08-07. Do not recreate them, and do not read their absence as an accident.

See **Branch lifecycle: trunk-based, delete after merge** in `~/.claude/CLAUDE.md` for the full rule and the agent-side decision rule.

### Rules

- **Scope check before the first commit of every session**: the checked-out branch is not authorization to commit to it. If the intended work does not match the branch's type and slug, cut a fresh branch from the latest `main`.
- **Hotfix rule**: an urgent production-impact fix gets its own `hotfix/<thing>` branch off `main` and ships on its own. Never hold one back to bundle it with unrelated work.
- **Cross-branch rule**: when one feature spans two branches (e.g. a sync change that needs a UI tab), merge the upstream-of-the-dependency branch first, rebase the dependent branch onto the new `main`, then commit the dependent piece. Never PR both simultaneously hoping git resolves the order.
- **Rebase cadence**: cut from the latest `main`, and rebase an open branch onto `origin/main` after any intervening merge. `git rebase origin/main` if conflicts are tame; fall back to `git merge origin/main` if not. `git push --force-with-lease` is fine on your own unmerged branch.
- **Version-stamp cadence (covers CHANGELOG and every other version artifact)**: a branch stamps every version artifact only when opening the PR, in a dedicated stamp commit. Work on the branch leaves all of these untouched and lets `[Unreleased]` accumulate:
    - `VERSION` file
    - `GuildBankLedger.toc` `## Version:` field
    - `src/Core.lua` `local VERSION = "..."` constant
    - `CHANGELOG.md` (the `## [X.Y.Z] - YYYY-MM-DD` header; work lands under `[Unreleased]` until stamp time)
    - `UI/ChangelogView.lua` `CHANGELOG_DATA` table (in-game changelog)
    - This `CLAUDE.md`'s "Current: X.Y.Z" line at the bottom
    - `src/Core.lua` `local DEV_BUILD = ...` constant must be reset to `nil` in the stamp commit. CI rejects any other value via the `Verify DEV_BUILD is nil` workflow step.

  **Do NOT sweep the version string through `spec/fixtures/wire/`.** Those files pin several releases at once on purpose: a v0.36.0 HELLO pair, a v0.37.0 floor-aware HELLO and SYNC_REQUEST, a pre-#67 deposit and a post-#67 one. Each is a frozen recording of what that version put on the wire, and the point is that it keeps saying so forever. A grep-and-replace stamp will try to bump all of them and quietly destroy the cross-version contract they exist to hold. The trap is that it destroys them *silently*: a sweep changes the frozen `serialized` string and its expectation table together, so the suite stays green while the fixture stops recording anything. If a fixture ever needs to change, `lua spec/fixtures/generate_wire_fixtures.lua` reports which committed string no longer decodes to its hand-written table; that is a finding, never a refresh.

  `spec/ui/changelog_spec.lua` asserts that `CHANGELOG_DATA[1]`'s version matches the addon version, so a half-landed stamp fails the suite instead of shipping. If two branches PR with the same target version, the second to merge rebases onto post-merge `main` and its stamp commit bumps to the next patch. The principle is: one version per PR, one stamp commit per PR, never per-commit churn on these artifacts. (This matches the global `~/.claude/CLAUDE.md` "Commit Versioning" standard, which stamps once at PR-open.)
- **Doc-only PRs take no version and no tag.** The objective test is whether the PR changes any file that ends up in the packaged zip. `.pkgmeta`'s `ignore:` list strips `spec`, `docs`, `.busted`, `.luacheckrc`, `.gitignore`, `.claude`, `CLAUDE.md`, `*.md`, `*.sh`, `*.bat`, and `VERSION`. If every file a PR touches is stripped, the packaged addon is byte-identical apart from the stamp itself, and there is nothing to release. Stamping one anyway ships a version whose only user-visible content is the announcement of its own existence. Before v0.37.0 it also cost a forced guild-wide sync break (see Release cost below); now the cost is a contentless update pushed to every auto-updating install, which is still not worth paying. This narrows the global "every merged PR gets a bump and a tag" rule rather than overturning it: that rule's origin (PR #7) was addon-relevant work shipping untagged, which this test still catches. A PR that touches even one packaged file is a normal release.

  **`CHANGELOG.md` is the trap: it ships despite matching `*.md`.** The packager detects a changelog file and copies it back into the package regardless of the ignore list, and also feeds it to CurseForge as the release notes. Verified against the published v0.36.0 zip, whose only top-level files are `CHANGELOG.md`, `GuildBankLedger.toc`, and `LICENSE`; `README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `spec/`, and `docs/` are all absent. So a CHANGELOG-only PR is **not** doc-only. Do not read the ignore list on its own. When a PR sits near the line, settle it empirically: `gh release download <tag> --pattern "*.zip"` and list the archive.
- **Dev-build isolation**: at the start of any branch session that ships protocol-affecting or schema-affecting changes, set `local DEV_BUILD = "<branch>"` in `src/Core.lua`. The runtime `self.version` becomes `X.Y.Z-dev.<branch>` and `GBL:IsVersionCompatible` refuses to sync with production peers in both directions, including the user's own production-version characters on the same account. Since v0.37.0 that refusal comes from the `isPlainSemver` short-circuit rather than the old exact-match gate, which is why that check has to stay ahead of every `CompareSemver` call (see Release cost above). The flag is reset to `nil` in the stamp commit (see Version-stamp cadence above). Local `bash run_tests.sh` is intentionally not gated on the flag so dev iteration keeps working; CI is the enforcement boundary, and `scripts/hooks/pre-push` is the local-clone fast-fail (activate once per clone with `git config core.hooksPath scripts/hooks`).
- **CI cadence**: `.github/workflows/ci.yml` runs on `pull_request` and `push: main` only. Intermediate commits on a branch are unverified by CI. Run `bash run_tests.sh` and `bash run_tests.sh --lint` locally before each commit so the branch stays green.
- **Carve-out from the global "small, focused PRs" rule**: the user's global `~/.claude/CLAUDE.md` "Open Source / Public Repo Workflow" section says "Keep PRs small and focused, one concern per PR." That rule is for external-contributor PRs. For the maintainer's own PRs in this repo, multiple related commits covering one concern is the intended pattern. External contributor PRs still follow the small-and-focused rule.

### Release cost: paid in full at v0.37.0, and only payable again on a floor raise

**Historical, through v0.36.1.** `HandleHello` refused to sync on **any** version difference, patch included, so every release was a forced lockstep guild update and until every member updated the guild was split into non-communicating islands. That cost was per account rather than per character (SavedVariables are account-wide, so a player's alts share one install and one version), but it was real and it was paid by other people. It is why doc-only PRs take no version, why bundling beat a fast sequence of small releases, and why the 103 tags cut between 2026-04-07 and 2026-06-24 were an accumulating bill.

**From v0.37.0 on, `MIN_SYNC_VERSION` replaces it with a range** (`src/Sync.lua`, `GBL:IsVersionCompatible`). Two peers sync when each is at or above the other's advertised floor. An ordinary release now costs nothing: ship a patch and a guild running three different versions keeps converging.

Three things to keep straight before touching it.

- **Raise the floor ONLY for a wire, record-identity or fingerprint break.** Never for a normal release, however large the diff. Raising it re-imposes exactly the lockstep split the floor exists to remove, so the value in the source is a decision about compatibility, not a version number that tracks releases. It moved to `0.37.0` in that release's stamp commit and should sit there until something genuinely breaks compatibility. **Worked example of a wire change that did not qualify: the v0.37.11 request manifest (#108).** It changed what SYNC_REQUEST puts on the wire, and a raise had been cleared for it, and it still did not take one, because the change turned out to be additive in both directions: unknown keys pass through untouched, and the serving side's "a bucket you did not mention reads as hash 0, so send it" rule means an under-described request degrades to redundancy rather than to divergence. The test to apply is not "did the wire format change" but "can either side misread the other into losing records". Where the answer is no, the cost of a raise (a split guild for the length of the adoption window, which for a starvation fix delays the very outcome being shipped) buys nothing.
- **v0.37.0 is the last prepaid compatibility break.** Before it, an id-format change was automatically safe: peers on different versions refused each other, so records built under two `buildPrefix` implementations never met. After it they do meet, and if their implementations disagree both sides accept the other's records as new and the guild's dataset silently duplicates. So an id-affecting change now costs a floor raise, which is why #67 (the tab in the prefix) had to ride v0.37.0 rather than follow it.
- **A peer advertising no `minSyncVersion` falls back to exact match.** That is the correct reading of a pre-v0.37.0 build and it is what keeps the old refusal behaviour testable. A peer sending no `version` at all is incompatible everywhere, which is what lets `HandleSyncRequest` recognise a pre-floor request.

The gate lives at three sites, not one: `HandleHello`, `HandleSyncRequest` (a request never passes through HELLO), and `RequestSync` (the bidirectional check after `FinishSending` reaches it without one, and so does a manual pull). All three call `IsVersionCompatible`. The settings merges in `HandleHello` deliberately sit **above** the gate so a GM's access-control, sort-access or layout change still propagates through a mixed-version window; only record exchange is gated. An incompatible peer gets one HELLO reply per session via `syncState.incompatibleReplied`, not one per heartbeat.

`IsVersionCompatible` short-circuits on `isPlainSemver` **before** any `CompareSemver` call. `CompareSemver` strips `-dev.<id>` by design, so a range test that reached it would read a dev build and its base release as compatible and undo `DEV_BUILD` isolation entirely. Do not reorder those checks.

### What reaches the public CurseForge channel

`.github/workflows/release.yml` fires only on `push:` of a `v*` tag. `BigWigsMods/packager` derives the release type from the tag name: a tag containing `alpha` or `beta` (case-insensitive) uploads as that channel, anything else uploads as a full release, and an untagged run packages as alpha. Three levers follow, in increasing order of machinery:

1. **Do not tag.** No tag, no workflow run, no CurseForge upload, no GitHub release.
2. **Tag with `-alpha` or `-beta` in the name.** Still matches the `v*` trigger and still uploads, but CurseForge files it off the default channel so users are not offered it.
3. **`-d` on the packager.** Skips uploading entirely. More machinery than either of the above and not currently needed.

Recorded as available options, not current practice. The caveat that matters: channel choice cannot change what the maintainer actually runs, because this repo is symlinked into AddOns, so the maintainer's client advertises whatever `main` holds regardless of what CurseForge is serving. Since v0.37.0, sync fragmentation is governed by the floor alone, not by version count; ordinary releases cost update churn, and only a floor raise re-imposes a guild split. Channel choice controls how much of that churn the guild sees.

## Issue and PR labels

20 labels in two namespaces: 6 `type:`, 8 `area:`, and GitHub's 6 remaining defaults. Adopted 2026-08-14 (#73), backfilled in one pass across all 42 issues and all 68 PRs, closed and merged included. Each label's GitHub description carries its own rule, so the meaning cannot drift into someone's head. The contributor-facing version lives in [CONTRIBUTING.md](CONTRIBUTING.md); this section is the maintainer's copy and carries the reasons.

WoW-Economy-Forecaster renamed to match its prefixes; this repo is public and takes outside PRs, so the words a stranger already recognizes are worth more than a literal 1:1 with the branch name. The mapping above is still 1:1 in the direction that matters: every prefix implies exactly one label.

## Sync subsystem notes

### Protocol / transport

- Sync transport stack is **AceSerializer → LibDeflate → AceComm → ChatThrottleLib → `C_ChatInfo.SendAddonMessage`**. AceComm splits payloads into 255 B wire fragments; a 980 B compressed chunk is ~4 fragments. Whole-chunk loss compounds: at per-fragment drop probability `p`, chunk loss is `1 - (1-p)^n`. Moving from 3 to 4 fragments at p=5% raises chunk loss from 14% to 19%.
- AceComm WHISPER has an empirically ~2000 B reliability ceiling (`WHISPER_SAFE_BYTES` in `src/Sync.lua`). Staying under it is necessary but not sufficient — fragment *count* is an independent reliability factor.
- `ChatThrottleLib.avail` is the **client-side** bandwidth meter only. It does not model server-side per-recipient addon-message throttling that Blizzard's chat server applies to `SendAddonMessage` independent of CTL. A healthy `CTL.avail` can still coincide with server-dropped messages when chunks are issued <1s apart.
- `C_ChatInfo.SendAddonMessage` via `AceComm:SendCommMessage` does not return a useful delivery status — reliability is observed only via ACK/NACK/timeout at the protocol layer. Do not branch on its return value.
- AceComm's progress callback fires per CTL piece; only `sent == totalBytes` indicates "handed to the wire," and only then should the ACK timer start. This is the v0.23.0 contract codified in `SendNextChunk`.

### Name forms quick reference

GBL handles three distinct name forms. Mixing them is a collision risk; each has a dedicated producer and a fixed set of consumers:

| Form | Example | Where it lives | Producer |
|---|---|---|---|
| Qualified `Name-Realm` | `Katorriwl-Stormrage` | `record.player`, `record.scannedBy` (after the `sync:` prefix), all migrations | `GBL:ResolvePlayerName` |
| Canonical peer key | bare for same-realm, qualified for cross-realm | keys of `syncState.peers`, `guildData.knownPeers`, `syncState.peerBusyUntil` | `GBL:CanonicalPeerKey` |
| Bare name | `Bob` | `recentWhisperTargets` keys (chat-system suppression), UI filter inputs | `GBL:StripRealm` |
| Raw network sender | whatever AceComm passes | runtime only; must never be stored without canonicalization | always wrap in `GBL:CanonicalPeerKey` before keying any peer-state table |

Helpers:

- `GBL:NormalizeRealm(realm)`: strips whitespace from a realm portion (e.g. `"Aerie Peak"` → `"AeriePeak"`). Always normalize before equality comparison or persistence.
- `GBL:GetLocalRealm()`: normalized local realm, or `"UnknownRealm"` sentinel when realm APIs are cold.
- `GBL:_isLocalRealm(realm)`: `true` iff realm matches local (raw or normalized). Used by `CanonicalPeerKey` to decide whether to strip.
- `GBL:BuildRosterCache()`: populates `guildData.playerRealms[bareName] → realm`. Two-pass: detects bare-name ambiguity and writes the `false` sentinel when a bare name maps to multiple distinct realms in the roster (so `CanonicalPeerKey` can refuse to guess and keep ambiguous bare arrivals bare).
- `GBL:RepairCorruptedPlayerRealms(t)`: trims hyphen-corrupted realm strings carried forward from a long-fixed code path; called from `BuildRosterCache` on each invocation. Leaves `false` sentinels untouched.

`ResolvePlayerName` priority order: **explicit `playerRealms` arg → current guild's playerRealms → local realm fallback**. There is no cross-guild fallback. Bare names from the bank log are assumed to belong to the current guild, not a guild the user previously belonged to. Migrations pass the per-guild table explicitly via the `playerRealms` arg.

### Code invariants to preserve

- Logging is split across three channels owned by `src/Logger.lua`. Sync code calls `GBL:SyncInfo / SyncWarn / SyncError / SyncDebug`; sort code calls `GBL:Sort*`; system events call `GBL:System*`. The lower-level form `GBL:LogSync(level, fmt, ...)` exists for runtime-computed levels. Each channel is a session-only ring buffer (sync 2000 / sort 3000 / system 500, FIFO from tail; sort is largest so a full sort run stays in the on-demand view). DEBUG entries are dropped entirely unless `db.profile.<channel>.debugChat` is on, which preserves the prior `chatOnly=true` "do not pollute the buffer with per-chunk noise" property without a separate side channel. Chat mirroring is gated by `chatLog` (INFO/WARN/ERROR) and `debugChat` (DEBUG). `GBL:AddAuditEntry(msg, chatOnly?)` is a deprecated shim that routes plain calls to `SyncInfo` and `chatOnly=true` calls to `SyncDebug`. `GBL:GetAuditTrail()` is a permanent alias for `GetLog("sync")` that also exposes a legacy `entry.timestamp` field; new readers should use `GetLog(channel)` or `GetMasterLog(opts)` directly. Slash commands: `/gbl synclog`, `/gbl sortlog`, `/gbl logs` (master pop-up), `/gbl logs dump [N]`, `/gbl logs clear sync|sort|system|all`, `/gbl logs debug sync|sort|system on|off`. The Sync tab no longer carries an always-visible audit panel; logs surface only on demand via slash command.
- `syncState.lastChunkBytes` is the canonical compressed chunk size. Reuse it for fragment-count estimates (`ceil(lastChunkBytes/255)`) rather than re-measuring.
- `HasSyncBandwidth()` uses a **dynamic** threshold `max(CTL_BANDWIDTH_MIN, lastChunkBytes)` — this is the v0.28.2 fix for the burst-stall regression from v0.28.0. Do not regress to a fixed threshold.
- The superset skip in `HandleHello` and again in the bidirectional check after `FinishSending` is load-bearing for convergence. The `HandleHello` superset case now re-nudges a behind peer past the hash-gated HELLO-reply suppression: when we are ahead, our data is stable, and the reply gate set `replyDecision == "suppressed-hash-unchanged"`, the superset branch re-sends a HELLO reply (an isReply HELLO drives the receiver's `shouldSync`/RequestSync path, so it is a real pull trigger) throttled per peer via `syncState.lastSupersetNudge[key]` + `SUPERSET_NUDGE_THROTTLE` (60s). This is the "tried and failed, back off" the v0.28.x note asked for, confirmed in-game (2026-06-09 capture: an ahead client at tx 10955 went idle and silently starved behind peers Fluphie/Fxh of the nudge, so they never requested). Wire-compatible (reuses the existing HELLO reply, no new message, no `DEV_BUILD`). The bidirectional-check site after `FinishSending` applies the same re-nudge: when we hold more it re-sends the HELLO reply through the shared `syncState.lastSupersetNudge[cleanTarget]` + `SUPERSET_NUDGE_THROTTLE` throttle, so a behind peer is driven to pull rather than skipped silently. The shared throttle means the `HandleHello` and bidirectional sites cannot double-nudge one peer inside the same 60s window. This closes the symmetric pure-skip gap the v0.28.x amplifier note flagged (previously the site short-circuited on "likely superset" with no back-off, so when sends failed both sides could mutually skip).
- Stale-ACK discard in `HandleAck` (v0.23.0) and `ScheduleReceiveTimeout` rescheduling (v0.25.3) are real defect fixes, not patches — do not remove during refactors.
- **The SYNC_REQUEST manifest is bounded, and the span fold must never become an XOR (#108, v0.37.11).** The request used to carry one entry per 6-hour bucket over the guild's whole history: ~2,500 B and 10 fragments at 273 buckets, over `WHISPER_SAFE_BYTES`, with no ACK and no retry, so on an ~18%-per-fragment route it arrived about one time in seven. That is what starved peers while the log on the serving side showed nothing at all. `BuildRequestManifest` now sends the newest `SYNC_REQUEST_DETAIL_BUCKETS` (50) buckets in `bucketHashes` plus up to `SYNC_REQUEST_SPAN_COUNT` (8) `spans` of `{ s, e, h }` covering everything older: 58 entries at any depth. **Measured size: 1,447 B serialized, 704 B deflated, 709 B encoded, so 3 AceComm fragments, and that figure does not move with history depth** (the bucket count is irrelevant once the manifest is bounded; ~580 of the raw bytes are near-random hash digits, which deflate cannot do much with). If the request ever has to fit in 2 fragments, the lever is `SYNC_REQUEST_DETAIL_BUCKETS`, not compression. Both constants are exported from `src/Fingerprint.lua` and specs read the exports. The requester logs its own request size (`Requesting sync from ... N bytes`), so a capture taken on the requesting side gives the figure directly rather than by reconstruction. Three things not to undo. **The fold is order-dependent djb2, not XOR**: bucket hashes are already XOR aggregates, so XORing them flattens to one XOR over every record in the range and two peers each missing records the other holds can fold identically over different data, which both sides then recompute the same way forever. It is the prefix-hash cancellation objection one level up. **Spans tile the older range** rather than hugging the keys the requester holds, so a serving peer's unknown bucket lands inside a declared span instead of an uncovered hole. **A key no span covers keeps the original comparison** (`localHash ~= (detail[key] or 0)`), which is what makes an old peer's full-table request take a byte-identical path and is why no floor raise was needed; the untouched bucket-diff and session-cap suites are that proof.
- **A receive timeout at zero chunks resends the request; after that it NACKs (#108).** Nothing arriving means the request went missing, and a NACK for chunk 1 asks for a retransmit of a send that never began, which `HandleNack` discards on arrival because it is not sending. That discarded signal already crossed the wire three times per failed request. The branch reuses `SendSyncRequestTo`, the stashed `syncState.receiveSinceTimestamp`, the existing `MAX_NACK_RETRIES` budget and the existing backoff ladder, and adds **no new timer**: it runs inside the timeout callback already scheduled. Keep the callback's check order (duration net, offline, budget, then the branch); the offline-detection specs pin it. Resending is only reasonable because the manifest made the request small and fixed-size, so do not keep the retry if the request ever grows again. **It is 3 fragments, not the 1-2 this bullet claimed before it was measured** (see the manifest bullet above), and the 2026-08-18 capture shows what that costs: four `Could not decompress` warnings, every one at exactly 459 B, which is 254+205 and therefore a 3-fragment message that lost its middle piece. Middle loss is the only single-fragment loss that is visible at all, since losing the first or the last delivers nothing, so each logged warning stands in for roughly two silent ones. That is the case *for* the retry rather than against it: the request loss it recovers is real and measured, and it starved a peer for 13 minutes in that same capture. Its necessary partner: `HandleSyncRequest` **ignores a repeat request from the peer it is already sending to** rather than answering BUSY, because `HandleBusy` would tear down the receive that send is feeding. BUSY still goes to third parties.
- **`ACK_TIMEOUT` and `MAX_RETRIES` move together (#92).** What matters is the product: total patience per chunk before the send gives up. They are 3s x 11 attempts ≈ 33s, down from 8s x 6 ≈ 40s. Changing one alone breaks the property they were tuned for: 3s at the old 6 attempts is ~18s, short enough to abort sends that today survive a receiver's 20-30s loading screen. Both are exported (`GBL.SYNC_ACK_TIMEOUT`, `GBL.SYNC_MAX_RETRIES`) and specs must read them rather than matching a literal delay — a spec that hardcoded `timer.delay == 8` matched nothing after the change and passed vacuously instead of failing, which is why `fireAckTimeout` errors when it finds no timer.
- **Free-agent pairing: a peer that finishes a session becomes free and takes whatever the next HELLO offers.** There is no stored picture of other members' bucket hashes and no scored queue choosing a "best" next partner. Both were removed in the v0.37.6 release along with the MANIFEST message that fed them (~335 lines): `syncState.peerManifests` had exactly one reader, the scoring loop inside `PopPendingPeer`, so the message and the scoring were the same feature. Removing it is wire-compatible in both directions, because the dispatch chain in `OnSyncMessage` has no `else`: an older peer's MANIFEST reaches an updated client and costs nothing. No `PROTOCOL_VERSION` bump and no floor raise. **The reasoning, which matters more than the mechanism:** gossip's guarantee is eventual delivery, not optimal routing, so it does not matter whether data reaches the most convenient partner next. The bookkeeping was not only code: `PopPendingPeer` recomputed every bucket hash (a full walk over 10k+ records) once per queued peer per pop. Two jobs the queue was quietly carrying had to survive it, and both are now single-purpose. **BUSY backoff** is `syncState.peerBusyUntil[peerKey]` plus `GBL:IsPeerBusy`, checked at the two automatic initiation sites (`HandleHello`'s skip chain and the bidirectional check's behind-branch) and deliberately NOT inside `RequestSync`, so a manual or forced pull still works. There used to be a second check behind the HELLO one, inside a jitter callback, to catch a BUSY arriving during the 0-1s deferral; it went with the jitter in v0.37.10 (#105), and a request now crosses a late BUSY on the wire instead, which `HandleBusy` resolves by aborting the receive it just started. **Combat deferral** is `syncState.helloAfterCombat` plus a forced `BroadcastHello` on combat end, which re-drives both directions (behind peers request from us, ahead peers reply or nudge). It is gated on the flag so a raid leaving combat together does not produce one broadcast per member; `FORCED_HELLO_COOLDOWN` is per client and would not stop that. The `isSyncPaused()` check is the third thing the queue used to provide, since everything deferred used to drain through `ProcessPendingPeers`, which checked. It is now its own arm in `HandleHello`'s skip chain, placed after the combat-lockdown arm so a HELLO arriving in combat still sets `helloAfterCombat`, and it logs which pause it was. What it covers is the cooldown that outlives the pause trigger (2s combat, 5s zone), the window in which `InCombatLockdown()` already reads false. Staleness and offline filtering are gone with no replacement and that is correct: a sync is now only ever started off a HELLO that just arrived or a session that just ended, so there is no way to name a peer we have not heard from.
- **Peer identity: always use `GBL:CanonicalPeerKey`** (src/Core.lua). The helper does its own local-realm-only strip via `GBL:_isLocalRealm`, NOT `Ambiguate("guild")`. Reason: retail's `Ambiguate("guild")` strips realm for ALL guildmates in a connected-realm group, which collapses two distinct same-name characters across connected realms (e.g. an Alice on Tichondrius and a different Alice on Stormrage in one guild) into one peer key. Custom strip rules: qualified `Name-Realm` keeps the suffix when realm differs from local (raw-or-normalized comparison), strips to bare when realm equals local. Bare input consults `guildData.playerRealms[name]` (built by `BuildRosterCache` on every `GUILD_ROSTER_UPDATE`, persistent across sessions); cross-realm bare names get re-realmed to `Name-Realm`, same-realm bare names stay bare. Both bare and qualified arrivals of the same character converge on the same canonical key in any realm topology, while two distinct same-name peers on different realms keep distinct keys. Bare names without a `playerRealms` entry (cold cache, departed peer, non-guildmate sender) pass through unchanged (best effort; the unresolvable case is two distinct same-name characters whose messages both arrive bare, which collide). **Defensive validation:** the helper rejects realm strings containing hyphens (corruption from a long-fixed code path; retail realm names never contain hyphens) and falls back to bare passthrough; `RepairCorruptedPlayerRealms` (called from `BuildRosterCache`) trims corrupt entries to their first segment so offline-peer corruption doesn't persist forever. `GBL:StripRealm` is reserved for true bare-name use cases where same-name on either realm should share state; the only current consumer is `recentWhisperTargets` for chat-system-message suppression (see comment near its declaration in `src/Sync.lua`). The test mock for `Ambiguate("guild")` is unused by `CanonicalPeerKey` now but still implements local-realm-only strip for any callers that legitimately want it. The `src/Sync.lua` `InitSync` knownPeers seed loop runs each persisted key through `CanonicalPeerKey` and consolidates `knownPeers` in place when a stale key collapses to a new canonical form. **Cold-roster gate:** `MigrateRecoverPeerRealms` returns 0 without bumping `schemaVersion` when `GetNumGuildMembers()` is 0 (cold roster); `GUILD_ROSTER_UPDATE` retriggers `MigrateAllGuilds` once per session via the `_migrationsRetried` flag so cold-roster short-circuits get a warm retry without waiting for the next login. Historical: v0.30.5 first patched the broken `Ambiguate(name, "none")` (identity in retail) with `StripRealm` (over-aggressive), then with `CanonicalPeerKey` wrapping `Ambiguate("guild")` (correct in tests but in-game collapsed all connected-realm guildmates to bare); the v0.30.5 follow-up replaced the `Ambiguate("guild")` delegation with custom local-realm-only logic, added the `playerRealms` fallback for bare arrivals, fixed the schema-11 cold-roster premature-bump, retriggered MigrateAllGuilds on first warm `GUILD_ROSTER_UPDATE`, and added `RepairCorruptedPlayerRealms`.
- **`chunkOutcomes[idx]` outcome vocabulary (v0.28.7):** `"pending"`, `"ok"`, `"aborted"` (ackTimeout), `"combatAbort"`, `"zoneAbort"`, `"busyAbort"`, `"sendFailed"` (target offline). Abort-tagging paths are all guarded by `outcome == "pending"` so a later ACK that sets `"ok"` wins correctly. **`retryReasons`** is a per-chunk array of `"ackTimeout"` / `"nack"` tags; only these two count toward the wire-loss `chunkFail` metric. Combat/zone/busy/offline aborts are bucketed separately — mixing them into a single "aborted" count loses the ability to tell a noisy test session from a reliability issue.
- **`sortAccess` rides HELLO like `accessControl` (v0.32.10).** The two-tier sort-access policy (`guildData.sortAccess`: write/sort tiers with rank thresholds + delegate lists) is attached to both HELLO builders in `src/Sync.lua`, gated on `(sortAccess.updatedAt or 0) > 0` so unconfigured guilds keep HELLO lean. `HandleHello` accepts a newer remote copy (last-writer-wins on `updatedAt`), normalizes it via `GBL:MigrateSortAccessShape`, and fires `GBL_ACCESS_CONTROL_CHANGED`; `SaveSortAccess` forces a HELLO and signals the same message. This propagation is what makes a GM's grant reach the granted member's client (before it, `sortAccess` was Core-only and never synced). Watch the delegate name-form edge: delegate keys are stored verbatim from the LayoutEditor input but matched against `normalizedPlayerName()` (space-stripped realm), so a multi-word-realm delegate typed with a space will not match.
- **Bank layout syncs via advertise-and-pull, NOT by riding HELLO (v0.32.11).** Unlike `accessControl`/`sortAccess` (small scalars that ride the HELLO body), the bank layout template is several KB, so putting it on every broadcast would regress the one-fragment HELLO the v0.28.x reliability arc fought for. Instead HELLO carries only `layoutUpdatedAt` (one timestamp, gated on `bankLayout.version > 0`). A receiver requests the full template via `LAYOUT_REQUEST` only when it both `HasSortAccess()` AND sees a newer cursor; the holder replies with `LAYOUT_DATA` (full template + `stockReserves`) over a whisper. The layout block in `HandleHello` sits AFTER the `sortAccess` merge, so a grant and its layout pull converge in a single HELLO round. There is NO ACK: every HELLO re-advertises the cursor, so a dropped `LAYOUT_DATA` is re-pulled on the next ping until cursors match (convergence, not per-message proof); `syncState.lastLayoutRequestAt` + `LAYOUT_REQUEST_THROTTLE` keep one request in flight. `GBL:AdoptRemoteBankLayout` validates via `BankLayout.Validate`, applies last-writer-wins on `updatedAt`, and bypasses the `HasLayoutWrite` gate (sync intake, not a local edit), then fires `GBL_LAYOUT_CHANGED` → `OnBankLayoutChanged` refreshes an open Layout/Sort tab. `SaveBankLayout` and a cursor-bumping `SetStockReserve` (only when `version > 0`, preserving the "version > 0 ⇒ valid layout" invariant) force a HELLO so the change advertises promptly. Serving is NOT access-gated (any holder serves, for epidemic spread); only requesting is gated. Watch: `LAYOUT_DATA` is a single whisper; if a real layout compresses above `WHISPER_SAFE_BYTES` it logs a `SyncWarn` (chunking is the unbuilt fix; the `nchunks`/`chunk` envelope fields reserve room for it). The mock serializer is pass-through, so payload size and numeric-key survival are not exercised in tests — verify in-game.

### Chunk sizing — observed reality

- **Every compression figure in this section is compressed size as a percentage of raw**, which is also what `chunkOutcomes.ratio`, the per-chunk send line and the `Compression for <peer>` summary all report. Lower is better. The per-chunk line printed the complement (percent reduction) until v0.37.12, so a capture taken before that reads 31% where this section would say 69%; invert it before comparing.
- **Compression ratio is 23–49%, not 23–26%.** v0.28.6 assumed ~18% and missed; v0.28.7 assumed 26% worst case and also missed. Measured across every capture: 23–26% (v0.28.5/28.6, item-heavy), 27–49% (v0.28.7 Roxeau), 30–42% (2026-08-10 Aeglos). Money-heavy chunks compress worst. **Derive any byte budget from the max, never the median**: `raw_budget <= (N * 255) / max_ratio`. Three consecutive misses came from predicting ratios.
- **Per-fragment drop is ~18%.** Back-solved from v0.28.6's `p_frag_est=44.9%` with 3-fragment chunks: `1-(1-0.18)^3 ≈ 0.45`. Reconfirmed at 18.7% in the 2026-08-10 capture. Per-peer route variance is ~25x, so this is a mid-range figure, not a constant.
- **The 1-fragment target was never met before #92.** v0.28.7 shipped `MAX_RECORDS_PER_CHUNK = 4` with `CHUNK_BYTE_BUDGET = 900` and believed the budget was binding. It never was: 4 records estimate ~790, so the record cap always sealed first, and the budget never fired once in a 2,731-chunk send. Worse, it only ever weighed records. The eventCounts rider (10 entries, ~768 B) and the envelope (~133 B) attach at serialize time, after chunking. Measured on a real chunk: 1,637 raw bytes, of which 736 were counted and 901 were not. Every chunk shipped as 3 fragments for four months.
- **Shipped (#92):** `CHUNK_TARGET_BYTES = 510` governing the **whole serialized message**, with `MAX_RECORDS_PER_CHUNK = 4` kept as a backstop. `PrepareChunks` reserves the envelope estimate up front and fills records then eventCounts entries against what is left, opening carrier chunks for leftover entries. Derivation: `255 / 0.50` at the worst measured ratio.
- **Density cost, measured:** at ~199 estimated bytes per record and a ~183-byte envelope allowance, the usable budget is ~327 bytes, which fits **one record per chunk** (two would need 398). A backfill therefore produces roughly one chunk per record instead of one per four. Per-record throughput is roughly a wash against the old 4-records-at-3-fragments arrangement; what improves is abort-resistance and the smoothness of partial progress. Do not expect a speedup from this change, and do not "fix" the density by raising the target without a compression measurement at the smaller size (see the open question below).
- **Open question — compression at small sizes.** Every ratio above was measured on ~1,600-byte messages. LibDeflate does worse on smaller inputs, and a 510-byte message may compress nearer 50–60% than 30–42%. That would put an encoded chunk back over 255 B. The runtime guard is the `over-255` counter in the FinishSending summary plus `syncState.lastChunkBytes`; read them on the first capture after this ships. This cannot be tested hermetically because LibDeflate is deliberately not vendored (see the wire-contract notes).
- **When a sync still aborts mid-stream:** the old advice ("do not shrink chunks, 1 fragment is the floor, raise `INTER_CHUNK_GAP_FLOOR` instead") assumed chunks were already 1 fragment. That precondition is only true from #92 on. Now that it holds, the gap floor is genuinely the next lever.
- **What NOT to do:** do not raise `CHUNK_TARGET_BYTES` without a fresh compression measurement at the new size, and do not re-derive it from a median ratio.

### Session cap — bounded slices (v0.37.7)

- **`SESSION_RECORD_CAP = 300`** (`src/Sync.lua`, exported as `GBL.SYNC_SESSION_RECORD_CAP`; specs must read the export, never the literal). A send stops at the first whole-bucket boundary at or past the cap. At the measured ~1 record per chunk and the 1.0s gap floor that is roughly 5 to 6 minutes per session, and about 2.5 minutes once the 708-byte budget (#96) lands. The number was chosen for session *length*, not byte count, so it moves when the per-chunk density does.
- **Whole buckets, never a partial one.** A half-sent 6-hour bucket hashes to something neither side holds, so it stays in the diff and comes back entire on the next request. Splitting a bucket to hit the cap exactly would mean a backfill that never converges. A single bucket larger than the whole cap still goes out whole, for the same reason.
- **`remaining` is how the receiver learns a session was capped.** Additive envelope field, final chunk only, omitted when zero, and attached in `SendNextChunk` at serialize time rather than baked into the chunk, so a NACK or ACK-timeout retransmit of the final chunk still carries it. `estimateEnvelopeBytes` reserves for it on **every** chunk: which chunk is final is not knowable while packing. An uncapped session therefore puts no new key on the wire at all, which is what keeps the wire-contract builder key-parity check green.
- **Tranche rotation is not partner selection.** `syncState.capLastTranche[peer]` records, per target, which buckets the last session carried and what their local hash was then. On the next request from that peer, buckets whose local hash has not moved since sort **last**. Without it, a receiver that already holds those buckets from a third peer pins the sender to the same all-duplicate tranche every session while older differing buckets starve. Session-only, self-expiring, and it does not choose who to sync with, so it is not the scored selection retired in v0.37.6. The bucket hashes are computed on **both** request paths for this: a request carrying no `bucketHashes` could otherwise never record a tranche and would loop on its first slice forever.
- **The continuation seam is the existing gossip, deliberately.** `FinishReceiving` reads `remaining` and `madeProgress` before teardown, logs "Partial session from `<peer>`: N bucket(s) remaining", and schedules nothing. The next request comes from the post-receive forced HELLO, the sender's superset nudge (60s throttle, shorter than a slice) and `shouldSync`. This is the ship-and-measure arm of a version-sequenced A/B, not an oversight: a spec pins that no continuation timer is scheduled. A direct 3s same-sender continuation is designed and held on file; build it only if a capture shows a median seam over ~30s or stalled backfills. Known edge: a zero-progress slice emits no forced HELLO and falls back to the 120s heartbeat, which tranche rotation should make rare. Measure it.

### Diagnosis discipline

- Do not lower a pacing constant without an independent reliability measurement — "more aggressive" is not the same as "better."
- Per-chunk audit outcomes (attempt count, wire-to-ACK latency, gap since prior chunk, estimated fragments) are the minimum signal needed to discriminate fragment loss from server throttle from callback-timing bugs. Add these before changing behavior.
- `sendChunkIndex` in the "Send complete X/Y chunks" line is the index of the **last attempted** chunk, not the count acknowledged. When writing future diagnostics or UI strings, prefer an explicit "N ok / M aborted" framing.
- **v0.28.7 FinishSending output is three per-peer lines:** `Sync outcomes for <peer>` (histogram + split abort causes), `Retry causes for <peer>` (ackTimeout / nack / chunkFail / p_frag with observed `n=` frags/chunk), `Compression for <peer>` (min/med/max compression percentage). `p_frag` is back-solved using observed average fragment count rather than `lastChunkBytes`, so A/B data across chunk-size changes is directly comparable. **Do not conflate `chunkFail` (raw retry rate) with `p_frag` (per-fragment loss)** — they are equal only at n=1 fragments.
- **Outcome vocabulary is load-bearing.** Any new abort/failure path should add a named outcome value, not reuse `"aborted"` — the split between wire-loss and environmental aborts is what makes the histogram interpretable.
- **v0.28.8 FinishReceiving emits a `Redundancy from <peer>` line** with total dupe rate + item-vs-money split (e.g. `78% duped (1023/1314 received) — items: 65% (412/635), money: 90% (611/679)`). Per-chunk audit also has a running `X% dup` annotation. This is the receiver-side complement to v0.28.7's three sender-side per-peer lines. Use it to decide whether bucket-granularity redundancy justifies designing a finer-grained exchange. Decision rule: `<30%` = bucket filter is doing most of the work, skip; `30–70%` = worth doing but not urgent; `>70%` = worth designing. **Note the cost moved:** that design used to be able to assume a periodic MANIFEST broadcast already existed to build on. It does not any more (see the free-agent pairing note below), so it now has to price in either reintroducing a broadcast or carrying the finer manifest inside the SYNC_REQUEST/SYNC_DATA session itself. This is a separate concern from partner selection, which is why removing MANIFEST did not retire the rule. Item-vs-money split tells you whether items, money, or both are the redundancy source — money-heavy redundancy may be addressable by smaller money-only buckets instead of full manifest. Suppression: line omitted on empty syncs; segments omitted when the corresponding record type is absent. **Do not conflate redundancy % with sender-side `chunkFail`** — redundancy measures dedup waste at the application layer, not wire-loss retries. **The figure is only trustworthy from v0.37.0 on.** Before it, a record rejected by `reconstructSyncRecord` incremented the dupe counter, so a peer sending nothing but corrupt records read as 100% duped, which this very decision rule reads as "the bucket filter is doing the work, skip". #68 gave rejects their own counter and their own `Rejected N record(s) from <peer>` line. Any redundancy reading from a capture taken before v0.37.0 carries that inflation and should not be compared against a later one. **A second inflation window opens at v0.37.11 and closes when the guild finishes updating.** A v0.37.11 client's request describes only its recent window in detail, and a pre-v0.37.11 server does not read `spans`, so it treats all of old history as missing and offers it. That converges (whole buckets, bounded per session by `SESSION_RECORD_CAP` on any server from v0.37.7 on) but it is nearly all duplicate, so a mixed-version capture reads high for a transitional reason rather than a structural one. Do not compare a reading taken during guild adoption against one from a settled guild, and do not read it as evidence for a finer-grained exchange.
- **v0.37.11 logs the two silent decode failures in `OnSyncMessage`**, at WARN, with sender, channel and the raw byte count. They used to be bare returns, which is what made a damaged arrival indistinguishable from a peer that never spoke. They are the direct measurement the erasure-coding question turns on: AceComm's reassembly has no sequence numbers and no completeness check, so a lost middle fragment is delivered as a truncated payload and lands here, and the surviving byte count says how much of the message made it. Payloads a few hundred bytes short mean independent single-fragment loss; payloads mostly missing, or silence, mean bursts. Those want different fixes, and forward error correction is only worth reconsidering for the first (see the spike on #108, which declined it for now). Read this before proposing any redundancy or coding scheme.
