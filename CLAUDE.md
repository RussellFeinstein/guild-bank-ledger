# GuildBankLedger — Project Instructions

## Overview

WoW addon that persistently logs guild bank transactions. Lua 5.1 + Ace3 stack. Tests via busted.

## Design Principles

**Accessibility first.** Accessibility is a blocking design requirement, not a retrofit. Every new UI feature lists its keyboard-navigation path, focus indicators, color-encoding fallbacks, font-scaling behavior, and screen-reader hooks during the design phase, alongside functional requirements. Implementation pairs with end-to-end verification: tabbing actually advances focus across all visible widgets, triple encoding actually distinguishes transactions without color, font scaling actually clamps without clipping, palettes actually auto-detect from WoW CVars. A claim in user-facing docs (CurseForge description, README, in-game About text, ChangelogView) requires end-to-end verification, not just confirmation that supporting functions exist somewhere in the codebase. See `~/.claude/accessibility.md` for the global standards checklist.

**The look is designed, not accumulated.** `docs/PLAN-visual-overhaul.md` (2026-09-21) is the direction every UI change is measured against: the native chassis, the four tab groups, the `UI/Theme.lua` tokens, the component vocabulary, the accessibility contract per element, the test seam and the migration order. Read it before changing the shell, a tab, a colour or a font, and change it when a step lands somewhere other than where it says. It also records that the high-contrast palette's "WCAG AAA" claim is unmet as measured (section 4), so do not repeat that claim anywhere until the replacement values land. Above it sits `docs/PLAN-views-and-access.md` (same day): the roles by rank and access family, what each role comes to the addon for, the view set each access mode shows (`full`, `own_transactions` as the Member set with My record, `sync_only`), what "own" means (the account, through a local roster), what may reach which client, and the one rule over all of it: the ledger functions as a standalone addon whether or not the hub is integrated. Read it before changing a gate, a tab list, a filter over another member's rows, or anything on HELLO; its section 5 recorded that `RefreshUI` had bypassed the Own Transactions filter since v0.15.0, which was the first thing built from either doc and shipped as #222 (the `UI/UI.lua` bullet in `.claude/rules/ui.md` carries the rule it left).

The May 2026 honest-status sweep discovered that `UI/Accessibility.lua` had defined `RegisterFocusable`, `AdvanceFocus`, and `SetFocusIndicator` since v0.3.0 but the functions were almost entirely unused outside `UI/ChangelogView.lua`. No AceGUI Tab key handler hooked into `AdvanceFocus`; no widget called `SetFocus`; no `TabIndex` attributes existed on the frame hierarchy. The README's "Full keyboard navigation (Tab/Shift+Tab)" claim was paper for multiple years. That regression is unacceptable; the audit pass and full widget wiring are a v1.0 release gate, codified in `docs/ROADMAP.md` Pre-1.0 readiness. Push accessibility left in every subsequent design discussion.

## Architecture

- **src/Core.lua** — AceAddon bootstrap, lifecycle, slash commands, bank open/close detection
- **src/Logger.lua**: Per-channel session log. Sync cap 2000, sort cap 3000, system cap 500, ledger cap 500. Severity levels DEBUG/INFO/WARN/ERROR; printf format with `pcall(string.format)` fallback so a bad format string never crashes. INFO/WARN/ERROR always record; DEBUG drops unless `db.profile.<channel>.debugChat` is on. Public API: `GBL:LogSync/LogSort/LogSystem/LogLedger(level, fmt, ...)` plus convenience wrappers (`SyncInfo`, `SortWarn`, `LedgerInfo`, etc.), `GetLog(channel)`, `GetMasterLog(opts)`, `ClearLog(channel)`. Surfaced on demand via `/gbl synclog`, `/gbl sortlog`, `/gbl systemlog`, `/gbl ledgerlog`, `/gbl logs` (master, interleaved by timestamp). **`GBL.LOG_CHANNELS` is the one list of channels** (a copy, in display order). Three other places name them, the capture's `ENTRY_CAPS`, the profile defaults in `src/Core.lua` and `scripts/audit-sessions.lua`'s `CHANNEL_ORDER`, and the "one list of channels" block in `spec/logger_spec.lua` pins each against it, so a channel added in one place fails the suite until it is added in all of them. `HandleLogsCommand` reads the list at call time, because Core loads before Logger. **The ledger channel is transaction recording's own (#85), not a share of system**, on Russell's call of 2026-10-02: a read that stores something writes a line, 1 to 157 a day measured from `scanTime` on this account, and system's 300-line capture is the budget #199 kept a restock run inside. Restock stays on system: it is the only producer that could fill that capture (about 13 lines a purchase), and the trigger to act is `audit-sessions.lua`'s `dropped` column reading `system:N`, at which point system's cap grows rather than restock moving.
- **src/AuditCapture.lua**: Persistent capture of Logger entries into the `GuildBankLedgerAuditDB` SavedVariable (raw account-wide global, deliberately NOT AceDB; see Conventions). Taps Logger's `emit()` via `GBL:CaptureAuditEntry(channel, entry)`; captures INFO/WARN/ERROR from every Logger channel (never DEBUG) into lazily-created per-login sessions with version-stamped headers (`addonVersion` incl. dev suffix, `protocolVersion`, player/realm/guild), per-channel caps (sync 1000 / sort 1500 / system 300 / ledger 300, oldest-out with `dropped` counters), 10-session rotation. A session saved before the ledger channel existed (#85) has no `ledger` list, and every reader treats it as empty. ON by default (`db.profile.sync.auditCapture`; recording locally is not a privacy event, the opt-in boundary is the unbuilt uploader, see docs/PLAN-audit-log-upload.md); `/gbl audit on|off|status|clear` manages it (`off` = kill switch, `clear` wipes the whole account's captures). The capture path self-heals a malformed SavedVariable shape rather than throwing, because an error would unwind Logger's `emit()` and break the caller being observed.
- **src/Scanner.lua**: Guild bank slot scanning (inventory snapshots), plus bag scanning for the sort (#139) and the record of which tabs a scan could see (#137). Full notes in [.claude/rules/sort.md](.claude/rules/sort.md).
- **src/Categories.lua** — Item classification via WoW classID/subclassID
- **src/Dedup.lua** — Deduplication engine (occurrence-based hashing, fuzzy matching, event count metadata, count-based cleanup)
- **src/Ledger.lua**: Transaction recording from GetGuildBankTransaction API. **Every log read writes one `Bank log read:` line to the ledger channel (#85)**: `on=open` or `on=rescan`, `via=event` or `via=timeout` (which timer ran it), `new`, `items`, `money`, `read`, `skipped` (entries with no type or name, which both read loops drop: the client does return a nil name, and Blizzard's own UI shows it as Unknown, #335) and `refused` (`StoreBatchRecords`' third return), then `[T1=new/read ... M=new/read]`. The open read is INFO on every visit. A rescan runs every 3s at the bank, so it is INFO only when it stored something or a log's counts moved since the previous read, and DEBUG otherwise. The previous read lives in `_lastLogRead`, kept per `guildData` for the session and deliberately not reset with the batch caches at bank close, or a nameless entry would warn on every visit. A WARN fires when a log's `skipped` or `refused` count goes above the most this session has already warned about for that log (`_lastLogRead.warned`), not above the previous read: the same entry is read again after every reopen and cache reset, and a tab that has not answered reads 0 and then comes back (#336), so a comparison with the previous read repeated the warning (the #85 review). An ERROR fires when either read raises. Both reads are `pcall`ed now: the rescan's error used to be discarded, and the open read's escaped the timer and skipped the callback that marks the first scan complete and starts the periodic rescan. The open read writes INFO when the guild bank window closed before it ran, and a rescan writes DEBUG, since every bank close ends a rescan chain that way. Both reads' debounce cancels need a handle the live client's `C_Timer.After` does not return (#118), so in game the first `GUILDBANKLOG_UPDATE`'s timer runs the read; #336 is what that does to a tab that has not answered by then, and the open line's per-tab counts are how a capture shows it. The four delays are exported (`GBL.LEDGER_SCAN_DEBOUNCE` and its three siblings) so the specs fire them by name. Also `GBL:GetTabName(tab, fallback)`, **the one place a bank tab is named for a LIVE reader** (#236), in four steps: the live name from `GetGuildBankTabInfo`, then a session cache of every name this client has read from the current guild's bank, then the caller's stored name, then `Tab N`. **The cache is what makes the fix work where it is needed**: `BackfillTabNames` (`src/Core.lua`) says the live read "only works while the bank is open", and the Restock tab is worked at the auction house, so the live branch answers nothing there; a remembered name is a reading rather than a guess, and it is per session so a rename is picked up on the next bank visit. **The cache is kept per guild (#287)**, keyed by `GetGuildName` as `GetGuildData` is: a player can change guild without logging out, and `BackfillTabNames` stores what this answers on records for good, so one guild's names must never answer for another's. The stored fallback covers the window before the bank has been opened at all. It is type-tested and its `|` is escaped, because `copyTab` passes `tabs[].name` through verbatim and `Validate` never looks at it, so a peer's layout reaches `SetText` with whatever it likes. Read by the record builders, by the Restock group heading and by the Layout tab's per-tab heading, which had its own copy of the rule until #236. **Historical records are the deliberate exception**: `CreateTxRecord` snapshots `tabName` at the transaction, and `UI/LedgerView.lua` renders that frozen string, so the Transactions list can show two names for one tab after a rename. That is a record of what the tab was called then, not a namer that drifted
- **src/Fingerprint.lua**: Dataset fingerprinting (djb2 hash, XOR aggregation, 6-hour bucket hashes); plus the bounded SYNC_REQUEST manifest (`BuildRequestManifest` splits a bucket table into the newest 50 buckets verbatim and up to 8 coarse spans, `FoldBucketRange` folds a span with order-dependent djb2 rather than XOR). The bucket-hash cache has three entry points beyond `GetBucketHashes`, because the sliced serve chain (#115) computes the cold path itself and cannot reach a file-local: `PeekBucketHashes` (cache when warm, nil when cold, never computes; `HandleHello` reads it), `_FreshBucketHashes` (the map only when current, which the chain asks first), and `StartBucketHashScan`/`StepBucketHashScan` for a resumable walk whose final step stamps the finished map into the cache, carrying the count from scan start so a record appended mid-walk forces a recompute rather than hiding in a short map, and stamping nothing if `ResetHashCache` ran since the walk began (#330), since a reset mid-walk can mean a walked id was rewritten in place. Both session caches, the dataset hash behind `GetDataHash` and the bucket map, key on the `guildData` table identity as well as the record count, through one file-local `cacheHolds`: a count-only key collides across two guilds in one session, which is how `GetDataHash` advertised the previous guild's hash after a mid-session guild change with a tied count (#276), and the bucket map decides which records get offered. Neither key can see an id rewritten in place, which is why every id-rewriting path calls `ResetHashCache`: the migration rungs at their exit, and a sync receive at the rewrite itself, in `NormalizeRecordId` (#330).
- **src/ItemCache.lua** — Lazy async item info cache (GetItemInfo + GET_ITEM_INFO_RECEIVED for synced records)
- **src/Sync.lua**: Guild-wide sync via AceComm (HELLO/SYNC_REQUEST/SYNC_DATA/ACK/BUSY/LAYOUT_REQUEST/LAYOUT_DATA protocol, epidemic gossip propagation, concurrent send+receive, free-agent pairing, hash-gated HELLO reply suppression, fingerprint-based delta sync, bounded sessions with whole-bucket slicing and per-target tranche rotation, per-peer BUSY cooldown, NACK backoff, combat/zone guards, bidirectional sync, bank-layout advertise-and-pull). Serving a request prepares across frames on a token-guarded `C_Timer.After(0)` chain of seven resumable stages (`prepStages`/`prepStep`) at `SYNC_PREP_RECORDS_PER_TICK = 1500`, with a `SYNC_PREP_TIMEOUT = 30`s watchdog; see the sliced-serving bullet in `.claude/rules/sync.md` for what must not be undone.
- **src/BankLayout.lua** — Per-guild saved bank layout templates (display/overflow/ignore tab modes with per-item slot counts and stack sizes); validation (at least one overflow tab from schema 2 / #57, optional numeric `overflowPriority` on overflow tabs with NaN rejected, no duplicate items across display tabs, ≤98 slots); `OrderedOverflowTabs` returns the overflow tabs in routing order (sort key `overflowPriority or tabIndex`, tabIndex tiebreak, total on unvalidated drafts), shared by the planner, `PrintSortPreview`, and the LayoutEditor fill-order label so the three never drift. `PrintSortPreview` subtracts `plan.unviewableOverflowTabs` from it before printing `Overflow tabs:` and names the removed ones as ` (not in scan: 5)`, so the breakdown lists what the sort will use rather than what the layout declares (#137); it subtracts rather than reading `plan.overflowTabs` because the planner's invalid-layout early return leaves that field empty, and this command is what someone runs to diagnose an invalid layout. Also: capture-from-snapshot; stock reserves storage; guild-wide sync via `BuildLayoutPayload`/`AdoptRemoteBankLayout` (advertise-and-pull, last-writer-wins on `bankLayout.updatedAt`). **`CaptureTabLayout(tabIndex, previousName)` snapshots the tab's name from `GetGuildBankTabInfo` once and nothing refreshes it**, so a rename in the guild bank leaves every synced copy carrying the old one; since #236 that field is a fallback for display rather than the name, and every reader goes through `GBL:GetTabName`. **The capture is its only writer, so it never overwrites a good name with nothing**: an empty live name counts as none, and `previousName` (the LayoutEditor passes the draft's) is kept instead, or a capture taken while the client could not name the tab would sync the loss guild-wide. The mode dropdown carries the name across its replacement of the tab table for the same reason. Re-stamping the stored names on Save is deliberately not built: it would write into synced state, which bumps the cursor and reaches every peer under last-writer-wins, on a reading of what `GetGuildBankTabInfo` answers for an unnamed tab, for a tab the rank cannot view, and before the bank has been opened, which nobody here has recorded (the 2026-09-17 rule)
- **src/SortPlanner.lua**: Pure-function move planner: given a bank snapshot + layout, produces deterministic ordered op list (split/move) to reshape bank. Full notes in [.claude/rules/sort.md](.claude/rules/sort.md).
- **src/SortExecutor.lua**: Executes a plan fire-and-forget on a self-rescheduling `C_Timer.After` loop, then rescans and replans until the bank converges. Full notes in [.claude/rules/sort.md](.claude/rules/sort.md), which also holds the 2026-09-17 rule the BankLayout and Restock notes cite: **never gate a safety action on a predicate whose real behaviour has not been observed, and a verification expires.**
- **src/Restock.lua**: Restock-to-target engine: the target math, the pending purchases, and the Auctionator search and commodity buy flow. Read `docs/PLAN-restock-ux.md` before changing it. Full notes in [.claude/rules/restock.md](.claude/rules/restock.md).
- **UI/Accessibility.lua** — Colorblind-safe palettes, font scaling, keyboard nav, triple encoding. `GBL:FocusNavKey(key, shiftDown)` is the one keyboard rule for every tab that captures keys (#214, #219): with nothing focused only TAB is consumed, with a widget focused TAB and the arrows move, ENTER and SPACE activate, ESCAPE resets; both `_RestockView_NavKey` and `_SortView_NavKey` delegate to it. `GBL:ResetFocus` drops the focus without touching the order (the ring hidden, `focusIndex` 0; not `ClearFocus`, which is WoW's protected unit-focus global and the EditBox method). `GBL:ActivateFocused` is the one walk activator (#211): OnClick for a button, `SetValue` plus `Fire("OnValueChanged")` for a CheckBox, `SetFocus` for an EditBox (Enter then commits through its own `OnEnterPressed`; a click is a handler it does not have), a disabled widget refused with the key left to propagate; the Sort and Restock tabs' `_*_ActivateFocused` delegate to it, because each had its own copy and the CheckBox branch was missing from one. `SetFocusIndicator` draws a 2px ring (four edge textures on `widget.frame`, read from the `FOCUS` palette colour, which is the same yellow in all eight palettes today, so the ring does not currently change with colourblind mode or high contrast; reading through the palette is what lets a future palette change it) and still sets `widget._focused`, which is the state other code reads. It was flag-only until #139, which is why the Sort and Restock focus walks were invisible; the tests could not catch it because the focus specs register plain tables and neither mock frame had `CreateTexture`, so nothing on either side could draw. `ClearFocusOrder` hides rings before clearing: AceGUI pools widget frames, so a ring left showing returns on whatever recycles that frame. A widget with no `.frame` (ChangelogView registers plain tables) degrades to flag-only rather than erroring.

## Critical WoW API Facts

- `GUILDBANKFRAME_OPENED/CLOSED` **removed in 10.0.2** — use `PLAYER_INTERACTION_MANAGER_FRAME_SHOW` with `Enum.PlayerInteractionType.GuildBanker`
- `GetGuildBankTransaction(tab, i)` returns **relative** time offsets — compute absolute via `GetServerTime() - offset`
- Must call `QueryGuildBankLog(tab)` before reading transactions; `QueryGuildBankTab(tab)` before reading slots
- Use `GetServerTime()` — never `time()` or `os.time()`
- Use numeric `classID`/`subclassID` via `C_Item.GetItemInfoInstant()` — never localized strings
- `MAX_GUILDBANK_SLOTS_PER_TAB = 98`
- `MAX_GUILDBANK_TABS = 8` (constant — max purchasable tabs)
- Money log tab index: `MAX_GUILDBANK_TABS + 1` (always 9, NOT `GetNumGuildBankTabs() + 1`)
- `GetGuildBankMoneyTransaction` returns type `"withdrawal"` (not `"withdraw"`) — normalize at record creation

## Conventions

- Addon object: `GBL` (local alias for the AceAddon instance)
- **In-game strings are ASCII.** Anything the addon can put on screen stays inside byte 127: chat output, labels, tooltips, audit lines, and `CHANGELOG_DATA`. WoW's default fonts carry Latin-1 and little past it, so an em dash, an arrow or a check mark draws as a blank or a box depending on the font and the client's locale. Symbols used as UI encoding fail worst, because a check mark that does not draw leaves a row whose state is carried by colour alone, which is the triple-encoding failure the accessibility rule exists to prevent. Code comments are exempt: they never reach a player. `spec/ascii_strings_spec.lua` enforces this over the file list in the `.toc`, stripping comments first and decoding decimal escapes, since `"\226\156\147"` is ASCII on disk and a check mark on screen.
- Module registration: use AceAddon modules, not standalone globals
- Events: always check interaction type before acting on `PLAYER_INTERACTION_MANAGER_FRAME_SHOW`
- Timestamps: always `GetServerTime()`, never `time()`
- Item IDs: use `C_Item.GetItemInfoInstant()` for classID/subclassID
- Guard `Enum.PlayerInteractionType.GuildBanker` existence for Classic compat
- Saved variables: `GuildBankLedgerDB` (AceDB), data keyed per guild name. Deliberate exception: `GuildBankLedgerAuditDB` (src/AuditCapture.lua) is a raw account-wide global, NOT AceDB and NOT guild-keyed — it is an append-only diagnostic capture store whose collection unit is the account's SavedVariables file; sessions carry player/realm/guild in their headers. Do not migrate it into AceDB (a second `AceDB:New` also breaks the `MockAce.dbInstance` single-instance assumption in specs).
- **A synced layout can arrive string-keyed.** Whether AceSerializer keeps numeric table keys through the layout sync is recorded as unverified in game, because the mock serializer passes tables straight through (the layout bullet in `.claude/rules/sync.md`). Code that joins synced layout data to number-keyed stock or reserves coerces the key first; `src/Restock.lua` and `UI/LayoutEditor.lua` both do, and the Restock comments that say "per CLAUDE.md" mean this line.
- **`docs/DATA-MODEL.md` is the record of what is actually stored, and of what is being done about the places the code disagrees with itself.** Read it before answering any question about what is stored, and before changing records, dedup, or the sync payload. The defaults block, the record builders and the live SavedVariables all disagree; every disagreement in the doc now carries a verdict, and the issues are collected under the **Data model integrity** milestone. Two things to take from it before touching anything here. `schemaVersion` defaults to 8 while migrations run to 11, and that is correct: AceDB strips a value equal to its default and hands back the current default on load, so the default IS the stored version of every guild sitting at it, and raising it strands them past migrations 9 to 11 permanently. Both halves are spec-pinned as of 2026-09-24, in two files that fail on different mutations: `spec/savedvariables_spec.lua` round-trips the default through a real AceDB and is what reds if the default is raised (#77, PR #261), and `spec/schema_version_spec.lua` asserts the ladder as a sequence, each rung bumping by exactly one (#76). The sequence assertion is also the only thing that reds if a strict gate is loosened to `>=`, since a guild above a gate is refused by both forms; `spec/core_spec.lua` holds the below-the-rung side. **Both of `OnEnable`'s per-guild walks take one guild at a time under `pcall` since #263**, the ladder in `MigrateAllGuilds` and the dedup pass in `DeduplicateAllGuilds`, because one guild's raise used to abandon every guild after it and then the whole of `OnEnable` below it, silently: AceAddon runs `OnEnable` under `safecall` and neither pass logs anything of its own. Isolating only the ladder moves that failure four lines down, since the corruption class that makes a rung raise reaches `BuildTxPrefix` and `ComputeTxHash` too, and `InitSync` still never runs. A failure is named once per guild per session on the system channel, so a capture is grepped for `Migration failed` and `Dedup pass failed`, and the hash cache is reset in both branches because a raise can leave it warm over ids a half-run pass already rewrote. Nothing in either loop may read the guild table outside the protection, or the isolation has a hole at its own first statement. That work is also why `DeduplicateRecords` no longer writes the version at all: the branch that forced it to 5 was reachable only through a stranded guild, and skipped the rungs beneath rung 5 when it fired. Two limits it left, both filed, and **#265 is closed (v0.41.11)**: rungs 7 and 10 rewrote `record.id` and never called `ResetHashCache`, so both caches in `src/Fingerprint.lua`, which key on the record count that a rewrite in place does not move, went on answering for ids no record carried, and the guild advertised that on HELLO. Each rung resets at its exit now, conditional on the same flag that gates its `seenTxHashes` rebuild, because clearing a warm bucket map costs a full walk of the history (#115) and a guild the rung did nothing to should not pay for it. `spec/schema_version_spec.lua` section 8 pins both behaviourally and adds a structural case that reads the id-rewriting rungs out of `src/Core.lua`, so a rung added later joins the contract without anyone having to remember it. Still open is #266, a guild left half-migrated reaching sync with `seenTxHashes` keyed on ids its records no longer carry. #266 is a pre-existing defect the isolation widened rather than one it created: the `GUILD_ROSTER_UPDATE` retrigger already re-ran the ladder with sync live, and what changed is that the `OnEnable` path no longer masks it by taking `OnEnable` down. And **unknown keys on a synced record must pass through untouched**: that tolerance is what makes adding a record field free, and a whitelist at intake would turn every future field into a forced guild-wide update. The doc also carries the measured sync-corruption rate (11.66% of everything ever received) and the `syncState.peers` name collision, whose persisted half turns out to have no reader at all.
- **Sync is guild-wide** — all members participate in HELLO/sync, not just officers. Officer rank only gates UI visibility (settings, admin features). Never add rank checks to the sync protocol.
- **Public description sync**: `docs/CURSEFORGE-DESCRIPTION.md` is the source of truth for the CurseForge project page. When user-facing surface changes (slash commands, UI tabs, access control, sync features, planned-feature framing), update it in the same PR. CI emits a `::warning::` annotation on PRs that change feature-surface files (`README.md`, `docs/ROADMAP.md`, `src/**/*.lua`, `UI/**/*.lua`, `GuildBankLedger.toc`) without updating the description; treat it as a checklist prompt, not a blocking gate. Pasting the updated content into the CurseForge web UI is a manual release step until BigWigsMods/packager#187 lands.

## Branch Workflow

`main` is the integration target and is GitHub-protected (PR + `test-and-lint` CI required, merge commits only, force-push and deletion blocked). Auto branch deletion on merge is **on**: `main` is the only permanent branch in this repo, and every other branch is deleted when its PR merges.

### Branches

Every branch is single-purpose: cut from the latest `main`, scoped to one PR, deleted when that PR merges. Follow-up work gets a fresh branch. Branch names are never reused.

- `feat/<thing>` for new features
- `fix/<thing>` for bug fixes that are not urgent
- `chore/<thing>` for maintainer chores, repo-config changes, doc-only updates
- `infra/<thing>` for CI / build / tooling changes
- `refactor/<thing>` for restructuring with no behaviour change (maps to `type: refactor`)
- `hotfix/<thing>` for urgent production-impact fixes (see Hotfix rule below)

`feature/` is retired in favour of `feat/`.

**No long-lived branches.** From 2026-04-27 to 2026-08-07 this repo ran long-lived per-area topic branches: `ui`, `sync`, `layout-sort`, `restock`, plus an `accessibility` lane that was declared but never created. They worked. They are retired because the global rule now allows a long-lived branch only for release maintenance in a project shipping several versions in parallel, and GBL ships one version at a time to CurseForge. All of them were merged and deleted on 2026-08-07. Do not recreate them, and do not read their absence as an accident.

See **Branch lifecycle: trunk-based, delete after merge** in `~/.claude/CLAUDE.md` for the full rule and the agent-side decision rule.

### Rules

- **Scope check before the first commit of every session**: the checked-out branch is not authorization to commit to it. If the intended work does not match the branch's type and slug, cut a fresh branch from the latest `main`.
- **Hotfix rule**: an urgent production-impact fix gets its own `hotfix/<thing>` branch off `main` and ships on its own. Never hold one back to bundle it with unrelated work.
- **Cross-branch rule**: when one feature spans two branches (e.g. a sync change that needs a UI tab), merge the upstream-of-the-dependency branch first, rebase the dependent branch onto the new `main`, then commit the dependent piece. Never PR both simultaneously hoping git resolves the order.
- **Rebase cadence**: cut from the latest `main`, and rebase an open branch onto `origin/main` after any intervening merge. `git rebase origin/main` if conflicts are tame; fall back to `git merge origin/main` if not. `git push --force-with-lease` is fine on your own unmerged branch.
- **Version-stamp cadence (covers CHANGELOG and every other version artifact)**: a branch stamps every version artifact only when opening the PR, in a dedicated stamp commit. Work on the branch leaves all of these untouched and lets `[Unreleased]` accumulate:
    - `VERSION` file
    - `GuildBankLedger.toc` `## Version:` field
    - `src/Core.lua` `local VERSION = "..."` constant
    - `CHANGELOG.md` (the `## [X.Y.Z] - YYYY-MM-DD` header; work lands under `[Unreleased]` until stamp time)
    - `UI/ChangelogView.lua` `CHANGELOG_DATA` table (in-game changelog)
    - This `CLAUDE.md`'s "Current: X.Y.Z" line at the bottom
    - `src/Core.lua` `local DEV_BUILD = ...` constant must be reset to `nil` in the stamp commit. CI rejects any other value via the `Verify DEV_BUILD is nil` workflow step.

  **Do NOT sweep the version string through `spec/fixtures/wire/`.** Those files pin several releases at once on purpose: a v0.36.0 HELLO pair, a v0.37.0 floor-aware HELLO and SYNC_REQUEST, a pre-#67 deposit and a post-#67 one. Each is a frozen recording of what that version put on the wire, and the point is that it keeps saying so forever. A grep-and-replace stamp will try to bump all of them and quietly destroy the cross-version contract they exist to hold. The trap is that it destroys them *silently*: a sweep changes the frozen `serialized` string and its expectation table together, so the suite stays green while the fixture stops recording anything. If a fixture ever needs to change, `lua spec/fixtures/generate_wire_fixtures.lua` reports which committed string no longer decodes to its hand-written table; that is a finding, never a refresh.

  `spec/ui/changelog_spec.lua` asserts that `CHANGELOG_DATA[1]`'s version matches the addon version, so a half-landed stamp fails the suite instead of shipping. If two branches PR with the same target version, the second to merge rebases onto post-merge `main` and its stamp commit bumps to the next patch. The principle is: one version per PR, one stamp commit per PR, never per-commit churn on these artifacts. (This matches the global `~/.claude/CLAUDE.md` "Commit Versioning" standard, which stamps once at PR-open.)
- **Doc-only PRs take no version and no tag.** The objective test is whether the PR changes any file that ends up in the packaged zip. `.pkgmeta`'s `ignore:` list strips `spec`, `docs`, `.busted`, `.luacheckrc`, `.gitignore`, `.claude`, `CLAUDE.md`, `*.md`, `*.sh`, `*.bat`, and `VERSION`. If every file a PR touches is stripped, the packaged addon is byte-identical apart from the stamp itself, and there is nothing to release. Stamping one anyway ships a version whose only user-visible content is the announcement of its own existence. Before v0.37.0 it also cost a forced guild-wide sync break (see Release cost below); now the cost is a contentless update pushed to every auto-updating install, which is still not worth paying. This narrows the global "every merged PR gets a bump and a tag" rule rather than overturning it: that rule's origin (PR #7) was addon-relevant work shipping untagged, which this test still catches. A PR that touches even one packaged file is a normal release.

  **`CHANGELOG.md` is the trap: it ships despite matching `*.md`.** The packager detects a changelog file and copies it back into the package regardless of the ignore list, and also feeds it to CurseForge as the release notes. Verified against the published v0.36.0 zip, whose only top-level files are `CHANGELOG.md`, `GuildBankLedger.toc`, and `LICENSE`; `README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `spec/`, and `docs/` are all absent. So a CHANGELOG-only PR is **not** doc-only. Do not read the ignore list on its own. When a PR sits near the line, settle it empirically: `gh release download <tag> --pattern "*.zip"` and list the archive.
- **Dev-build isolation**: at the start of any branch session that ships protocol-affecting or schema-affecting changes, set `local DEV_BUILD = "<branch>"` in `src/Core.lua`. The runtime `self.version` becomes `X.Y.Z-dev.<branch>` and `GBL:IsVersionCompatible` refuses to sync with production peers in both directions, including the user's own production-version characters on the same account. Since v0.37.0 that refusal comes from the `isPlainSemver` short-circuit rather than the old exact-match gate, which is why that check has to stay ahead of every `CompareSemver` call (see Release cost above). The flag is reset to `nil` in the stamp commit (see Version-stamp cadence above). Local `bash run_tests.sh` is intentionally not gated on the flag so dev iteration keeps working; CI is the enforcement boundary, and `scripts/hooks/pre-push` is the local-clone fast-fail (activate once per clone with `git config core.hooksPath scripts/hooks`).
- **CI cadence**: `.github/workflows/ci.yml` runs on `pull_request` and `push: main` only. Intermediate commits on a branch are unverified by CI. Run `bash run_tests.sh` and `bash run_tests.sh --lint` locally before each commit so the branch stays green.
- **Carve-out from the global "small, focused PRs" rule**: the user's global `~/.claude/CLAUDE.md` "Open Source / Public Repo Workflow" section says "Keep PRs small and focused, one concern per PR." That rule is for external-contributor PRs. For the maintainer's own PRs in this repo, multiple related commits covering one concern is the intended pattern. External contributor PRs still follow the small-and-focused rule.

### Release cost: paid in full at v0.37.0, and only payable again on a floor raise

**Historical, through v0.36.1.** `HandleHello` refused to sync on **any** version difference, patch included, so every release was a forced lockstep guild update and until every member updated the guild was split into non-communicating islands. That cost was per account rather than per character (SavedVariables are account-wide, so a player's alts share one install and one version), but it was real and it was paid by other people. It is why doc-only PRs take no version, why bundling beat a fast sequence of small releases, and why the 103 tags cut between 2026-04-07 and 2026-06-24 were an accumulating bill.

**From v0.37.0 on, `MIN_SYNC_VERSION` replaces it with a range** (`src/Sync.lua`, `GBL:IsVersionCompatible`). Two peers sync when each is at or above the other's advertised floor. An ordinary release now costs nothing: ship a patch and a guild running three different versions keeps converging.

Three things to keep straight before touching it.

- **Raise the floor ONLY for a wire, record-identity or fingerprint break.** Never for a normal release, however large the diff. Raising it re-imposes exactly the lockstep split the floor exists to remove, so the value in the source is a decision about compatibility, not a version number that tracks releases. It moved to `0.37.0` in that release's stamp commit and should sit there until something genuinely breaks compatibility. **Worked example of a wire change that did not qualify: the v0.37.11 request manifest (#108).** It changed what SYNC_REQUEST puts on the wire, and a raise had been cleared for it, and it still did not take one, because the change turned out to be additive in both directions: unknown keys pass through untouched, and the serving side's "a bucket you did not mention reads as hash 0, so send it" rule means an under-described request degrades to redundancy rather than to divergence. The test to apply is not "did the wire format change" but "can either side misread the other into losing records". Where the answer is no, the cost of a raise (a split guild for the length of the adoption window, which for a starvation fix delays the very outcome being shipped) buys nothing.
- **v0.37.0 is the last prepaid compatibility break.** Before it, an id-format change was automatically safe: peers on different versions refused each other, so records built under two `buildPrefix` implementations never met. After it they do meet, and if their implementations disagree both sides accept the other's records as new and the guild's dataset silently duplicates. So an id-affecting change now costs a floor raise, which is why #67 (the tab in the prefix) had to ride v0.37.0 rather than follow it.
- **A peer advertising no `minSyncVersion` falls back to exact match.** That is the correct reading of a pre-v0.37.0 build and it is what keeps the old refusal behaviour testable. A peer sending no `version` at all is incompatible everywhere, which is what lets `HandleSyncRequest` recognise a pre-floor request.

The gate lives at three sites, not one: `HandleHello`, `HandleSyncRequest` (a request never passes through HELLO), and `RequestSync` (the bidirectional check after `FinishSending` reaches it without one, and so does a manual pull). All three call `IsVersionCompatible`. The settings merges in `HandleHello` deliberately sit **above** the gate so a GM's access-control, sort-access or layout change still propagates through a mixed-version window; only record exchange is gated. An incompatible peer gets one HELLO reply per session via `syncState.incompatibleReplied`, not one per heartbeat.

`IsVersionCompatible` short-circuits on `isPlainSemver` **before** any `CompareSemver` call. `CompareSemver` strips `-dev.<id>` by design, so a range test that reached it would read a dev build and its base release as compatible and undo `DEV_BUILD` isolation entirely. Do not reorder those checks.

### What reaches the public CurseForge channel

`.github/workflows/release.yml` fires only on `push:` of a `v*` tag. `BigWigsMods/packager` derives the release type from the tag name: a tag containing `alpha` or `beta` (case-insensitive) uploads as that channel, anything else uploads as a full release, and an untagged run packages as alpha. Three levers follow, in increasing order of machinery:

1. **Do not tag.** No tag, no workflow run, no CurseForge upload, no GitHub release.
2. **Tag with `-alpha` or `-beta` in the name.** Still matches the `v*` trigger and still uploads, but CurseForge files it off the default channel so users are not offered it.
3. **`-d` on the packager.** Skips uploading entirely. More machinery than either of the above and not currently needed.

Recorded as available options, not current practice. The caveat that matters: channel choice cannot change what the maintainer actually runs, because this repo is symlinked into AddOns, so the maintainer's client advertises whatever `main` holds regardless of what CurseForge is serving. Since v0.37.0, sync fragmentation is governed by the floor alone, not by version count; ordinary releases cost update churn, and only a floor raise re-imposes a guild split. Channel choice controls how much of that churn the guild sees.

## Issue and PR labels

21 labels: 6 `type:`, 8 `area:`, one `tracking issue`, and GitHub's 6 remaining defaults. Adopted 2026-08-14 (#73), backfilled in one pass across all 42 issues and all 68 PRs, closed and merged included. Each label's GitHub description carries its own rule, so the meaning cannot drift into someone's head. The contributor-facing version lives in [CONTRIBUTING.md](CONTRIBUTING.md); this section is the maintainer's copy and carries the reasons.

**Invariant, after triage: exactly one `type:` and at least one `area:`.** A second `area:` only where the item has separate acceptance criteria in two places (#44, #52, #77, #93 are the four). An unlabeled inbound issue from an outside contributor is the normal starting state, not a miss: applying labels needs triage permission, so a contributor cannot do it.

- **`type:` mirrors the branch prefixes**: `fix/` and `hotfix/` to `type: bug`, `feat/` to `type: enhancement`, `chore/` to `type: chore`, `infra/` to `type: infra`, `refactor/` to `type: refactor`. `type: documentation` is the exception with no prefix of its own, because doc-only work goes on `chore/` here; it is applied by hand.
- **`type:` keeps GitHub's default wording rather than the prefix wording** (`type: bug`, not `type: fix`). WoW-Economy-Forecaster renamed to match its prefixes; this repo is public and takes outside PRs, so the words a stranger already recognizes are worth more than a literal 1:1 with the branch name. The mapping above is still 1:1 in the direction that matters: every prefix implies exactly one label.
- **`area:` names the subsystem**: sync (Sync.lua, Fingerprint.lua, protocol, peer identity), storage (Ledger, Dedup, records, schema, migrations), sort (SortPlanner, SortExecutor, SortView), restock, layout (BankLayout, LayoutEditor), ui, accessibility, repo (CI, test infrastructure, governance, repo docs). `layout` stays separate from `sort` because #57 and #58 are about what the layout model can express rather than about sorting.
- **`area: repo` is an eighth label beyond the seven designed in #73**, added because three open issues needed it (#51, #73, #77) and about twenty PRs did. That is the rule working: a taxonomy entry is added when an item needs it, never because the set looks incomplete. `area: core` still does not exist, because no issue is core-only today. `src/Core.lua`, `src/Logger.lua` and `src/ItemCache.lua` are unmapped in the labeler for the same reason; they are cross-cutting, so the area comes from whatever else the PR touched.
- **`UI/ChangelogView.lua` and `CLAUDE.md` are unmapped too, and that one was learned the hard way (#128, fixed 2026-08-21).** Both are written by every version stamp, so every release PR arrived carrying `area: ui` and `area: repo` whatever it was about, and the labels were stripped by hand on four consecutive releases (#124, #125, #127, #129) before the rule itself was fixed. The failure is worth telling apart from the config-versus-backfill trap that #112 fixed: that one was two implementations of the taxonomy disagreeing, and diffing them against each other found it. This one is a single internally-consistent rule that fires on a strict superset of what it means, so nothing internal contradicts and only reading the applied labels against what the PR actually changed finds it. Hand-stripping is not a fix: it works until the release nobody remembers to strip, and that one is mislabelled in the record forever. Note that `spec/ui/changelog_spec.lua` stays mapped, because the stamp never touches it. **Read the labels on every PR before merging it** either way: that duty covers the advisory-glob misses the config header already warns about, and it is what caught this.
- **The defaults are NOT pruned.** The global rule that deletes `good first issue` and `help wanted` is conditional on a repo taking no outside PRs, and this one does (#40 came from outside; PRs #1, #24, #25, #27 and #32 came from forks). Those two are discovery surface and stay, along with `question`, `duplicate`, `invalid` and `wontfix`.
- **No priority axis.** The scope addition on #73's comment stays recorded there until an issue actually needs it.
- **Milestones are not duplicated as labels.** Areas overlapping milestones is deliberate: milestones are chronological arcs that close and stop being lookup tools, so `gh issue list --state all --label "area: sync"` is the only thing that assembles a subsystem's whole history across them. That is why closed issues and merged PRs are labelled at all.
- **PRs label themselves** via [.github/workflows/labeler.yml](.github/workflows/labeler.yml), rules in [.github/labeler.yml](.github/labeler.yml). It runs on **`pull_request_target`**, unlike the WoW-Economy-Forecaster copy it was modelled on, because a `pull_request` run for a fork PR gets a read-only token whatever the `permissions:` block says. Never add a checkout step to that workflow, and never change the action version and the config file in the same PR: the run reads config from base while the action comes from head. `sync-labels` stays off, so it only adds and never removes a hand-applied label.
- **`tracking issue` is a third axis: one label and one open issue, added 2026-09-19 (Russell's call) for the build-order issue #188, modelled on WGA-Raid-Hub's #1155.** It holds the cross-milestone order and no work of its own; each milestone description keeps its within-milestone order, and the issue is pinned so it sits at the top of the Issues page. It carries `type: chore` and `area: repo` as well, so the one-type-one-area invariant holds on it; the label exists so a search for it finds the current order in one hit, which neither axis can do. Not on the labeler: no path predicts it. When the body nears GitHub's 64 KB cap, open a successor that names the old one and close the old one, which is what the hub did with #947 and #1155.
