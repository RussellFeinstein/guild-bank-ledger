# GuildBankLedger — Project Instructions

## Overview

WoW addon that persistently logs guild bank transactions. Lua 5.1 + Ace3 stack. Tests via busted.

## Design Principles

**Accessibility first.** Accessibility is a blocking design requirement, not a retrofit. Every new UI feature lists its keyboard-navigation path, focus indicators, color-encoding fallbacks, font-scaling behavior, and screen-reader hooks during the design phase, alongside functional requirements. Implementation pairs with end-to-end verification: tabbing actually advances focus across all visible widgets, triple encoding actually distinguishes transactions without color, font scaling actually clamps without clipping, palettes actually auto-detect from WoW CVars. A claim in user-facing docs (CurseForge description, README, in-game About text, ChangelogView) requires end-to-end verification, not just confirmation that supporting functions exist somewhere in the codebase. See `~/.claude/accessibility.md` for the global standards checklist.

**The look is designed, not accumulated.** `docs/PLAN-visual-overhaul.md` (2026-09-21) is the direction every UI change is measured against: the native chassis, the four tab groups, the `UI/Theme.lua` tokens, the component vocabulary, the accessibility contract per element, the test seam and the migration order. Read it before changing the shell, a tab, a colour or a font, and change it when a step lands somewhere other than where it says. It also records that the high-contrast palette's "WCAG AAA" claim is unmet as measured (section 4), so do not repeat that claim anywhere until the replacement values land. Above it sits `docs/PLAN-views-and-access.md` (same day): the roles by rank and access family, what each role comes to the addon for, the view set each access mode shows (`full`, `own_transactions` as the Member set with My record, `sync_only`), what "own" means (the account, through a local roster), what may reach which client, and the one rule over all of it: the ledger functions as a standalone addon whether or not the hub is integrated. Read it before changing a gate, a tab list, a filter over another member's rows, or anything on HELLO; its section 5 recorded that `RefreshUI` had bypassed the Own Transactions filter since v0.15.0, which was the first thing built from either doc and shipped as #222 (the `UI/UI.lua` bullet below carries the rule it left).

The May 2026 honest-status sweep discovered that `UI/Accessibility.lua` had defined `RegisterFocusable`, `AdvanceFocus`, and `SetFocusIndicator` since v0.3.0 but the functions were almost entirely unused outside `UI/ChangelogView.lua`. No AceGUI Tab key handler hooked into `AdvanceFocus`; no widget called `SetFocus`; no `TabIndex` attributes existed on the frame hierarchy. The README's "Full keyboard navigation (Tab/Shift+Tab)" claim was paper for multiple years. That regression is unacceptable; the audit pass and full widget wiring are a v1.0 release gate, codified in `docs/ROADMAP.md` Pre-1.0 readiness. Push accessibility left in every subsequent design discussion.

## Architecture

- **src/Core.lua** — AceAddon bootstrap, lifecycle, slash commands, bank open/close detection
- **src/Logger.lua**: Per-channel session log. Sync cap 2000, sort cap 3000, system cap 500. Severity levels DEBUG/INFO/WARN/ERROR; printf format with `pcall(string.format)` fallback so a bad format string never crashes. INFO/WARN/ERROR always record; DEBUG drops unless `db.profile.<channel>.debugChat` is on. Public API: `GBL:LogSync/LogSort/LogSystem(level, fmt, ...)` plus convenience wrappers (`SyncInfo`, `SortWarn`, etc.), `GetLog(channel)`, `GetMasterLog(opts)`, `ClearLog(channel)`. Surfaced on demand via `/gbl synclog`, `/gbl sortlog`, `/gbl logs` (master, interleaved by timestamp).
- **src/AuditCapture.lua** — Persistent capture of Logger entries into the `GuildBankLedgerAuditDB` SavedVariable (raw account-wide global, deliberately NOT AceDB; see Conventions). Taps Logger's `emit()` via `GBL:CaptureAuditEntry(channel, entry)`; captures INFO/WARN/ERROR from all three channels (never DEBUG) into lazily-created per-login sessions with version-stamped headers (`addonVersion` incl. dev suffix, `protocolVersion`, player/realm/guild), per-channel caps (sync 1000 / sort 1500 / system 300, oldest-out with `dropped` counters), 10-session rotation. ON by default (`db.profile.sync.auditCapture`; recording locally is not a privacy event, the opt-in boundary is the unbuilt uploader, see docs/PLAN-audit-log-upload.md); `/gbl audit on|off|status|clear` manages it (`off` = kill switch, `clear` wipes the whole account's captures). The capture path self-heals a malformed SavedVariable shape rather than throwing, because an error would unwind Logger's `emit()` and break the caller being observed.
- **src/Scanner.lua** — Guild bank slot scanning (inventory snapshots). Also owns bag scanning for the sort (#139): `ScanBags` reads bags 0-4 plus the reagent bag synchronously through `C_Container` into a bank-shaped snapshot keyed by NEGATIVE pseudo-tabs, skipping bound, locked and link-less slots with per-bag counters and warming the item cache once per distinct item. **Those counters are not scanner-local bookkeeping any more**: the planner reads `boundSkips`, `lockedSkips` and `noLink` off the snapshot and reports them on the plan line as `bound=`, `locked=` and `nolink=`, so a player whose bags looked full but deposited nothing gets the reason instead of a zero. Anything added to the skip set needs a counter and a term beside them or it becomes an invisible subtraction. **The bank half of that rule is half-kept on purpose.** `ScanTab` skips a slot two ways: locked, which it counts into `tabResult.lockedSkips` and which the plan line reports as `locked=` since v0.39.12 (#178; see the SortPlanner bullet), and link-less, which has no counter. Before that the locked count only ever reached the SYSTEM channel (`T5=12(event,locked=2)`), and a sort gets diagnosed from `/gbl sortlog`, so from the plan line's point of view it did not exist. A `nolink=` term beside it needs to know what `GetGuildBankItemInfo` returns for a slot with no link, which nothing had recorded, because `ScanTab` gates every read on `GetGuildBankItemLink`. v0.39.12 probed for it with a per-scan `Scan linkless:` line on the system channel; it read zero warm and zero again after a full client relaunch with the bank opened first (2026-09-19, on #178), a consumer-side zero of exactly the shape the 2026-08-29 lesson warns about, which proves nothing about the API. That closed the question as a decision to stop measuring rather than as a finding, so v0.39.15 removed the probe (#184) and put the info read back under the link test, where it costs one call per occupied slot rather than one per slot. **Admission never moved through either change**: the link gates it and a locked slot is counted only when it has a link, which is what keeps `lockedSkips` meaning what `locked=` says. `TabFromBagID` / `BagIDFromTab` are the encoding (bagID N is tab `-(N+1)`, so a pseudo-tab can never collide with bank tabs 1-8 nor enter `layout.tabs`, whose Validate rejects tabIndex < 1), and `FormatSlotRef` is the single render helper every sort-side site routes through so a negative tab can never surface as `T-1`. The reagent bag is admitted only when its client-supplied index round-trips through the encoding, and `BagIDFromTab` rejects a non-integer tab: both keep a tab the executor could not decode back into a bag index out of the pipeline. `ExtractItemID` and `GetMaxStack` are both existence-guarded because Scanner loads ahead of BankLayout and ItemCache in the .toc. **`FinalizeScan` also records what the scan could look at (#137)**: `lastScanCoverage = { viewableTabs = {...} }`, read back through `GetLastScanCoverage`, written in that one place beside `lastScanResults` so a snapshot and its coverage always describe the same scan. It cannot ride on the results table, and that is the whole reason it is a second record: `FinalizeScan` sums `itemCount` over every value and the planner formats every key as `T%d`, so a placeholder entry for a hidden tab breaks both, and `UI/LayoutEditor.lua` reads a present entry as "scanned, capture it" and would record an empty template for a tab it currently declines with an accurate message. Three states, not two: nil means no scan has finished and nothing may be concluded; an empty list means a scan ran and saw no tab, which the planner acts on; a populated list is the filter. The list is copied out of `scanState` rather than shared, which no mutation can currently observe (`resetScanState` allocates a fresh table) and is hygiene rather than a fix.
- **src/Categories.lua** — Item classification via WoW classID/subclassID
- **src/Dedup.lua** — Deduplication engine (occurrence-based hashing, fuzzy matching, event count metadata, count-based cleanup)
- **src/Ledger.lua** — Transaction recording from GetGuildBankTransaction API. Also `GBL:GetTabName(tab, fallback)`, **the one place a bank tab is named for a LIVE reader** (#236), in four steps: the live name from `GetGuildBankTabInfo`, then a session cache of every name this client has read, then the caller's stored name, then `Tab N`. **The cache is what makes the fix work where it is needed**: `BackfillTabNames` in this file says the live read "only works while the bank is open", and the Restock tab is worked at the auction house, so the live branch answers nothing there; a remembered name is a reading rather than a guess, and it is per session so a rename is picked up on the next bank visit. The stored fallback covers the window before the bank has been opened at all. It is type-tested and its `|` is escaped, because `copyTab` passes `tabs[].name` through verbatim and `Validate` never looks at it, so a peer's layout reaches `SetText` with whatever it likes. Read by the record builders, by the Restock group heading and by the Layout tab's per-tab heading, which had its own copy of the rule until #236. **Historical records are the deliberate exception**: `CreateTxRecord` snapshots `tabName` at the transaction, and `UI/LedgerView.lua` renders that frozen string, so the Transactions list can show two names for one tab after a rename. That is a record of what the tab was called then, not a namer that drifted
- **src/Fingerprint.lua** — Dataset fingerprinting (djb2 hash, XOR aggregation, 6-hour bucket hashes); plus the bounded SYNC_REQUEST manifest (`BuildRequestManifest` splits a bucket table into the newest 50 buckets verbatim and up to 8 coarse spans, `FoldBucketRange` folds a span with order-dependent djb2 rather than XOR). The bucket-hash cache has three accessors beyond `GetBucketHashes`, because the sliced serve chain (#115) computes the cold path itself and cannot reach a file-local: `PeekBucketHashes` (cache when warm, nil when cold, never computes; `HandleHello` reads it), `_FreshBucketHashes`/`StartBucketHashScan` for a resumable walk, and `_StampBucketHashes(guildData, map, count)` to install the result. The cache keys on the `guildData` table identity as well as the record count, which is stricter than `GetDataHash`: a count-only key collides across two guilds in one session, and this map decides which records get offered.
- **src/ItemCache.lua** — Lazy async item info cache (GetItemInfo + GET_ITEM_INFO_RECEIVED for synced records)
- **src/Sync.lua** — Guild-wide sync via AceComm (HELLO/SYNC_REQUEST/SYNC_DATA/ACK/BUSY/LAYOUT_REQUEST/LAYOUT_DATA protocol, epidemic gossip propagation, concurrent send+receive, free-agent pairing, hash-gated HELLO reply suppression, fingerprint-based delta sync, bounded sessions with whole-bucket slicing and per-target tranche rotation, per-peer BUSY cooldown, NACK backoff, combat/zone guards, bidirectional sync, bank-layout advertise-and-pull). Serving a request prepares across frames on a token-guarded `C_Timer.After(0)` chain of seven resumable stages (`prepStages`/`prepStep`) at `SYNC_PREP_RECORDS_PER_TICK = 1500`, with a `SYNC_PREP_TIMEOUT = 30`s watchdog; see the sliced-serving bullet under Sync subsystem notes for what must not be undone.
- **src/BankLayout.lua** — Per-guild saved bank layout templates (display/overflow/ignore tab modes with per-item slot counts and stack sizes); validation (at least one overflow tab from schema 2 / #57, optional numeric `overflowPriority` on overflow tabs with NaN rejected, no duplicate items across display tabs, ≤98 slots); `OrderedOverflowTabs` returns the overflow tabs in routing order (sort key `overflowPriority or tabIndex`, tabIndex tiebreak, total on unvalidated drafts), shared by the planner, `PrintSortPreview`, and the LayoutEditor fill-order label so the three never drift. `PrintSortPreview` subtracts `plan.unviewableOverflowTabs` from it before printing `Overflow tabs:` and names the removed ones as ` (not in scan: 5)`, so the breakdown lists what the sort will use rather than what the layout declares (#137); it subtracts rather than reading `plan.overflowTabs` because the planner's invalid-layout early return leaves that field empty, and this command is what someone runs to diagnose an invalid layout. Also: capture-from-snapshot; stock reserves storage; guild-wide sync via `BuildLayoutPayload`/`AdoptRemoteBankLayout` (advertise-and-pull, last-writer-wins on `bankLayout.updatedAt`). **`CaptureTabLayout(tabIndex, previousName)` snapshots the tab's name from `GetGuildBankTabInfo` once and nothing refreshes it**, so a rename in the guild bank leaves every synced copy carrying the old one; since #236 that field is a fallback for display rather than the name, and every reader goes through `GBL:GetTabName`. **The capture is its only writer, so it never overwrites a good name with nothing**: an empty live name counts as none, and `previousName` (the LayoutEditor passes the draft's) is kept instead, or a capture taken while the client could not name the tab would sync the loss guild-wide. The mode dropdown carries the name across its replacement of the tab table for the same reason. Re-stamping the stored names on Save is deliberately not built: it would write into synced state, which bumps the cursor and reaches every peer under last-writer-wins, on a reading of what `GetGuildBankTabInfo` answers for an unnamed tab, for a tab the rank cannot view, and before the bank has been opened, which nobody here has recorded (the 2026-09-17 rule)
- **src/SortPlanner.lua**: Pure-function move planner: given a bank snapshot + layout, produces deterministic ordered op list (split/move) to reshape bank. Assign-then-schedule algorithm: Phase 0 pre-merges same-item partial stacks across the overflow space (#145: every usable overflow tab is one contiguous space in `OrderedOverflowTabs` routing order, the first tab being virtual slots 1 to 98, the next 99 to 196, and so on), walking it as virtual slots (two-pointer pour up to the per-item max stack size from ItemCache or an opts.maxStackByItem override) so the space is compacted to its minimum slot count BEFORE any routing happens; a pour crosses tabs when the run does, and `diag.phase0CrossTabPours` counts those. The receiver is the larger partial (the earlier one on a tie), not the earlier one outright, so a pour can carry stock backwards in the order and Phase 4 then brings the merged stack forward: one item pooled across the boundary can cost a cross pour and a cross pack move, which is why `merge=(cross=)` and `pack=(cross=)` are counted apart. Phase 1 builds demands (slotOrder-pinned + items.slots extensions that right-extend then left-extend to keep each item's group contiguous), assigns each demand to the best source (same-tab direct → overflow → cross-tab; largest-count first within each tier; keep-slot harvest protection), and routes leftover supply to overflow via a capacity-aware pickOverflowSlot that runs the four tiers once over the overflow space in routing order (#145 reversed #57's tab-major walk, which ran all four tiers in one tab before any tier in the next: now a same-item partial in a later tab is topped up before a fresh slot opens in an earlier one, and a run continues from the last slot of one tab into the first of the next, so tiers 2 and 3 read across the boundary), the tiers being (1) topping up an existing same-item partial slot, then (2) right-extend, (3) left-extend, (4) first-empty; a single supply may split across multiple destinations, tab boundaries included, until consumed or unplaced. **Tiers 2 to 4 hold a take to one stack (#151)**: tier 1 already capped at the destination's capacity, but the three that open a fresh slot returned the caller's whole remaining supply, so an oversized supply landed there as one illegal stack. The three share one exit now and the cap sits at it, with `m >= 1` as the test (a max stack of 0 or nil is unknown, and a cap of nothing would place nothing and call the tab full), and a deferred whole stack (#146) stops deferring once a clamped take has left a partial behind, or its remainder opens the second partial the deferral exists to prevent. No real bank or bag slot holds more than a stack, so the clamp is unreachable from live input; `diag.overflowClamps` counts each held take and a WARN `  overflow clamp: N take(s) held to max stack` continuation says so if a fixture or a scanner change ever produces one. **The clamp covers this one producer and no other.** The fresh-placement branch of `canExecute` and `applyOpToState` does not compare `op.count` to the max stack, so the same impossible input still lands whole through Phase 1A (a `perSlot` of two stacks or more, which is #150's ground), `findPivot` parking a blocker, and Phase 4 packing; that gap is recorded on #168 beside its siblings. `spec/sortplanner_spec.lua`'s `applyPlan` holds a fresh placement to the ceiling as well as a merge since this change, so any of those producers emitting one reds every fixture that runs its plan through the simulator. **Tier 1 is skipped for a whole stack while another whole stack of its item is still behind it in the walk, and within one source (all the bank tabs as one source, then each bag) whole stacks are walked before partials, so a whole stack in tab 5 spills before a partial in tab 3 (#146).** Topping up from a whole stack splits it and leaves a remainder that is itself a partial, so the next whole stack split into that one and the odd remainder walked through every stack of the item: eleven ops for six stacks in the 2026-09-07 capture. The LAST whole stack still tops up, which lands the remainder at the tail of the run in one split and leaves the run canonical for Phase 4. A deferred stack that no overflow tab can take whole tops up after all: with nothing free the remainder cannot open a new partial, so that cannot restart the cascade, and skipping it stranded the room a second tab's partial still had (Phase 0 merged within a tab then; since #145 it pools across the space, so that reason is gone and the second one keeps the branch) and spent a deposit on a top-up a bank stack should have made, both caught in review. The walk sort's final key is the supply index, which keeps the order total and the walk deterministic, and the old slot order between stacks of the same kind is pinned. Neither the pure form of fix (a) on the issue (a whole stack never tops up) nor a whole-first walk alone gets there: the first leaves a whole stack after the partial, which Phase 4 cannot reorder at all today (#147: a same-item destination refused for max stack is never classified as stuck, so both stacks come back `cycle-no-pivot` with zero ops and the residual repeats every pass), and the second still cascades into a partial that was already in the tab. Phase 2 schedules moves via a greedy feasibility loop and breaks swap cycles with a pivot slot (same-tab empty preferred, overflow fallback). **The stuck scan reads `canExecute`'s reason rather than comparing itemIDs, and a `max-stack-overflow` refusal counts as stuck only when the assignment carries `pack = true`, which only Phase 4 sets (#147).** The scope is the whole finding: on a Phase 4 packing assignment that refusal means two stacks of one item must exchange positions and a pivot settles it in three ops, while on any non-packing assignment (the guard is `a.pack`, so Phase 1B spills are covered by it too) it can only mean the layout's `perSlot` exceeds the item's max stack, since Phase 1A takes `min(perSlot - filled, available)` against a `filled` capped at `perSlot`, 1B spills are capacity-tracked, `findPivot` never adds to a demand slot, and `Validate` checks only `perSlot >= 1`. Pivoting there would empty the demand slot, fill it, and plan the identical pair again next pass. That case stays a zero-op residual and is spec-pinned as such. **The loop is bounded by `GBL.SORT_PIVOT_BUDGET` (500), overridable per plan by the test-only `opts.pivotBudget`, and the budget exit now records what it drops** as `cycle-budget-exhausted` and clears it (#138). **`diag.phase2CycleAborts` counts abort EVENTS and `diag.phase2StrandedAssignments` counts the assignments they gave up on (#165)**, rendered as `P2 pivot=%d(abort=%d,stranded=%d)`. They were one field under the first name, incremented once per remaining assignment at all three abort sites, so one cycle abandoning eight pending assignments reported itself as eight aborts. `scripts/audit-sessions.lua` parses the term without a closing paren so both forms still read, and its `phaseZeroAbort` measure means the same thing across the change, since the counter only moves inside an abort path and zero of either is the same event. Note the budget site was the only one of the three with a spec pinning its count: a mutation deleting the increment at either no-pivot site survived the whole suite, and a raise-probe proved both are reached, by four #147 and #143 fixtures that assert other things. Both halves are load-bearing: without the record the sources stay unflagged and Phase 3 sweeps to overflow the very stacks the plan gave up on, and without the clear Phase 4's own run of the loop picks the stale assignments up and moves stacks the plan already reported unplaced. A spec pins that no op ever sources from a reported slot. Phase 3 sweeps stragglers using the same multi-destination overflow routing. **`opLabel` is the only thing that writes `op.op`, and all three op producers route through it (#161).** The Phase 3 sweep used to hardcode `"move"` while its count came from tier 1, which caps a take at the destination partial's capacity, so a sweep into a same-item partial described itself as moving a stack it only took part of. The pivot hardcoded it too and was right by construction (its count IS `blockerSlot.count`); it goes through `opLabel` anyway, because the value is one writer rather than three sites that agree by inspection. Call it BEFORE `applyOpToState`, or the label inverts. Nothing on the execution path has read the field since #169, so what this protects is `UI/SortView.lua`'s preview and progress rows and the executor's per-op sort-log line. Reaching that sweep branch at all is a three-way squeeze, which is why it had no fixture for so long: Phase 1B hands every non-overflow supply either an assignment or a `recordUnplaced` at its own slot and every Phase 2 abort flags its source, so the only producer of an occupied, undemanded, unflagged display slot is `findPivot` priority 1 parking a blocker; that pivot needs the blocker's own spill to have failed, so overflow was full for its item; and the label is only wrong if tier 1 has capacity again by Phase 3 and less of it than the swept stack needs, which `rebuildOverflowSlotInfo` supplies by re-reading state after Phase 2 drained a slot of that item. The `op labels (#161)` fixture in `spec/sortplanner_spec.lua` is the only thing in the suite that gets there, and every `phases:` line in `docs/sort-logs/` still reads `P3 sweep=0`. Phase 4 packs the overflow space into one deterministic contiguous run from virtual slot 1 sorted by (itemID ASC, count DESC, virtual position ASC), so a stack moves between real tabs when its rank crosses a tab boundary (#145); partial-stack merging happens earlier in Phases 0/1B. **The space is internal to `PlanSort` (#145, v0.39.17).** `V = #overflowTabsOrdered * MAX_SLOTS`, `vToReal(v)` and `realToV(tab, slot)` sit beside the #181 walk; Phase 0, the tiers and Phase 4 run over `v`, `vToReal` is applied at every emit, and `pickOverflowSlot` and `notePlacement` keep their real-slot signatures, so nothing outside the function and no op, deficit, unplaced entry or log line ever sees a virtual index. `unplacedSlots` stays keyed by real slot and Phase 4 maps through it per virtual slot. `findPivot`, Phase 2, Phase 3 and `overflowStackOrder` did not change; the comparator's third key is the virtual position under its old name. **The cost model, settled at the re-audit against the 2026-09-16 estimate.** That estimate carried #140's 146-op figure forward and doubled it for a 196-slot space; the stay-put rule below means a run of interchangeable stacks whose target range shifts by one moves ONE stack, the one that fell outside the new range, so a stack inserted ahead of a run costs one move per later run, not per later stack, and the first sort after #145 costs one move per run whose range moves across the boundary. Pinned by the boundary-split spec (a 97-stack identical run plus one inserted stack packs in three moves, one pivot included) and measured by two new terms on the `phases:` line, `P0 merge=N(free=,cross=)` and `P4 pack=N(cross=)`, present at zero because the brackets are unconditional. Bounding Phase 4 beyond that is a contract change for the Sort rework design pass. **The full-space limit.** A space with no free slot cannot be reordered: every Phase 4 cycle needs a pivot, none exists, so the pack aborts as `cycle-no-pivot` and the residual repeats until a slot frees. A full tab had the same limit; one space widens the cases that hit it, since bringing a stack forward into a full earlier tab needs a free slot somewhere. The #146 two-tab spec pins it deliberately, with both tabs at 98/98 after its spill. The first converged bags-off sort after this lands is the after capture: its final replan should read `frag=0 extra=0 partials=51 items=53` on the baseline bank with no `overflow split:` line, and its `cross=` counts are the cost measurement. **A slot Phase 2 gave up on is excluded from the packing entirely (#143): it is skipped when the stack list is built, and the rank-to-slot target list skips it too, so the run closes around it and the stack the plan reported unplaced is never shoved aside.** The producer is a Phase 2 abort on any pending assignment whose source is an overflow slot, and note that both aborts and the budget exit record EVERY remaining assignment rather than only the stuck one: an ordinary overflow-sourced demand fill (source tier 2) that is merely still pending when an unrelated cycle gives up is flagged too. The reachable fixture is the over-stack refusal above, because it strands an overflow slot while the rest of the tab stays free; that is why the branch had no fixture for so long. The fix is skip-and-reserve rather than packing the slot like any other, since an idempotent `recordUnplaced` would change what `_BagStays` sums. **Within a run of stacks sharing an itemID AND a count the assignment minimises movement rather than following the comparator's origSlot rank (#140, v0.38.1): a stack already inside the run's slot range stays put** (the range being the run's target slots, which stopped being its rank indices at #143 and became virtual slots at #145, so a run straddling a tab boundary does not churn at it). Those stacks are interchangeable, so a move between two of them has no observable result, and ranking them by origSlot made the target depend on current positions, which executing the plan changes. A pass that ended early therefore re-aimed the rest of the plan instead of shortening it, the replan came back larger than the work that remained, and the executor's non-decreasing rule stopped the sort with a residual. The fixture shape is the whole finding: a tab of DISTINCT items never reproduces it, because the comparator settles on itemID or count and never reaches the origSlot tiebreak, so a repro needs many stacks sharing both. `count` in the run test is load-bearing and is pinned by three existing packing specs. Hard max-stack invariant: `canExecute` and `applyOpToState` refuse same-item merges that would exceed the per-item maxStack (looked up via the same getMaxStack closure as Phase 0/1B), so the planner cannot emit a plan that depends on illegal in-state over-stack accumulations (a merge; a fresh placement of a stack that is already over-sized is not checked there, see the #151 note below). Phase 4 cascades that would otherwise over-stack are reordered by the greedy drain or bailed via the existing pivot/cycle paths, the same-item two-cycle included since #147. Items with unknown max stack (cold cache after `/reload`) skip Phase 0 merging and Phase 1B top-ups for that item only, falling back to grouping; a follow-up sort completes the work once item info loads. Repeat sorts are idempotent. Existing stock crosses between overflow tabs only as the space's order requires (#145; before it, never). Reports deficits, unplaced items (with reason code), and the overflow tabs in routing order (`plan.overflowTabs`, with `plan.overflowTab` kept as a first-entry alias). **`opts.coverage` filters the overflow tabs by what the scan could see (#137).** It carries `{ viewableTabs = {...} }` from `GBL:GetLastScanCoverage()`; a declared overflow tab outside it leaves the routing order and lands in `plan.unviewableOverflowTabs` (ascending by index, always a table, present on the invalid-layout early return too), so `plan.overflowTabs` publishes only usable tabs. The seeding loop is what made this necessary: it hands any declared tab absent from the snapshot 98 free slots, and the scanner omits a hidden tab exactly as it omits an unscanned one. **Every production caller supplies it, `PrintDeviations` included** (`src/Core.lua`), and that last one is the trap: its own output reads `demandMap` only, so it looks exempt, but `PlanSort` writes its plan line to the sort log whatever the caller does with the result, and the Sort tab runs the command after every executed sort. Without coverage there, one capture carries the run's filtered plan and then an unfiltered one routing into the tab the run skipped. It passes coverage and deliberately not bags, since bags cannot change a line it prints and a bag scan is not free. **Absent coverage means no filter**, which is what keeps the fresh-layout case working and what every pre-#137 caller and spec relies on; an EMPTY `viewableTabs` is not absence, it is a scan that saw no tab, and reading it as absence puts a client with no visibility back on the seeding path. When a layout declares overflow tabs and none survives, the unplaced reason is `overflow-unviewable` rather than `no-overflow-defined`: the two need different actions from the player (a rank change against a layout edit), and both the Phase 1B spill and the Phase 3 sweep read one computed `noOverflowReason` so they cannot drift. The plan line gains ` unviewable:T5,T7` or ` unviewable:none`, present whenever coverage was handed in, on the #139 rule that a term's presence says the input was there. `SummarizeSortPlan` appends one line per hidden tab AFTER its "no moves needed" fallback, and `PrintSortPreview` skips its own empty-plan early return when a tab was hidden, or it would answer the case this exists for with "every demand is already satisfied". **Bags are an optional source-only input (#139)**: `opts.bagSnapshot` carries `ScanBags` output as negative pseudo-tabs and is deliberately NOT part of `snapshot`, so tab classification, the `perTabOccupied` breakdown and `BankLayout.Validate` never see one. Admitted slots are filtered to the union of display-tab `items` keys and merged into `bank` between the overflow-ensure loop and the state deep copy, which is `bank`'s only consumer. Bag supplies are appended AFTER the `tabOrder` walk rather than joining it (a negative key would sort to the front and put deposits ahead of bank leftovers in the spill), and `findBestSource` gives them tier `p = 4`, below every bank source, because shuffling inside the bank is free and a deposit is not. - **src/SortExecutor.lua** — Executes a plan fire-and-forget on a self-rescheduling `C_Timer.After(CADENCE=1.0s, pumpOne)` loop: each tick clears a stuck cursor, issues the planner's next op via `issueOp` (the WoW-API-mandated `SplitGuildBankItem`/`PickupGuildBankItem` src + `PickupGuildBankItem` dst sequence), clears the cursor again if the place left an item on it, advances `state.opIndex`, and schedules the next tick. There is no per-op confirmation, no timeout cascade, and no `state.waiting`; correctness comes from convergence, not per-move proof. The two reads left are the source lift's own and the cursor check straight after it, and both look forward rather than back: `liftFromBank` and `liftFromBag` decide a partial take from what the slot holds and refuse an op the slot cannot satisfy, then the guard confirms something actually reached the cursor before the destination half runs. Nothing checks an op once it has completed. When the op list is exhausted, `state.pumping=false`, the executor waits `SETTLE_DELAY=3.5s` (above the worst observed 3.3s deposit latency) so the last deposits commit, then runs `endOfPass`: `StartFullScan` → poll `scanInProgress` (`SCAN_WAIT_TIMEOUT=10s`) → `GetLastScanResults` → `PlanSort(snapshot, state.layout)`. If the new plan is empty → finish (clean); if it is non-empty but ≥ the previous pass's op count → finish (converged, residual reported, no infinite loop); if `state.passes ≥ MAX_PASSES=5` → finish with the residual; otherwise `startPass(newPlan)`. `state.layout` is required for auto-rerun and is threaded by SortView via `opts.layout = self:GetBankLayout()`; if nil, the executor finishes after one pass rather than re-planning to nothing. Bank-close abort is driven by Core (not a self-registered event, which would shadow Core's handler under AceEvent's one-callback-per-object rule): `GBL:OnBankClosed` calls `GBL:_SortExecutorOnBankClosed` to abort a running sort; `pumpOne` also re-checks `IsBankOpen()` each tick as a backstop. The executor registers no bank events of its own (the pump issues no event-driven confirmation, so there is no `GUILDBANKBAGSLOTS_CHANGED` handler to misfire on our own moves). A frame-hitch sampler (a single reused OnUpdate frame; `recordHitch` is pure and unit-tested) records inter-frame gaps so a capture shows whether the pump kept the render loop responsive. A stall watchdog (`C_Timer.NewTicker(5s)` running `checkStall`) re-kicks `pumpOne` when `state.pumping` AND `now - state.lastProgressAt > CADENCE + STALL_SLACK=6s` (the lost-frame-timer mechanism behind the historical op-88 hang), bumping `state.pumpToken` so a late original timer no-ops rather than double-issues. `finish` emits a per-run summary (passes, ops issued, residual, avg s/op, cursorStuck, stalls, rescans, plus `skipped=N` and its histogram when any op was refused), a hitch summary line, and a final ping, then calls `ClearCursor` + `stopHitchSampler` + `stopStallWatchdog`, clears `state`, and invokes the onComplete callback with `result = { ok, reason, done, failed, total, replans, passes, ... }` — that result shape is the SortView contract along with the `GBL_SORT_PROGRESS` message phases `start`/`step`(opIndex)/`planupdated`(plan)/`finish`. **Every field on that message means what it says, which took #162 to make true.** `issued` (not `done`) is `state.totalIssued`, because the pump cannot prove a move landed and only `finish` knows the residual, so `finish` attaches the real `done`/`failed` itself from the same two locals the `result` table uses; before that the tab's completion line and the chat print reported two different numbers under one word. `refused` is `state.skippedOps` and used to be `state.cursorStuck`, which counts destination pickups that SWAPPED rather than placed and is therefore a successful move; `cursorStuck` is still on the payload under its own name. **A `step` carries the PREVIOUS op's outcome** as `issuedOpIndex` or `failedOpIndex`+`failedReason`+`failedDetail`, stashed on `state.lastOutcome*`. The emit fires before `issueOp`, so this op's outcome is not knowable yet, and a second emit after it would have to mark one index both current and settled; riding it one tick forward costs no extra message and leaves exactly one row current with the settled run behind it. Three consequences to keep. `finish` carries the stash out, because the last op has no following step. `startPass` clears it and the `planupdated` emit carries no outcome field, both needed, because a new plan renumbers every row. And reason and detail stay apart on the wire, because the sort log's own `why` string already brackets the detail and a row rendering that would nest parentheses. The producer guarantees `opIndex` never equals either outcome index, which is what makes the consumer's mark order free; it is spec-pinned, because a mutation reversing that order survived. **`src/Ledger.lua` `RescanTransactionLogs` calls `GBL:_sortNoteRescanTick` while a sort runs, and until #165 the bullet here claimed that made the summary count rescans that competed with the pump.** It could not: `ExecuteSortPlan` stops the periodic rescan for the run's duration, so the only remaining caller is the executor's own 15-op flush, which then notes itself, and `rescans=N` was `floor(totalIssued / 15)` in every capture this repo holds. The term is `flushes=` now and the note is the one place either figure is counted, **deliberately in the callee rather than at the flush call site**: `RescanTransactionLogs` returns early on a closed bank and on missing guild data before it reaches the note, so a counter at the call site records an intent, which is #90's `reply=sent` under another name. A genuinely competing rescan is still reachable through one path the stop cannot cover, the Auto re-scan checkbox ticked mid-sort on a run that began with the rescan already off (there was nothing to stop, so `rescanWasActive` is false and no flush fires either); `state.inOwnFlush` tells the two apart, the first external tick is named once at WARN, and `extrescans=N` rides the summary only when non-zero. The old code logged the first 40 and every one of them was the sort's own flush. To stop the periodic rescan from starving the pump (its `numTabs+1` synchronous `QueryGuildBankLog` burst hitches the main thread every ~3s and stretched per-op time from 1s to 3-4s in-game), `ExecuteSortPlan` captures `state.rescanWasActive = GBL:IsPeriodicRescanActive()`, stops Ledger's rescan via `GBL:StopPeriodicRescan()`, and `finish` restarts it via `GBL:StartPeriodicRescan()`, which self-guards on `bankOpen`, `_initialScanComplete`, `rescanEnabled` and already-active, so a bank-close exit safely no-ops. **The `Sort: resumed the periodic rescan` line reports the outcome and not the attempt (#165)**: `OnBankClosed` clears `bankOpen` before aborting the sort, so on that path the restart does nothing and the old unconditional line claimed a resume that never happened. It reads `IsPeriodicRescanActive()` after the call, which covers all four guards without restating any of them, and stays silent otherwise because the abort reason is already on the summary line above. To keep capturing without overflowing the bank's ~25-entry per-tab log, `pumpOne` calls `GBL:RescanTransactionLogs(function() end)` every `TRANSACTION_LOG_FLUSH_OPS=15` issued ops (gated on `state.rescanWasActive` so a user-disabled rescan stays off). **Bag deposits (#139)**: an op with a negative `srcTab` has its source half lifted by `liftFromBag` through `C_Container` instead of `PickupGuildBankItem`; the destination half is unchanged. `liftFromBag` refuses a slot that is gone, locked, holds a different item, or holds too little, takes exactly `op.count` by splitting whenever the slot holds more than that (decided from what the slot holds NOW, not from the plan-time `op.op`, because a stack the player topped up between Preview and Execute would otherwise be deposited whole and the destination was sized for `op.count`), refuses as `no-api` rather than falling through to a whole-stack pickup when a partial take is needed and `SplitContainerItem` is absent, and `issueOp` returns false and stops **before** the destination pickup, which is the load-bearing ordering: `PickupGuildBankItem` on an empty cursor does not place, it picks the destination slot up, so falling through after a refused source would harvest an innocent bank stack. **The source-lift guard is the bank half of #169's fix and it took three releases to land right.** The bank branch had no equivalent of `liftFromBag`'s refusals: a bank source that was gone, locked, or read stale-empty put nothing on the cursor, fell through, and the destination pickup harvested a stack the plan never named. So `issueOp` checks the cursor after either lift and returns `false, "lift-failed"` before the destination, which also covers the failures no pre-check can see: a split the server refuses, a slot locked between the read and the call. A client that cannot answer keeps the old behaviour rather than refusing every op, because an unreadable cursor is not evidence that the lift failed. **The predicate is `GetCursorInfo()`, never `CursorHasItem()`, and that is a measurement rather than a preference.** v0.39.5 gated it on `CursorHasItem()` without once watching it run against a guild bank cursor; in game it refused every op attempted (30 then 5, across two hand-cancelled runs of a 207-op plan, 0 issued either time), and v0.39.6 withdrew it and shipped `probeAfterLift` in its place. The 2026-09-17 capture (`docs/sort-logs/2026-09-17-cursor-predicate-outage-and-probe.md`) then ran 238 bank lifts that all demonstrably succeeded, since the bank converged and the replan came back empty, and read `GetCursorInfo [item:238], CursorHasItem true=0 false=238`. **The same capture refuted the signal this project had twice written down as authoritative.** The probe deliberately led with source drain, on the standing finding that `PickupGuildBankItem` updates the client's slot view optimistically; it read `src drained=0 not-drained=238`, and 162 of those lifts had their source tab selected at the time, so the view-gating caveat does not cover it. The slot API does not see a lift within the same frame, and the optimistic update is at the display layer. Drain stays authoritative read across frames, which is what `endOfPass` relies on; the counter is gone from the probe and must not come back. **The guard carries a fuse, which is what the outage bought.** `LIFT_GUARD_FUSE = 5`, exported as `GBL.SORT_LIFT_GUARD_FUSE`: once the guard has refused that many ops in a run **without ever once passing**, it disables itself for the rest of the run, logs a WARN, and the probe line gains ` guard=disabled`. The arming condition is "never passed" and not the count alone, because a guard that has demonstrably worked and then starts refusing is seeing real failures, and standing down there would be the harvest bug under another name. It trades a harvest no capture has ever recorded against an outage that has. #191's ledger inherits that trade: under a blown guard a fallen-through op's destination is recorded like any other write, so a later bypassed lift from it can fall through again, and the accepted harvest can chain; gating the write on the fuse was considered and declined on the same reasoning, since a blown guard is a blind predicate whose lifts are in fact landing, and the ledger is what keeps those runs converging. The probe line's ` guard=disabled` is the flag either way. **The rule the outage produced: never gate a safety action on a predicate whose real behaviour has not been observed**, with the corollary that a verification expires, which is the whole reason the fuse exists. **The pre-op `ClearCursor()` is unconditional**, the second casualty of the same blind spot: it and `cursorStuck` were both gated on `CursorHasItem`, so for a bank item neither ever fired, and the `cursorStuck=0` in every capture this repo holds was never evidence of a clean cursor. Both read `cursorLoaded()` now. The unconditional clear is also the recovery path for the op before it, since a client will not pick a second item up while one is held. **`bagOpsIssued` is incremented past the guard rather than at `liftFromBag`'s return**, because a bag source can now be refused at two places and counting at the first makes `Sort bags: N deposit(s) issued` count deposits that never reached a tab. Refusals from both source kinds count into `state.skippedOps` and `state.skipReasons`, surfaced on the run summary as `skipped=N` with a sorted reason histogram, absent at zero; the bag counters stay separate so the `Sort bags:` line keeps its meaning and the run total sits at or above it. **`liftFromBank` is the bank half of that pair (#169), and it reads like `liftFromBag` on purpose.** No slot refuses as `empty`, a slot holding less than `op.count` as `short-stack` with the count as detail, more than `op.count` splits for exactly `op.count`, and exactly `op.count` is taken whole (what a real client does with a split whose count equals the stack is not recorded anywhere here, so the pickup is the branch whose shape we know). **It reads `op.op` in exactly one case** (the stale-source bypass below, #191); everywhere else the slot decides, which is what makes a mislabelled partial harmless at execution and demotes #161 to a correctness-of-plan issue outside that case. Two checks `liftFromBag` has are deliberately absent: `locked` and `item-mismatch`. A bank slot's locked flag and item link come through the same view-gated cache as its count, and a stale-locked read would refuse an op that would have worked while the cursor guard already covers a slot that is genuinely locked. **The count had the same exposure in the low direction and it took #191 to see it**: the guard compensates for a read that is stale HIGH (the lift finds nothing), and nothing compensated for one that is stale LOW (the pre-check refuses a lift that would have worked). **The stale-low producer is the run itself (#191, v0.39.16).** A tab the client is not viewing answers a slot read as of that tab's last query, so a slot the run wrote earlier in the pass on a tab that is off screen reads whatever it held when that tab was last queried or viewed: the 2026-09-19 capture (`docs/sort-logs/2026-09-19-overflow-baseline-and-unviewed-tab-refusals.md`) refused eight ops in that shape and none outside it, every one a pivot on the overflow tab with another tab on screen, so a three-op pivot cycle lost its third op every time, the replan planned the same cycle, and run A's non-decreasing rule stopped it with 23 ops remaining. The executor keeps `state.wroteThisPass`, a set of `T/S` keys written in `issueOp` PAST the cursor guard (the `bagOpsIssued` rule: a refused op reached no destination) and reset in `startPass`, because every pass follows a full scan that re-queries every tab. `liftFromBank` hands a source in that set whose tab is not `GetCurrentGuildBankTab()` to `liftPerPlan`, which does not judge the count: `op.op == "split"` takes `op.count` through `SplitGuildBankItem` and anything else takes the stack whole, the read is logged beside it (`Sort op N/M: stale source T7/69 (written this pass, viewing T6) reads 1, lifting 14 per plan as move`, INFO because it is the fix working), `state.staleSourceLifts` counts the attempt, ahead of the lift and the guard, so a bypassed lift the guard then refuses sits in both `stalesrc=` and `skipped=` (that pairing is the reading, not a double count), and the summary carries ` stalesrc=N`, absent at zero like `skipped=`. Two conditions on purpose: a written slot on the VIEWED tab reads live and keeps the pre-check (the player can take from it mid-run), and an unwritten slot off screen keeps it too (nothing can tell a slot the player filled from one the last query missed, and the refusal is what a capture reader wants named). A client whose `GetCurrentGuildBankTab` is absent or answers nil treats every written slot as off screen, in production as in the spec, and the guard bounds that. The proxy is nearly tight: `src/Scanner.lua` is the only production caller of `QueryGuildBankTab`, inside a scan, so mid-run a tab's cache moves only with the view, with the end-of-pass scan, or with a scan the player starts by hand (the Sort tab's Scan bank button, `/gbl scan` and the Layout tab's capture all call `StartFullScan` with no gate on a running sort), after which the ledger over-fires for the rest of that pass and the bypass lifts per plan on a read that would have agreed with it. **This re-couples execution to the label in that one case**, so #161's single writer is load-bearing at execution again and `applyPlan`'s assertion in `spec/sortplanner_spec.lua` is the pin; a `want` of zero stays with the pre-check. The mechanism rests on the mock's `viewGatedReads` model and the capture's pattern, not on a same-slot read both ways: the next capture reads `stalesrc=` against zero `short-stack`/`empty` refusals on written slots, and a `lift-failed` on one of them is the plan being wrong about its own write. In the executor spec `currentTab` is nil (`before_each` queries no tab), so every self-written bank source in a non-gated multi-op fixture takes the bypass; the 2026-09-19 survey found none besides the #191 fixtures. A refusal is ordinary rather than an error (the plan is a snapshot and the player can move things mid-run), so it is counted, named at WARN with its slot, and left to convergence. **The refusal vocabulary is source-agnostic where it can be**: `empty`, `short-stack` and `no-api` come from either lift and `lift-failed` from the guard that covers both, while `no-bag`, `locked` and `item-mismatch` come only from `liftFromBag` for the reason above: `liftFromBag` returns `false, reason[, detail]`, the WARN reads `Sort op N/M skipped: Bag1/25 <reason>, wanted <count> x <item>` with `short-stack (have 12)` and `item-mismatch (holds it:999)` carrying the detail, and `state.bagSkipReasons[reason]` counts each. A reason is what makes a capture actionable: "skipped" alone cannot tell a player who moved a stack mid-run from a client whose container API is missing. **A refused op is not an issued op**: `state.totalIssued` and the transaction-log flush counter both live under the issued branch, so a run of refusals cannot re-fire the flush and cannot inflate the summary's ops-issued count or its average seconds per op. Only the abort path adjusts `result.done`; the normal path stays `total - residual`. `opts.includeBags` is kept for the whole run in `state.includeBags` and `endOfPass` re-reads the bags via `ScanBags()` for its replan: before this, `ExecuteSortPlan` stored only `opts.layout` and `endOfPass` re-planned with no third argument, so pass 2 would silently revert to bank-only and strand the rest. The snapshot is re-read rather than cached, or it would still show the stacks the pass just deposited. **`endOfPass` rebuilds every opts field the run needs, never carrying one from the opening plan (#137 generalises #139's trap).** It now also passes `coverage = GBL:GetLastScanCoverage()`, from the scan that pass just ran, so a tab that became visible mid-run is picked up on the next pass and a bank-only run is filtered too. Any future opts field belongs in that same block; one added only at `BuildSortPlanOpts` (which builds opts for the Core callers and is never consulted by the executor) is silently dropped from pass 2 onward, which is the exact defect `includeBags` had. `result.bagOpsIssued` / `bagOpsSkipped` and a `Sort bags: N deposit(s) issued, M skipped [locked:1 short-stack:1], still in bags: K (U unplaceable)` summary line report the split, plus `result.bagSkipReasons`, `bagsStillInBags` and `bagsUnplaceable`. The line is written whenever `state.includeBags` is set, including a run that issued no bag ops at all, and is absent entirely when bags are off. The histogram appears only when something was skipped and its keys are sorted, so two captures of the same run read identically rather than in `pairs` order. **K and U come from the LAST replan's `diag.bagSupplies`/`bagStay`, not the first plan's**, stamped into `state.lastBagSupplies`/`lastBagStay` in `endOfPass`: the first plan describes what was in the bags before the run, which is the one number the summary must not report. A run that aborted before any replan says `still in bags: unknown (no replan)` rather than guessing. The start line carries `bags=on|off` from the same flag, so a capture says which mode produced everything below it. **Two limits to read the tail with.** `still in bags` counts only stacks the layout names, so it can say 0 while the player's bags are full of items the layout never mentioned; the plan line's `ignored=` term is where those are counted. And `ScanBags` skips a locked slot, so a bag slot still locked from the pass's own deposit activity is neither planned nor counted by the `endOfPass` rescan: `SETTLE_DELAY` plus the full scan makes that unlikely and a follow-up sort clears it, but a run can in principle report 0 with a stack left behind.
- **src/Restock.lua** — Restock-to-target engine. ## Critical WoW API Facts

- `GUILDBANKFRAME_OPENED/CLOSED` **removed in 10.0.2** — use `PLAYER_INTERACTION_MANAGER_FRAME_SHOW` with `Enum.PlayerInteractionType.GuildBanker`
- `GetGuildBankTransaction(tab, i)` returns **relative** time offsets — compute absolute via `GetServerTime() - offset`
- Must call `QueryGuildBankLog(tab)` before reading transactions; `QueryGuildBankTab(tab)` before reading slots
- Use `GetServerTime()` — never `time()` or `os.time()`
- Use numeric `classID`/`subclassID` via `C_Item.GetItemInfoInstant()` — never localized strings
- `MAX_GUILDBANK_SLOTS_PER_TAB = 98`
- `MAX_GUILDBANK_TABS = 8` (constant — max purchasable tabs)
- Money log tab index: `MAX_GUILDBANK_TABS + 1` (always 9, NOT `GetNumGuildBankTabs() + 1`)
- `GetGuildBankMoneyTransaction` returns type `"withdrawal"` (not `"withdraw"`) — normalize at record creation

Porting the reachable half is exactly how the mock came to model a login and never a logout, so the unreachable branches are deliberate and carry synthetic cases. **`db:_simulateLogout()` strips in place**, so `db.global` becomes the on-disk image, and `db:_simulateLogin()` is the next login over that file; run the pair to model an upgrade, because what AceDB does to a guild ALREADY in the file is a different path from what it does to a fresh one, and the mock had no second path at all before #77. **Absence is read with `rawget`**, never by indexing: a wildcard metatable turns a read into a write, which is also why `removeDefaults` clears the metatable on its first line. Three read-path gaps came out of the same work and one is worth carrying: the vivification used to deep-copy the template, which copies the literal `"*"` key into the new table, so every `guildData.playerStats` in this suite held a phantom player. Seven production sites walk that table with `pairs` (`src/Core.lua:761`, `:813`, `:1045`, `:1243`, `:1704`, `:1751`, `:3014`); **four sit inside migrations, and two resolve every name they find and write it back**, those two being `:761` in `MigrateSchemaV2ToV3` and `:1704` in `RepairPlayerNames`, of which only the first is a migration. The other five are clear-and-repopulate loops that resolve nothing, and `:3014` is `CleanupWithEventCounts`, runtime sync cleanup rather than a migration. One migration storing a resolved phantom is the whole of it, and it is enough. **Nothing went red when it was removed**, which is the lesson rather than a relief: no case had ever asserted what that table contains, only what its own fixture put in it, so an extra key was invisible in both directions. `spec/savedvariables_spec.lua` holds the round trip, and its last describe runs the same defaults through a real AceDB from `spec/vendor/` and compares the file each side leaves behind, because a hand port can only ever agree with itself.
- Test helper: `spec/helpers.lua`
- Pattern: `*_spec.lua`
- **The sync tests are nine topic files, `spec/sync_*_spec.lua`, sharing `spec/sync_helpers.lua`** (#116, split from an 11,900-line `sync_spec.lua`). `Sync.setup()` builds GBL and guildData the way every one of them needs; the three timer-drive helpers and the SYNC_REQUEST payload builder live there too. Grep across `spec/sync_*_spec.lua` rather than guessing which file holds a behaviour: hello, version_gate, request, chunking, send, receive, peers, lifecycle, convergence.

### Wire-contract fixtures

`spec/wire_contract_spec.lua` is the one spec that does not use the serializer mock. **`spec/vendor_helpers.lua` is where a real Ace3 library gets loaded**, by `dofile` (`require` cannot be used: the module names contain a dot, which `require` turns into a path separator), stashing and restoring `_G.LibStub` and `strmatch` around the load. Real LibStub reads the existing global and evaluates `LibStub.minor < 2`, which the suite's mock does not have, so skipping the stash either throws or leaves the mock registry replaced for whatever runs next in the same file. `spec/wire_helpers.lua` is the serializer-shaped API over it and holds no loading of its own since #77, when `spec/savedvariables_spec.lua` needed a real AceDB the same way. The addon's own mixed-in `Serialize`/`Deserialize` are never touched, and neither is its AceDB instance. **`loadVendored`'s third argument generalises the `strmatch` shim**: a global a vendored library reads AT LOAD and production never reads is installed for the load and restored after, rather than becoming a permanent entry in `mock_wow.lua`, which exists to describe the client the addon actually talks to. AceDB needs seven of them, six profile-key globals it computes once at load and `CreateFrame`, because it owns one frame solely to catch `PLAYER_LOGOUT` and the mock's frames have no `RegisterEvent`.

**The libraries come from `spec/vendor/`, not `Libs/`.** `Libs/` is gitignored and fetched by the packager from `.pkgmeta` externals, so it exists only on a machine that has run the packager: CI checks out a tree with none. Committing LibStub (51 lines, public domain), AceSerializer (287 lines) and, from #77, AceDB (797 lines) under `spec/vendor/` is what makes the suite hermetic. `spec/vendor/README.md` carries the provenance. The generator additionally diffs those copies against `Libs/` when `Libs/` is present, so a developer still finds out when upstream moves while the test run stays deterministic everywhere; that check was verified to fire rather than assumed to, and AceDB is the one of the three where it earns its keep, since its vendored revision is dated 2026-09-18 while the other two have not moved since 2022 and 2014.

**No compression in the harness.** LibDeflate is a pure byte-exact codec this addon neither configures nor extends, so pinning it would test LibDeflate rather than GBL, at the cost of vendoring 3,600 more lines. The test is whether this addon configures the library, not how large it is: AceDB is vendored at 797 lines because GBL hands it a defaults block and every claim in `docs/DATA-MODEL.md` section 2 is about what AceDB does with that block, so pinning it pins our defaults. LibDeflate is handed nothing. `estimateRecordBytes` is documented against AceSerializer output, and the compressed size that matters at runtime is measured live as `syncState.lastChunkBytes`.

**The golden strings in `spec/fixtures/wire/*.lua` are frozen and are not regenerated.** They are what a v0.36.x peer puts on the wire, and "an older peer's bytes still decode" is the contract the `MIN_SYNC_VERSION` floor (#74) rests on. A record-shape change (#67) adds cases beside them; it never rewrites them. `spec/fixtures/generate_wire_fixtures.lua` is an authoring aid for new cases plus a check that every committed string still decodes to its hand-written table; it is not a refresh tool.

Expectations are hand-written from `docs/DATA-MODEL.md`, never pasted from program output, because a characterization fixture built from what the code prints can only ever agree with the code. The `serialized` field records AceSerializer output rather than the compressed and encoded channel bytes, so a reviewer can read the diff. Field order inside those strings comes from `pairs()` and is not meaningful: the tests only ever decode them.

`src/Sync.lua` exposes `_StripForSync`, `_ReconstructSyncRecord` and `_EstimateRecordBytes` for this spec alone. They have no production callers and exist because the codec is otherwise file-local and unreachable.

Two format facts worth not rediscovering: AceSerializer escapes space (and control codes, `^`, `~`) to two bytes, and an **unescaped** space is silently dropped on decode, so a hand-typed payload containing `"Test Guild"` comes back `"TestGuild"`. Pipes and colons, which record ids are built from, pass through unescaped, which is why `estimateRecordBytes` holds as an upper bound for records.

## Conventions

- Addon object: `GBL` (local alias for the AceAddon instance)
- **In-game strings are ASCII.** Anything the addon can put on screen stays inside byte 127: chat output, labels, tooltips, audit lines, and `CHANGELOG_DATA`. WoW's default fonts carry Latin-1 and little past it, so an em dash, an arrow or a check mark draws as a blank or a box depending on the font and the client's locale. Symbols used as UI encoding fail worst, because a check mark that does not draw leaves a row whose state is carried by colour alone, which is the triple-encoding failure the accessibility rule exists to prevent. Code comments are exempt: they never reach a player. `spec/ascii_strings_spec.lua` enforces this over the file list in the `.toc`, stripping comments first and decoding decimal escapes, since `"\226\156\147"` is ASCII on disk and a check mark on screen.
- Module registration: use AceAddon modules, not standalone globals
- Events: always check interaction type before acting on `PLAYER_INTERACTION_MANAGER_FRAME_SHOW`
- Timestamps: always `GetServerTime()`, never `time()`
- Item IDs: use `C_Item.GetItemInfoInstant()` for classID/subclassID
- Guard `Enum.PlayerInteractionType.GuildBanker` existence for Classic compat
- Saved variables: `GuildBankLedgerDB` (AceDB), data keyed per guild name. Deliberate exception: `GuildBankLedgerAuditDB` (src/AuditCapture.lua) is a raw account-wide global, NOT AceDB and NOT guild-keyed — it is an append-only diagnostic capture store whose collection unit is the account's SavedVariables file; sessions carry player/realm/guild in their headers. Do not migrate it into AceDB (a second `AceDB:New` also breaks the `MockAce.dbInstance` single-instance assumption in specs).
- **`docs/DATA-MODEL.md` is the record of what is actually stored, and of what is being done about the places the code disagrees with itself.** Read it before answering any question about what is stored, and before changing records, dedup, or the sync payload. The defaults block, the record builders and the live SavedVariables all disagree; every disagreement in the doc now carries a verdict, and the issues are collected under the **Data model integrity** milestone. Two things to take from it before touching anything here. `schemaVersion` defaults to 8 while migrations run to 11, and that is correct: AceDB strips a value equal to its default and hands back the current default on load, so the default IS the stored version of every guild sitting at it, and raising it strands them past migrations 9 to 11 permanently. Both halves are spec-pinned as of 2026-09-24, in two files that fail on different mutations: `spec/savedvariables_spec.lua` round-trips the default through a real AceDB and is what reds if the default is raised (#77, PR #261), and `spec/schema_version_spec.lua` asserts the ladder as a sequence, each rung bumping by exactly one (#76). The sequence assertion is also the only thing that reds if a strict gate is loosened to `>=`, since a guild above a gate is refused by both forms; `spec/core_spec.lua` holds the below-the-rung side. **Both of `OnEnable`'s per-guild walks take one guild at a time under `pcall` since #263**, the ladder in `MigrateAllGuilds` and the dedup pass in `DeduplicateAllGuilds`, because one guild's raise used to abandon every guild after it and then the whole of `OnEnable` below it, silently: AceAddon runs `OnEnable` under `safecall` and neither pass logs anything of its own. Isolating only the ladder moves that failure four lines down, since the corruption class that makes a rung raise reaches `BuildTxPrefix` and `ComputeTxHash` too, and `InitSync` still never runs. A failure is named once per guild per session on the system channel, so a capture is grepped for `Migration failed` and `Dedup pass failed`, and the hash cache is reset in both branches because a raise can leave it warm over ids a half-run pass already rewrote. Nothing in either loop may read the guild table outside the protection, or the isolation has a hole at its own first statement. That work is also why `DeduplicateRecords` no longer writes the version at all: the branch that forced it to 5 was reachable only through a stranded guild, and skipped the rungs beneath rung 5 when it fired. Two limits it left, both filed: #265, two rungs rewrite record ids and never invalidate the fingerprint cache, and #266, a guild left half-migrated reaches sync with `seenTxHashes` keyed on ids its records no longer carry. #266 is a pre-existing defect the isolation widened rather than one it created: the `GUILD_ROSTER_UPDATE` retrigger already re-ran the ladder with sync live, and what changed is that the `OnEnable` path no longer masks it by taking `OnEnable` down. And **unknown keys on a synced record must pass through untouched**: that tolerance is what makes adding a record field free, and a whitelist at intake would turn every future field into a forced guild-wide update. The doc also carries the measured sync-corruption rate (11.66% of everything ever received) and the `syncState.peers` name collision, whose persisted half turns out to have no reader at all.
- **Sync is guild-wide** — all members participate in HELLO/sync, not just officers. Officer rank only gates UI visibility (settings, admin features). Never add rank checks to the sync protocol.
- **Public description sync**: `docs/CURSEFORGE-DESCRIPTION.md` is the source of truth for the CurseForge project page. When user-facing surface changes (slash commands, UI tabs, access control, sync features, planned-feature framing), update it in the same PR. CI emits a `::warning::` annotation on PRs that change feature-surface files (`README.md`, `docs/ROADMAP.md`, `src/**/*.lua`, `UI/**/*.lua`, `GuildBankLedger.toc`) without updating the description; treat it as a checklist prompt, not a blocking gate. Pasting the updated content into the CurseForge web UI is a manual release step until BigWigsMods/packager#187 lands.

## Branch Workflow

`main` is the integration target and is GitHub-protected (PR + `test-and-lint` CI required, merge commits only, force-push and deletion blocked). Auto branch deletion on merge is **on**: `main` is the only permanent branch in this repo, and every other branch is deleted when its PR merges.

### Branches

Every branch is single-purpose: cut from the latest `main`, scoped to one PR, deleted when that PR merges. Follow-up work gets a fresh branch. Branch names are never reused.

- `feat/<thing>` for new features
- `fix/<thing>` for bug fixes that are not urgent
- `chore/<thing>` for maintainer chores, repo-config changes, doc-only updates
- `infra/<thing>` for CI / build / tooling changes
- `refactor/<thing>` for restructuring with no behaviour change (maps to `type: refactor`)
- `hotfix/<thing>` for urgent production-impact fixes (see Hotfix rule below)

`feature/` is retired in favour of `feat/`.

**No long-lived branches.** From 2026-04-27 to 2026-08-07 this repo ran long-lived per-area topic branches: `ui`, `sync`, `layout-sort`, `restock`, plus an `accessibility` lane that was declared but never created. They worked. They are retired because the global rule now allows a long-lived branch only for release maintenance in a project shipping several versions in parallel, and GBL ships one version at a time to CurseForge. All of them were merged and deleted on 2026-08-07. Do not recreate them, and do not read their absence as an accident.

See **Branch lifecycle: trunk-based, delete after merge** in `~/.claude/CLAUDE.md` for the full rule and the agent-side decision rule.

### Rules

- **Scope check before the first commit of every session**: the checked-out branch is not authorization to commit to it. If the intended work does not match the branch's type and slug, cut a fresh branch from the latest `main`.
- **Hotfix rule**: an urgent production-impact fix gets its own `hotfix/<thing>` branch off `main` and ships on its own. Never hold one back to bundle it with unrelated work.
- **Cross-branch rule**: when one feature spans two branches (e.g. a sync change that needs a UI tab), merge the upstream-of-the-dependency branch first, rebase the dependent branch onto the new `main`, then commit the dependent piece. Never PR both simultaneously hoping git resolves the order.
- **Rebase cadence**: cut from the latest `main`, and rebase an open branch onto `origin/main` after any intervening merge. `git rebase origin/main` if conflicts are tame; fall back to `git merge origin/main` if not. `git push --force-with-lease` is fine on your own unmerged branch.
- **Version-stamp cadence (covers CHANGELOG and every other version artifact)**: a branch stamps every version artifact only when opening the PR, in a dedicated stamp commit. Work on the branch leaves all of these untouched and lets `[Unreleased]` accumulate:
    - `VERSION` file
    - `GuildBankLedger.toc` `## Version:` field
    - `src/Core.lua` `local VERSION = "..."` constant
    - `CHANGELOG.md` (the `## [X.Y.Z] - YYYY-MM-DD` header; work lands under `[Unreleased]` until stamp time)
    - `UI/ChangelogView.lua` `CHANGELOG_DATA` table (in-game changelog)
    - This `CLAUDE.md`'s "Current: X.Y.Z" line at the bottom
    - `src/Core.lua` `local DEV_BUILD = ...` constant must be reset to `nil` in the stamp commit. CI rejects any other value via the `Verify DEV_BUILD is nil` workflow step.

  **Do NOT sweep the version string through `spec/fixtures/wire/`.** Those files pin several releases at once on purpose: a v0.36.0 HELLO pair, a v0.37.0 floor-aware HELLO and SYNC_REQUEST, a pre-#67 deposit and a post-#67 one. Each is a frozen recording of what that version put on the wire, and the point is that it keeps saying so forever. A grep-and-replace stamp will try to bump all of them and quietly destroy the cross-version contract they exist to hold. The trap is that it destroys them *silently*: a sweep changes the frozen `serialized` string and its expectation table together, so the suite stays green while the fixture stops recording anything. If a fixture ever needs to change, `lua spec/fixtures/generate_wire_fixtures.lua` reports which committed string no longer decodes to its hand-written table; that is a finding, never a refresh.

  `spec/ui/changelog_spec.lua` asserts that `CHANGELOG_DATA[1]`'s version matches the addon version, so a half-landed stamp fails the suite instead of shipping. If two branches PR with the same target version, the second to merge rebases onto post-merge `main` and its stamp commit bumps to the next patch. The principle is: one version per PR, one stamp commit per PR, never per-commit churn on these artifacts. (This matches the global `~/.claude/CLAUDE.md` "Commit Versioning" standard, which stamps once at PR-open.)
- **Doc-only PRs take no version and no tag.** The objective test is whether the PR changes any file that ends up in the packaged zip. `.pkgmeta`'s `ignore:` list strips `spec`, `docs`, `.busted`, `.luacheckrc`, `.gitignore`, `.claude`, `CLAUDE.md`, `*.md`, `*.sh`, `*.bat`, and `VERSION`. If every file a PR touches is stripped, the packaged addon is byte-identical apart from the stamp itself, and there is nothing to release. Stamping one anyway ships a version whose only user-visible content is the announcement of its own existence. Before v0.37.0 it also cost a forced guild-wide sync break (see Release cost below); now the cost is a contentless update pushed to every auto-updating install, which is still not worth paying. This narrows the global "every merged PR gets a bump and a tag" rule rather than overturning it: that rule's origin (PR #7) was addon-relevant work shipping untagged, which this test still catches. A PR that touches even one packaged file is a normal release.

  **`CHANGELOG.md` is the trap: it ships despite matching `*.md`.** The packager detects a changelog file and copies it back into the package regardless of the ignore list, and also feeds it to CurseForge as the release notes. Verified against the published v0.36.0 zip, whose only top-level files are `CHANGELOG.md`, `GuildBankLedger.toc`, and `LICENSE`; `README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `spec/`, and `docs/` are all absent. So a CHANGELOG-only PR is **not** doc-only. Do not read the ignore list on its own. When a PR sits near the line, settle it empirically: `gh release download <tag> --pattern "*.zip"` and list the archive.
- **Dev-build isolation**: at the start of any branch session that ships protocol-affecting or schema-affecting changes, set `local DEV_BUILD = "<branch>"` in `src/Core.lua`. The runtime `self.version` becomes `X.Y.Z-dev.<branch>` and `GBL:IsVersionCompatible` refuses to sync with production peers in both directions, including the user's own production-version characters on the same account. Since v0.37.0 that refusal comes from the `isPlainSemver` short-circuit rather than the old exact-match gate, which is why that check has to stay ahead of every `CompareSemver` call (see Release cost above). The flag is reset to `nil` in the stamp commit (see Version-stamp cadence above). Local `bash run_tests.sh` is intentionally not gated on the flag so dev iteration keeps working; CI is the enforcement boundary, and `scripts/hooks/pre-push` is the local-clone fast-fail (activate once per clone with `git config core.hooksPath scripts/hooks`).
- **CI cadence**: `.github/workflows/ci.yml` runs on `pull_request` and `push: main` only. Intermediate commits on a branch are unverified by CI. Run `bash run_tests.sh` and `bash run_tests.sh --lint` locally before each commit so the branch stays green.
- **Carve-out from the global "small, focused PRs" rule**: the user's global `~/.claude/CLAUDE.md` "Open Source / Public Repo Workflow" section says "Keep PRs small and focused, one concern per PR." That rule is for external-contributor PRs. For the maintainer's own PRs in this repo, multiple related commits covering one concern is the intended pattern. External contributor PRs still follow the small-and-focused rule.

### Release cost: paid in full at v0.37.0, and only payable again on a floor raise

**Historical, through v0.36.1.** `HandleHello` refused to sync on **any** version difference, patch included, so every release was a forced lockstep guild update and until every member updated the guild was split into non-communicating islands. That cost was per account rather than per character (SavedVariables are account-wide, so a player's alts share one install and one version), but it was real and it was paid by other people. It is why doc-only PRs take no version, why bundling beat a fast sequence of small releases, and why the 103 tags cut between 2026-04-07 and 2026-06-24 were an accumulating bill.

**From v0.37.0 on, `MIN_SYNC_VERSION` replaces it with a range** (`src/Sync.lua`, `GBL:IsVersionCompatible`). Two peers sync when each is at or above the other's advertised floor. An ordinary release now costs nothing: ship a patch and a guild running three different versions keeps converging.

Three things to keep straight before touching it.

- **Raise the floor ONLY for a wire, record-identity or fingerprint break.** Never for a normal release, however large the diff. Raising it re-imposes exactly the lockstep split the floor exists to remove, so the value in the source is a decision about compatibility, not a version number that tracks releases. It moved to `0.37.0` in that release's stamp commit and should sit there until something genuinely breaks compatibility. **Worked example of a wire change that did not qualify: the v0.37.11 request manifest (#108).** It changed what SYNC_REQUEST puts on the wire, and a raise had been cleared for it, and it still did not take one, because the change turned out to be additive in both directions: unknown keys pass through untouched, and the serving side's "a bucket you did not mention reads as hash 0, so send it" rule means an under-described request degrades to redundancy rather than to divergence. The test to apply is not "did the wire format change" but "can either side misread the other into losing records". Where the answer is no, the cost of a raise (a split guild for the length of the adoption window, which for a starvation fix delays the very outcome being shipped) buys nothing.
- **v0.37.0 is the last prepaid compatibility break.** Before it, an id-format change was automatically safe: peers on different versions refused each other, so records built under two `buildPrefix` implementations never met. After it they do meet, and if their implementations disagree both sides accept the other's records as new and the guild's dataset silently duplicates. So an id-affecting change now costs a floor raise, which is why #67 (the tab in the prefix) had to ride v0.37.0 rather than follow it.
- **A peer advertising no `minSyncVersion` falls back to exact match.** That is the correct reading of a pre-v0.37.0 build and it is what keeps the old refusal behaviour testable. A peer sending no `version` at all is incompatible everywhere, which is what lets `HandleSyncRequest` recognise a pre-floor request.

The gate lives at three sites, not one: `HandleHello`, `HandleSyncRequest` (a request never passes through HELLO), and `RequestSync` (the bidirectional check after `FinishSending` reaches it without one, and so does a manual pull). All three call `IsVersionCompatible`. The settings merges in `HandleHello` deliberately sit **above** the gate so a GM's access-control, sort-access or layout change still propagates through a mixed-version window; only record exchange is gated. An incompatible peer gets one HELLO reply per session via `syncState.incompatibleReplied`, not one per heartbeat.

`IsVersionCompatible` short-circuits on `isPlainSemver` **before** any `CompareSemver` call. `CompareSemver` strips `-dev.<id>` by design, so a range test that reached it would read a dev build and its base release as compatible and undo `DEV_BUILD` isolation entirely. Do not reorder those checks.

### What reaches the public CurseForge channel

`.github/workflows/release.yml` fires only on `push:` of a `v*` tag. `BigWigsMods/packager` derives the release type from the tag name: a tag containing `alpha` or `beta` (case-insensitive) uploads as that channel, anything else uploads as a full release, and an untagged run packages as alpha. Three levers follow, in increasing order of machinery:

1. **Do not tag.** No tag, no workflow run, no CurseForge upload, no GitHub release.
2. **Tag with `-alpha` or `-beta` in the name.** Still matches the `v*` trigger and still uploads, but CurseForge files it off the default channel so users are not offered it.
3. **`-d` on the packager.** Skips uploading entirely. More machinery than either of the above and not currently needed.

Recorded as available options, not current practice. The caveat that matters: channel choice cannot change what the maintainer actually runs, because this repo is symlinked into AddOns, so the maintainer's client advertises whatever `main` holds regardless of what CurseForge is serving. Since v0.37.0, sync fragmentation is governed by the floor alone, not by version count; ordinary releases cost update churn, and only a floor raise re-imposes a guild split. Channel choice controls how much of that churn the guild sees.

## Issue and PR labels

21 labels: 6 `type:`, 8 `area:`, one `tracking issue`, and GitHub's 6 remaining defaults. Adopted 2026-08-14 (#73), backfilled in one pass across all 42 issues and all 68 PRs, closed and merged included. Each label's GitHub description carries its own rule, so the meaning cannot drift into someone's head. The contributor-facing version lives in [CONTRIBUTING.md](CONTRIBUTING.md); this section is the maintainer's copy and carries the reasons.

**Invariant, after triage: exactly one `type:` and at least one `area:`.** A second `area:` only where the item has separate acceptance criteria in two places (#44, #52, #77, #93 are the four). An unlabeled inbound issue from an outside contributor is the normal starting state, not a miss: applying labels needs triage permission, so a contributor cannot do it.

- **`type:` mirrors the branch prefixes**: `fix/` and `hotfix/` to `type: bug`, `feat/` to `type: enhancement`, `chore/` to `type: chore`, `infra/` to `type: infra`, `refactor/` to `type: refactor`. `type: documentation` is the exception with no prefix of its own, because doc-only work goes on `chore/` here; it is applied by hand.
- **`type:` keeps GitHub's default wording rather than the prefix wording** (`type: bug`, not `type: fix`). WoW-Economy-Forecaster renamed to match its prefixes; this repo is public and takes outside PRs, so the words a stranger already recognizes are worth more than a literal 1:1 with the branch name. The mapping above is still 1:1 in the direction that matters: every prefix implies exactly one label.
- **`area:` names the subsystem**: sync (Sync.lua, Fingerprint.lua, protocol, peer identity), storage (Ledger, Dedup, records, schema, migrations), sort (SortPlanner, SortExecutor, SortView), restock, layout (BankLayout, LayoutEditor), ui, accessibility, repo (CI, test infrastructure, governance, repo docs). `layout` stays separate from `sort` because #57 and #58 are about what the layout model can express rather than about sorting.
- **`area: repo` is an eighth label beyond the seven designed in #73**, added because three open issues needed it (#51, #73, #77) and about twenty PRs did. That is the rule working: a taxonomy entry is added when an item needs it, never because the set looks incomplete. `area: core` still does not exist, because no issue is core-only today. `src/Core.lua`, `src/Logger.lua` and `src/ItemCache.lua` are unmapped in the labeler for the same reason; they are cross-cutting, so the area comes from whatever else the PR touched.
- **`UI/ChangelogView.lua` and `CLAUDE.md` are unmapped too, and that one was learned the hard way (#128, fixed 2026-08-21).** Both are written by every version stamp, so every release PR arrived carrying `area: ui` and `area: repo` whatever it was about, and the labels were stripped by hand on four consecutive releases (#124, #125, #127, #129) before the rule itself was fixed. The failure is worth telling apart from the config-versus-backfill trap that #112 fixed: that one was two implementations of the taxonomy disagreeing, and diffing them against each other found it. This one is a single internally-consistent rule that fires on a strict superset of what it means, so nothing internal contradicts and only reading the applied labels against what the PR actually changed finds it. Hand-stripping is not a fix: it works until the release nobody remembers to strip, and that one is mislabelled in the record forever. ## Sync subsystem notes

### Protocol / transport

- Sync transport stack is **AceSerializer → LibDeflate → AceComm → ChatThrottleLib → `C_ChatInfo.SendAddonMessage`**. AceComm splits payloads into 255 B wire fragments; a 980 B compressed chunk is ~4 fragments. Whole-chunk loss compounds: at per-fragment drop probability `p`, chunk loss is `1 - (1-p)^n`. Moving from 3 to 4 fragments at p=5% raises chunk loss from 14% to 19%.
- AceComm WHISPER has an empirically ~2000 B reliability ceiling (`WHISPER_SAFE_BYTES` in `src/Sync.lua`). Staying under it is necessary but not sufficient — fragment *count* is an independent reliability factor.
- `ChatThrottleLib.avail` is the **client-side** bandwidth meter only. It does not model server-side per-recipient addon-message throttling that Blizzard's chat server applies to `SendAddonMessage` independent of CTL. A healthy `CTL.avail` can still coincide with server-dropped messages when chunks are issued <1s apart.
- `C_ChatInfo.SendAddonMessage` via `AceComm:SendCommMessage` does not return a useful delivery status — reliability is observed only via ACK/NACK/timeout at the protocol layer. Do not branch on its return value.
- AceComm's progress callback fires per CTL piece; only `sent == totalBytes` indicates "handed to the wire," and only then should the ACK timer start. This is the v0.23.0 contract codified in `SendNextChunk`.

### Name forms quick reference

GBL handles three distinct name forms. Mixing them is a collision risk; each has a dedicated producer and a fixed set of consumers:

| Form | Example | Where it lives | Producer |
|---|---|---|---|
| Qualified `Name-Realm` | `Katorriwl-Stormrage` | `record.player`, `record.scannedBy` (after the `sync:` prefix), all migrations | `GBL:ResolvePlayerName` |
| Canonical peer key | bare for same-realm, qualified for cross-realm | keys of `syncState.peers`, `guildData.knownPeers`, `syncState.peerBusyUntil` | `GBL:CanonicalPeerKey` |
| Bare name | `Bob` | `recentWhisperTargets` keys (chat-system suppression), UI filter inputs | `GBL:StripRealm` |
| Raw network sender | whatever AceComm passes | runtime only; must never be stored without canonicalization | always wrap in `GBL:CanonicalPeerKey` before keying any peer-state table |

Helpers:

- `GBL:NormalizeRealm(realm)`: strips whitespace from a realm portion (e.g. `"Aerie Peak"` → `"AeriePeak"`). Always normalize before equality comparison or persistence.
- `GBL:GetLocalRealm()`: normalized local realm, or `"UnknownRealm"` sentinel when realm APIs are cold.
- `GBL:_isLocalRealm(realm)`: `true` iff realm matches local (raw or normalized). Used by `CanonicalPeerKey` to decide whether to strip.
- `GBL:BuildRosterCache()`: populates `guildData.playerRealms[bareName] → realm`. Two-pass: detects bare-name ambiguity and writes the `false` sentinel when a bare name maps to multiple distinct realms in the roster (so `CanonicalPeerKey` can refuse to guess and keep ambiguous bare arrivals bare).
- `GBL:RepairCorruptedPlayerRealms(t)`: trims hyphen-corrupted realm strings carried forward from a long-fixed code path; called from `BuildRosterCache` on each invocation. Leaves `false` sentinels untouched.

`ResolvePlayerName` priority order: **explicit `playerRealms` arg → current guild's playerRealms → local realm fallback**. There is no cross-guild fallback. Bare names from the bank log are assumed to belong to the current guild, not a guild the user previously belonged to. Migrations pass the per-guild table explicitly via the `playerRealms` arg.

### Code invariants to preserve

- Logging is split across three channels owned by `src/Logger.lua`. Sync code calls `GBL:SyncInfo / SyncWarn / SyncError / SyncDebug`; sort code calls `GBL:Sort*`; system events call `GBL:System*`. The lower-level form `GBL:LogSync(level, fmt, ...)` exists for runtime-computed levels. Each channel is a session-only ring buffer (sync 2000 / sort 3000 / system 500, FIFO from tail; sort is largest so a full sort run stays in the on-demand view). DEBUG entries are dropped entirely unless `db.profile.<channel>.debugChat` is on, which preserves the prior `chatOnly=true` "do not pollute the buffer with per-chunk noise" property without a separate side channel. Chat mirroring is gated by `chatLog` (INFO/WARN/ERROR) and `debugChat` (DEBUG). `GBL:AddAuditEntry(msg, chatOnly?)` is a deprecated shim that routes plain calls to `SyncInfo` and `chatOnly=true` calls to `SyncDebug`. `GBL:GetAuditTrail()` is a permanent alias for `GetLog("sync")` that also exposes a legacy `entry.timestamp` field; new readers should use `GetLog(channel)` or `GetMasterLog(opts)` directly. Slash commands: `/gbl synclog`, `/gbl sortlog`, `/gbl logs` (master pop-up), `/gbl logs dump [N]`, `/gbl logs clear sync|sort|system|all`, `/gbl logs debug sync|sort|system on|off`. The Sync tab no longer carries an always-visible audit panel; logs surface only on demand via slash command.
- **An event count goes on the wire no later than the first record of any bucket whose records can use it, and nothing may reorder that (#114 v0.41.8, widened by #270 v0.41.10).** `PrepareChunks` indexes each entry under every bucket in its **ride set** and emits it when the record walk reaches the first record of whichever of them comes up first, so per bucket `max(usable entry chunk) <= first-record chunk <= last-record chunk`, and therefore **any prefix of the chunk list that completes a bucket's records carries every count those records can use**. That prefix property is the whole fix, because an abort is exactly a prefix. **It holds by construction, not by luck:** `emitBucketEntries` runs for every record in both lists, so an entry reaches the leftover pass exactly when no record produced any of its ride buckets, and a leftover entry therefore has no first-record chunk it could be late for. The emission chunk is the minimum over the ride set of the first-record chunk, which is at or before every member's, so nothing rests on which ride bucket the walk reaches first. **The ride set is `GBL:EventCountRideBuckets` (`src/Dedup.lua`), and it exists because "usable" is not "in the same bucket" (#270).** `CleanupWithEventCounts` reaches a count `GBL.EVENT_COUNT_SLOT_RADIUS` (1) hourly slots either side of a record's own slot, because two scans of one transaction can round its hour differently, so a count on the edge of a bucket is owed to the neighbouring bucket as well as its own: one bucket for a slot inside a bucket, two for a slot on either edge. That radius is one exported field with no file-local copy and both ends read it at call time, this function and the cleanup loop it mirrors, because a local in either place leaves two windows with one name to show for it. It deliberately does **not** govern the three other slot-drift windows in `src/Dedup.lua` (`CountFromRecordIndex`, `CountStoredForHash`, `FindDriftedCount`), which share the number and answer how many records exist under a prefix. **The filter and the packer must read the same set, and widening one alone is wrong in a way that is worth spelling out:** `EventCountRidesWithBuckets` selecting a boundary count without `PrepareChunks` indexing it under the neighbour puts it back in the trailing carriers this ordering exists to empty, because its own bucket has no records in the send and so no first record to ride ahead of, which is #114 reopened. **Measured on the live store before and after:** all 46 of the counts that were usable locally and unsendable forever are now offered, 22 more of the 104 empty-bucket counts become reachable through a neighbour populated by another prefix (harmless over-inclusion at bucket granularity), and 36 stay unreachable because no bucket in their ride set holds any record, which is the inert population the issue put out of scope. **The cost, also measured: 4,644 of 16,644 entries sit on a bucket edge, and the entries eligible for a selected bucket rise 26.1%, a mean of 41.4 to 52.1 per bucket and +262 on the worst one.** That is session length rather than waste, since those are the counts the receiving client's cleanup needs, and #92's budget still governs each chunk. A tighter filter is available and not built: the serve holds the records it is about to send, so it could admit a boundary count only when a record within the window is really in the send, which on this store would drop the 22 coincidental ones and much of the 26%. It needs the packer to reach the same answer, so it is a change to both sides and is recorded here rather than attempted. **The remaining limit is the fallback reading, and it measured zero.** The invariant is over bucket KEYS and the two sides reach a key by different readings: a count key always yields its trailing slot, while `bucketKeyForRecord` reads the slot out of the record id and falls back to `floor(timestamp / BUCKET_SECONDS)` for an id it cannot parse. #270's measurement put numbers on it for the first time: of 18,988 records, 0 carry an id the trailing `slot:occ` pattern cannot read, 0 have no timestamp, and 0 disagree between `floor(timestamp / 3600)` and the slot in their own id, so the divergence below is a latent shape rather than a live one. Those agree for every record the current builders produce, and on the fallback too while the timestamp matches the slot, since a slot is hours and the divisor is the same; they cannot agree when `tx.timestamp` is absent, where the fallback keys off `GetServerTime()` at packing time. Where they disagree the per-bucket promise still holds and what it buys does not, because that record's own count is filed under another bucket and travels with that one, and on the bucket path it rides only if that bucket is also in the send. That is a selection question in `EventCountRidesWithBuckets`, not a packing one, and no capture has shown a record arriving with an id the pattern cannot read, so it is recorded rather than fixed: changing that fallback moves bucket placement, which moves the fingerprint, which is wire-visible and costs a floor raise. Before it the packer filled records first and then swept entries forward into leftover room and trailing carriers, so every session's counts rode in a tail that was 12% of the 2026-08-18 capture and a quarter of 2026-08-13. Counts contribute nothing to the fingerprint (`ComputeBucketHashes` walks the two record arrays only), so a session that delivered all of a bucket's records and then aborted before that tail left both sides' hashes for the bucket **matching**: the diff never selected it again, `CollectEventCountsForBuckets` only collects for selected buckets, no third peer offered it either because they converge on the same hashes, and the receiver cannot re-derive counts locally because they are minted from live bank scans against a log holding about 25 entries per tab. `CleanupWithEventCounts` never trims a cluster with no count data by design, so that receiver keeps its duplicates permanently, the surplus inflates its own bucket hashes so it diverges from every correct peer, and once the surplus pushes its total past the sender's the superset skip blocks the very pull that would have carried the counts. A convergence trap, not a cosmetic count. Aborts in that window were never exotic: two of four sessions on 2026-08-13 were killed by BUSY. **Sender-local and additive: no wire change, no `PROTOCOL_VERSION` bump, no floor raise**, because `eventCounts` was already an optional per-chunk field, `estimateEnvelopeBytes` already reserves its wrapper on every chunk, and the receiver's merge is max-wins with no ordering or completeness assumption. Six things not to undo. **The seal test is emptiness, not "has it got a record in it"**: a chunk holding entries and no records is legal mid-stream and on the wire, and the old record-only test seals it away as empty and drops them; with `eventCounts` nil the new condition is exactly the old one, which is what keeps the record-only suite byte-identical. **The emission mark is per ENTRY and is shared by both record walks**, because one bucket can own records in the item list and in the money list and must emit once, and because since #270 one entry sits in two groups: clearing the group it was reached through leaves the other group holding it, so a group clear alone puts a boundary count on the wire twice. The group clear stays beside it, since a bucket once emitted has nothing left to walk. **The money walk's own emit call is load-bearing for a money-only bucket**, and a fixture with records in both lists cannot show that, because the item walk always reaches it first: dropping that call survived the both-lists test and is killed only by the money-only one. **Correctness does not rest on the send list being bucket-contiguous** the way `SortSendListNewestFirst` leaves it, nor on which of an entry's ride buckets the walk reaches first, since the entries go out at the first record of one of them either way and that chunk is at or before every other member's. **Both add helpers re-read the open chunk's tables after any seal**, because sealing hands the old ones to the sealed chunk and installs fresh ones. And **the forward-cursor leftover pass stays**, for entries none of whose ride buckets sends records and for keys whose slot cannot be read: that is the #92 behaviour, and the no-`bucketHashes` fallback path makes it the normal case rather than an edge, because that path filters by time and has no bucket keys to filter counts by. **It walks the entries and not the leftover groups**, which is load-bearing from #270: an entry indexed under two buckets appears in two groups, so a group walk hands it to the cursor twice and puts two copies of it on the wire. The unmarked set is exactly what the record walks did not emit, unreadable keys included, since those reach no group at all, which is why the separate orphan list is gone. Note that every fixture in the older #92 rider suite (`spec/sync_chunking_spec.lua`, "PrepareChunks with event counts") sits in **one** bucket, so that suite cannot see this property in either direction and stays green by construction rather than by luck; the interleaving specs beside it carry multi-bucket fixtures for exactly that reason. **And read `slotOf(bucket, offset)` in the interleaving describe before adding a fixture there.** Offset 0 is the FIRST hour of a bucket, so a count written at it also rides with the bucket below; 5 is the last hour and rides with the one above; 1 to 4 are interior and ride alone. Every fixture predating #270 was written at offset 0 and so exercised the boundary path without saying so, which is why the interior case had to be added by hand and why two of them were moved to offset 5, where the records really are within the window of the counts they ride with rather than six hours from them. **The rejected alternative stays rejected**: folding counts into the bucket hash would make the loss self-heal, but a fingerprint change is the class `MIN_SYNC_VERSION` exists for, so it costs a floor raise and a split guild for the adoption window, which is not worth paying when a packing reorder closes the window for free.
- `syncState.lastChunkBytes` is the canonical compressed chunk size. Reuse it for fragment-count estimates (`ceil(lastChunkBytes/255)`) rather than re-measuring.
- `HasSyncBandwidth()` uses a **dynamic** threshold `max(CTL_BANDWIDTH_MIN, lastChunkBytes)` — this is the v0.28.2 fix for the burst-stall regression from v0.28.0. Do not regress to a fixed threshold.
- The superset skip in `HandleHello` and again in the bidirectional check after `FinishSending` is load-bearing for convergence. The `HandleHello` superset case now re-nudges a behind peer past the hash-gated HELLO-reply suppression: when we are ahead, our data is stable, and the reply gate set `roundReply == "hash-suppressed"` (the round-local state #90 replaced `replyDecision` with; it rides out on the round line as `reply=`, so the correlation the old DEBUG-only detail line recorded is now readable in any capture), the superset branch re-sends a HELLO reply (an isReply HELLO drives the receiver's `shouldSync`/RequestSync path, so it is a real pull trigger) throttled per peer via `syncState.lastSupersetNudge[key]` + `SUPERSET_NUDGE_THROTTLE` (60s). This is the "tried and failed, back off" the v0.28.x note asked for, confirmed in-game (2026-06-09 capture: an ahead client at tx 10955 went idle and silently starved behind peers Fluphie/Fxh of the nudge, so they never requested). Wire-compatible (reuses the existing HELLO reply, no new message, no `DEV_BUILD`). The bidirectional-check site after `FinishSending` applies the same re-nudge: when we hold more it re-sends the HELLO reply through the shared `syncState.lastSupersetNudge[cleanTarget]` + `SUPERSET_NUDGE_THROTTLE` throttle, so a behind peer is driven to pull rather than skipped silently. The shared throttle means the `HandleHello` and bidirectional sites cannot double-nudge one peer inside the same 60s window. This closes the symmetric pure-skip gap the v0.28.x amplifier note flagged (previously the site short-circuited on "likely superset" with no back-off, so when sends failed both sides could mutually skip).
- Stale-ACK discard in `HandleAck` (v0.23.0) and `ScheduleReceiveTimeout` rescheduling (v0.25.3) are real defect fixes, not patches — do not remove during refactors.
- **The SYNC_REQUEST manifest is bounded, and the span fold must never become an XOR (#108, v0.37.11).** The request used to carry one entry per 6-hour bucket over the guild's whole history: ~2,500 B and 10 fragments at 273 buckets, over `WHISPER_SAFE_BYTES`, with no ACK and no retry, so on an ~18%-per-fragment route it arrived about one time in seven. That is what starved peers while the log on the serving side showed nothing at all. `BuildRequestManifest` now sends the newest `SYNC_REQUEST_DETAIL_BUCKETS` (50) buckets in `bucketHashes` plus up to `SYNC_REQUEST_SPAN_COUNT` (8) `spans` of `{ s, e, h }` covering everything older: 58 entries at any depth. **Measured size: 1,447 B serialized, 704 B deflated, 709 B encoded, so 3 AceComm fragments, and that figure does not move with history depth** (the bucket count is irrelevant once the manifest is bounded; ~580 of the raw bytes are near-random hash digits, which deflate cannot do much with). If the request ever has to fit in 2 fragments, the lever is `SYNC_REQUEST_DETAIL_BUCKETS`, not compression. Both constants are exported from `src/Fingerprint.lua` and specs read the exports. The requester logs its own request size (`Requesting sync from ... N bytes`), so a capture taken on the requesting side gives the figure directly rather than by reconstruction. Three things not to undo. **The fold is order-dependent djb2, not XOR**: bucket hashes are already XOR aggregates, so XORing them flattens to one XOR over every record in the range and two peers each missing records the other holds can fold identically over different data, which both sides then recompute the same way forever. It is the prefix-hash cancellation objection one level up. **Spans tile the older range** rather than hugging the keys the requester holds, so a serving peer's unknown bucket lands inside a declared span instead of an uncovered hole. **A key no span covers keeps the original comparison** (`localHash ~= (detail[key] or 0)`), which is what makes an old peer's full-table request take a byte-identical path and is why no floor raise was needed; the untouched bucket-diff and session-cap suites are that proof.
- **A receive timeout at zero chunks resends the request; after that it NACKs (#108).** Nothing arriving means the request went missing, and a NACK for chunk 1 asks for a retransmit of a send that never began, which `HandleNack` discards on arrival because it is not sending. That discarded signal already crossed the wire three times per failed request. The branch reuses `SendSyncRequestTo`, the stashed `syncState.receiveSinceTimestamp`, the existing `MAX_NACK_RETRIES` budget and the existing backoff ladder, and adds **no new timer**: it runs inside the timeout callback already scheduled. Keep the callback's check order (duration net, offline, budget, then the branch); the offline-detection specs pin it. Resending is only reasonable because the manifest made the request small and fixed-size, so do not keep the retry if the request ever grows again. **It is 3 fragments, not the 1-2 this bullet claimed before it was measured** (see the manifest bullet above), and the 2026-08-18 capture shows what that costs: four `Could not decompress` warnings, every one at exactly 459 B, which is 254+205 and therefore a 3-fragment message that lost its middle piece. Middle loss is the only single-fragment loss that is visible at all, since losing the first or the last delivers nothing, so each logged warning stands in for roughly two silent ones. That is the case *for* the retry rather than against it: the request loss it recovers is real and measured, and it starved a peer for 13 minutes in that same capture. Its necessary partner: `HandleSyncRequest` **ignores a repeat request from the peer it is already sending to** rather than answering BUSY, because `HandleBusy` would tear down the receive that send is feeding. BUSY still goes to third parties.
- **`ACK_TIMEOUT` and `MAX_RETRIES` move together (#92).** What matters is the product: total patience per chunk before the send gives up. They are 3s x 11 attempts ≈ 33s, down from 8s x 6 ≈ 40s. Changing one alone breaks the property they were tuned for: 3s at the old 6 attempts is ~18s, short enough to abort sends that today survive a receiver's 20-30s loading screen. Both are exported (`GBL.SYNC_ACK_TIMEOUT`, `GBL.SYNC_MAX_RETRIES`) and specs must read them rather than matching a literal delay — a spec that hardcoded `timer.delay == 8` matched nothing after the change and passed vacuously instead of failing, which is why `fireAckTimeout` errors when it finds no timer.
- **Free-agent pairing: a peer that finishes a session becomes free and takes whatever the next HELLO offers.** There is no stored picture of other members' bucket hashes and no scored queue choosing a "best" next partner. Both were removed in the v0.37.6 release along with the MANIFEST message that fed them (~335 lines): `syncState.peerManifests` had exactly one reader, the scoring loop inside `PopPendingPeer`, so the message and the scoring were the same feature. Removing it is wire-compatible in both directions, because the dispatch chain in `OnSyncMessage` has no `else`: an older peer's MANIFEST reaches an updated client and costs nothing. No `PROTOCOL_VERSION` bump and no floor raise. **The reasoning, which matters more than the mechanism:** gossip's guarantee is eventual delivery, not optimal routing, so it does not matter whether data reaches the most convenient partner next. The bookkeeping was not only code: `PopPendingPeer` recomputed every bucket hash (a full walk over 10k+ records) once per queued peer per pop. Two jobs the queue was quietly carrying had to survive it, and both are now single-purpose. **BUSY backoff** is `syncState.peerBusyUntil[peerKey]` plus `GBL:IsPeerBusy`, checked at the two automatic initiation sites (`HandleHello`'s skip chain and the bidirectional check's behind-branch) and deliberately NOT inside `RequestSync`, so a manual or forced pull still works. There used to be a second check behind the HELLO one, inside a jitter callback, to catch a BUSY arriving during the 0-1s deferral; it went with the jitter in v0.37.10 (#105), and a request now crosses a late BUSY on the wire instead, which `HandleBusy` resolves by aborting the receive it just started. **Combat deferral** is `syncState.helloAfterCombat` plus a forced `BroadcastHello` on combat end, which re-drives both directions (behind peers request from us, ahead peers reply or nudge). It is gated on the flag so a raid leaving combat together does not produce one broadcast per member; `FORCED_HELLO_COOLDOWN` is per client and would not stop that. The `isSyncPaused()` check is the third thing the queue used to provide, since everything deferred used to drain through `ProcessPendingPeers`, which checked. It is now its own arm in `HandleHello`'s skip chain, placed after the combat-lockdown arm so a HELLO arriving in combat still sets `helloAfterCombat`, and it logs which pause it was. What it covers is the cooldown that outlives the pause trigger (2s combat, 5s zone), the window in which `InCombatLockdown()` already reads false. Staleness and offline filtering are gone with no replacement and that is correct: a sync is now only ever started off a HELLO that just arrived or a session that just ended, so there is no way to name a peer we have not heard from.
- **BUSY carries a `reason`, and it is a required builder argument rather than an optional field (#97).** `GBL:BuildBusyMessage(reason)` has three call sites and three shipped values: `"combat"` from `OnCombatStart` (one serialized message reused for both partners) and from the serve gate, `"sending:<peer>"` from the already-sending decline, which names who holds the slot, and `"preparing:<peer>"` from that same decline when `syncState.prep` is live (#115b, v0.37.17). The prep/send split is the one a capture reader needs: preparing is sub-second and sending is minutes, so the two say very different things about how long the declined peer should expect to wait. `HandleBusy` reads it and logs `unknown` for a pre-#97 peer. Additive with unknown-key passthrough, so no `PROTOCOL_VERSION` bump and no floor raise, on the same reasoning as #108. Since #202 the send-target branch hands its teardown to `FinishSending` rather than clearing fields inline, so the reason now arrives with a full summary block behind it; see the `chunkOutcomes` bullet below for what that changed and what must not move. **The receiver treats the value as an opaque string**, so a later producer adds a value without a wire change; record new values in this bullet. Two things not to undo. **`BUSY_KEYS` in `spec/wire_contract_spec.lua` must list `reason`**: that absolute set is the maintenance cost #70 deliberately bought, and it is the only thing that catches a field dropped from the one builder both sites now read from, since parity compares the two emitted messages to each other and a shared builder drops from both at once. **The value asserts beside it are not redundant with parity either**: two sites passing the same wrong reason still agree, so the shipped values are pinned individually; both failures were proven by mutation. The vocabulary the 2026-08-12 capture needed is exactly this: a mid-send BUSY can only be a combat abort, a BUSY answering a fresh request can only be already-sending, and until the field shipped a capture could not tell them apart.
- **SYNC_RECEIPT carries the receiver's redundancy figures back to the sender, and it is log-only on purpose (#237).** The receiver computes the `Redundancy from <peer>` figure in `FinishReceiving` and the sender is the side holding `capLastTranche`, which decides what the next session to that peer carries, so the number the v0.28.8 decision rule reads lived on the wrong client. `GBL:BuildReceiptMessage` is the one builder, the emit sits in `FinishReceiving`, `HandleReceipt` writes one INFO `Receipt from <peer>:` line on the sync channel, and nothing else reads it: the tranche-rotation change waits for two receipts to say the same thing. Additive with unknown-key passthrough, so no `PROTOCOL_VERSION` bump and no floor raise, on the #97 and #108 reasoning. Eight things not to undo. **A receipt goes out only for a session that completed AND that we asked for.** `FinishReceiving` takes a second argument and only the branch that runs when the last chunk arrived passes it, because that function is the single teardown for every abort too (the stuck-receive timeout, the sender-offline abort, the NACK budget, a request that could not be sent, and `OnCombatStart`): a partial session's percentage is a real number over an unrepresentative sample, and the combat abort would put a fresh whisper on the wire in the same frame as the BUSY it sends. Deriving it from `receiveGot >= receiveExpected` was written and rejected, because that reads true for the teardown of a session whose last chunk arrived with no `chunk` field, which never reaches the completion branch. `syncState.receiveRequested` is the second half and is not belt and braces: without it a retransmitted final chunk arriving after the session was torn down bootstraps a one-chunk session of pure duplicates through `HandleSyncData`'s auto-bootstrap, reaches the completion branch again, and whispers a SECOND receipt reading 100% duped for a session already reported. **The message is built where the counters still stand and sent after the teardown**, because `compressMessage` and `SendSyncWhisper` both reach code that can raise, and unwinding from inside `FinishReceiving` would leave `receiving` true with the timer armed, which blocks every future pull until the `MAX_RECEIVE_DURATION` watchdog; `OnCombatStart` already orders its own BUSY that way. **`stored` and `duped` on the wire are NOT the sums of the four halves beside them**, because `CleanupWithEventCounts` runs inside `FinishReceiving` and decrements the total alone, so `stored` is what the receiver kept and not what it took in; that is deliberate, since the receipt's whole purpose is that the two clients' logs describe one session identically. **`received` and the capped session's `remaining` are both absent from the wire.** `received` is derived by the reader on the #215 rule that two stored copies of one number can disagree with nothing to say which is right, and `remaining` is the same rule from the other side: the SENDER authored that count and attached it to the final SYNC_DATA, so echoing it back carries nothing it does not already hold. `rejectFields` is the opposite case and earns its bytes, because the peer holding the records is the only side that can act on which field failed and the only side that cannot see it. **Every remaining field is unconditional**, unlike SYNC_DATA's optional ones: that optionality exists to keep an uncapped session byte-identical to a build that predates the field, and a message type introduced whole has no predecessor to match, so the absolute key set in `spec/wire_contract_spec.lua` is worth more than the bytes. **A session in which every record was refused still sends a receipt** (the gate is `redundancy or rejected > 0`) and the handler renders it with no percentage, because a peer serving records nobody can accept is the peer that most needs telling, and that reading is why #68 gave rejects a counter of their own. **The handler refuses a figure that cannot be a measurement** (negative, NaN, infinite, non-integer; AceSerializer round-trips all of them) and names the drop, because rendered they read as readings, `200% duped` and `nan% duped`, on the one message type whose only job is to measure. A receipt from a peer `capLastTranche` has no record of serving is marked `(unsolicited...)` rather than dropped: dropping it would hide a real receipt if that record ever turns out narrower than the cases producing one, and that cannot be checked before release. **`redundancyText` and `rejectFieldText` are the one writer of each half of the prose**, read by the receiver's lines and the sender's, so the two cannot drift into describing one session two ways.
- **`clearReceiveCounters` is the one writer of the receive session's thirteen counters, and it had to land with #237.** There were four reset sites carrying four different subsets: `RequestSync` set all of them (three fields twice), `FinishReceiving`'s teardown set all of them, `HandleBusy` set four, and `HandleSyncData`'s auto-bootstrap set two. So a session ended by BUSY and then picked up by a bootstrapped one carried the first session's item, money and reject counts into the second session's `Redundancy from <peer>` line. **The two partial sites mask each other**, since `RequestSync` always cleared the lot, so reverting either one alone leaves the system correct and only the pair leaks; the spec pins the pair, and the two single-site mutants survive by construction rather than by a gap. It was tolerable while the figure stayed in one client's log. Since #237 it crosses the wire to the peer that served the records, and a stale `rejected` count in particular reads over there as that peer's own store being corrupt, which is the signal #68 built the separate counter to make trustworthy.
- **Every processed HELLO writes exactly one INFO round line, and that count is the design (#90).** `HELLO round <peer>: verdict=<v> reply=<r> peer=v<ver> remote=Ntx [local=Ntx hash=local/remote] [buckets=N] [extra]`, emitted at all 9 terminal exits of `HandleHello`. **Verdicts:** `refused-version` (`refusal=` rider), `no-guild-data`, `identical`, `superset-skip`, `superset-nudge`, `busy-cooldown`, `combat-deferred`, `paused-zone`, `paused-combat`, `requested` (`trigger=hash-mismatch` or `trigger=count-no-hash`), `no-sync-needed`, `receiving` (`from=` rider), `autosync-off`. **Reply gate:** `sent`, `send-failed`, `hash-suppressed`, `sync-active`, `suppressed` (repeat refusal), `n/a` (an isReply HELLO never runs the gate). It **replaced** rather than added: the three DEBUG diagnostics the issue named plus the per-round INFO chatter that duplicated them (the arrival line, the hash compare, the per-arm skip and trigger lines), so per-round capture cost fell from three entries to one. That is why folding beat the issue's literal "promote the three lines", which would have made it four against a 1000-entry cap one large send already eats 40% of. **Reasons not to undo any of it.** DEBUG cannot reach a shared capture at all (Logger drops it ahead of the capture tap, AuditCapture rejects it again unconditionally), which is the whole defect. `reply=` reports the **outcome**, not the intent: `SendHelloReply` returns a boolean because it gives up quietly on three paths and a line claiming a whisper that never left is worse than no line. The bucket count rides along only via `GBL:PeekBucketHashes` (`src/Fingerprint.lua`, cached map or nil, never computes, checks guildData identity but deliberately not the count) — the old unconditional `GetBucketHashes` call walked the whole history on every inbound HELLO, worst during a receive where the count moves per stored chunk so the cache missed every time. Do not point it back at `GetBucketHashes`. Every verdict emit is pinned by a spec and each was proven by mutation; the `roundLine()` helper asserts **exactly one** line per round, so a fall-through double-emit or a silent exit reds broadly. Note that `refused-version` and `no-guild-data` rounds carry no `hash=` (`roundStats` is built after the guild-data check), which is deliberate, not a gap.
- **The combat policy has three doors, and serving was the one with no lock (#126, v0.37.15).** "Combat is no time to sync" is implemented separately at each: `HandleHello` defers *requesting* on live `InCombatLockdown()` plus an `isSyncPaused()` arm for the tail, a *live session* entering combat is aborted outright by `OnCombatStart` with BUSY to both partners, and `HandleSyncRequest` now declines with BUSY on the same two conditions. Before this it checked neither, so a raider was handed a full synchronous serve mid-pull, which is the context of the #115 watchdog kills. **The trap that hid it: `combatPaused` is not the combat check and never was.** `OnCombatStart` returns early unless a session is in flight, so an idle client in a raid never sets the flag; reading it as "are we in combat" says no for exactly the client this bug hit. The flag is a post-abort debounce tail (2s combat, 5s zone) covering the window where the live API already reads false, which is why every door needs both terms and not just one. The gate sits **after** the version gate deliberately: BUSY means "try again shortly" and would drive an incompatible peer's retry loop forever, so that peer keeps getting silence. `spec/sync_request_spec.lua`'s "combat serve gate" describe pins the ordering, and that assertion passes vacuously without a gate present, so it was proven by swapping the two blocks rather than by inspection. #115b's restructured accept block keeps this gate synchronous and ahead of the prep chain; leave it there.
- **Serving prepares across frames, and the send slot is claimed synchronously before it starts (#115b, v0.37.17).** `HandleSyncRequest` keeps four things synchronous in this order: version gate, combat/pause serve gate, sending guard, guildData check. Then it commits `sending`/`sendTarget`, inits the send fields every teardown path reads (`FinishSending` takes `#syncState.sendChunks`, which throws on nil), and starts a token-guarded `C_Timer.After(0)` chain of seven resumable stages. The synchronous commit is load-bearing and about ten specs depend on it: two peers requesting in the same frame must not both be accepted, and every caller asking `GetSyncStatus().sending` straight after the call must get a real answer. **The property that made the change cheap: the first `prepStep` runs synchronously, and a stage that finishes with budget left hands onward inside the same tick.** So a small dataset completes inside the accepting call with the first chunk already sent, which is why only 2 of ~113 existing serve call sites needed a drain and the rest call `HandleSyncRequest` bare and are none the wiser. `spec/sync_helpers.lua`'s `serveRequest` is for tests that seed past one tick's budget; `Helpers.drainZeroDelayTimers` (spec/helpers.lua) fires **only** `delay == 0` timers, because `MockWoW.fireTimers` empties the whole queue and would fire the 120s hard timer and the HELLO heartbeat, aborting the thing under test. **Five things not to undo.** `SYNC_PREP_RECORDS_PER_TICK = 1500` shipped on a measurement, not an estimate (5.25 us/record for the heaviest stage, 7.87 ms/tick); re-measure before moving it. The `SYNC_PREP_TIMEOUT = 30`s watchdog is what stops a chain that dies silently from holding the send slot until reload while BUSYing every request. The **tranche is stamped only once the preparation completes** (it used to be stamped before packing, so a serve that died partway told the next session it had handed those buckets over). Every teardown path must call `_AbortSyncPrep`: the chain is not reachable through the send state those paths clear, so an orphaned chain runs to completion and commits into the torn-down session. And a mid-prep **loading screen aborts rather than pauses**, unlike a live send: the resume calls `SendNextChunk` against the empty chunk list the accept installed, and `SendNextChunk` answers an absent chunk with `FinishSending`, writing a "Send complete 0/0 chunks" block for a session that never sent a byte. **`OnCombatStart` checks the prep before `sending`**, because prep implies sending: reversed, the arm is unreachable and every live-send spec still passes. Ten mutations pin this, the reversal included. Mutation tolerance is deliberate at two points: a tail append lands after the walk and rides the next session, and an id normalization from a receive finishing mid-prep degrades to redundancy rather than divergence because the receiver dedups by id. The `Prep complete for <peer>: N examined, M selected, K tick(s), T` line is how a capture verifies any of this on a real client.
- **Peer identity: always use `GBL:CanonicalPeerKey`** (src/Core.lua). The helper does its own local-realm-only strip via `GBL:_isLocalRealm`, NOT `Ambiguate("guild")`. Reason: retail's `Ambiguate("guild")` strips realm for ALL guildmates in a connected-realm group, which collapses two distinct same-name characters across connected realms (e.g. an Alice on Tichondrius and a different Alice on Stormrage in one guild) into one peer key. Custom strip rules: qualified `Name-Realm` keeps the suffix when realm differs from local (raw-or-normalized comparison), strips to bare when realm equals local. Bare input consults `guildData.playerRealms[name]` (built by `BuildRosterCache` on every `GUILD_ROSTER_UPDATE`, persistent across sessions); cross-realm bare names get re-realmed to `Name-Realm`, same-realm bare names stay bare. Both bare and qualified arrivals of the same character converge on the same canonical key in any realm topology, while two distinct same-name peers on different realms keep distinct keys. Bare names without a `playerRealms` entry (cold cache, departed peer, non-guildmate sender) pass through unchanged (best effort; the unresolvable case is two distinct same-name characters whose messages both arrive bare, which collide). **Defensive validation:** the helper rejects realm strings containing hyphens (corruption from a long-fixed code path; retail realm names never contain hyphens) and falls back to bare passthrough; `RepairCorruptedPlayerRealms` (called from `BuildRosterCache`) trims corrupt entries to their first segment so offline-peer corruption doesn't persist forever. `GBL:StripRealm` is reserved for true bare-name use cases where same-name on either realm should share state; the only current consumer is `recentWhisperTargets` for chat-system-message suppression (see comment near its declaration in `src/Sync.lua`). The test mock for `Ambiguate("guild")` is unused by `CanonicalPeerKey` now but still implements local-realm-only strip for any callers that legitimately want it. The `src/Sync.lua` `InitSync` knownPeers seed loop runs each persisted key through `CanonicalPeerKey` and consolidates `knownPeers` in place when a stale key collapses to a new canonical form. **Cold-roster gate:** `MigrateRecoverPeerRealms` returns 0 without bumping `schemaVersion` when `GetNumGuildMembers()` is 0 (cold roster); `GUILD_ROSTER_UPDATE` retriggers `MigrateAllGuilds` once per session via the `_migrationsRetried` flag so cold-roster short-circuits get a warm retry without waiting for the next login. Historical: v0.30.5 first patched the broken `Ambiguate(name, "none")` (identity in retail) with `StripRealm` (over-aggressive), then with `CanonicalPeerKey` wrapping `Ambiguate("guild")` (correct in tests but in-game collapsed all connected-realm guildmates to bare); the v0.30.5 follow-up replaced the `Ambiguate("guild")` delegation with custom local-realm-only logic, added the `playerRealms` fallback for bare arrivals, fixed the schema-11 cold-roster premature-bump, retriggered MigrateAllGuilds on first warm `GUILD_ROSTER_UPDATE`, and added `RepairCorruptedPlayerRealms`.
- **`chunkOutcomes[idx]` outcome vocabulary (v0.28.7):** `"pending"`, `"ok"`, `"aborted"` (ackTimeout), `"combatAbort"`, `"zoneAbort"`, `"busyAbort"`, `"sendFailed"` (target offline). Abort-tagging paths are all guarded by `outcome == "pending"` so a later ACK that sets `"ok"` wins correctly. **A tag is worth nothing without the path that renders it, which `"busyAbort"` proved by reading zero from v0.28.7 on 2026-04-22 until v0.41.9 (#202).** `HandleBusy`'s send-target branch tagged the chunk and then cleared eight send fields inline and returned, so it never reached `FinishSending`, the only renderer of the histogram, and `chunkOutcomes` was replaced wholesale at the next send. Every `+ N busy +` figure in every capture this repo holds reads `0 busy`, and that is an artefact rather than a reading: the counter existed, the tag was applied, and the number was zero by construction. The branch calls `FinishSending` now. **The tag alone still cannot answer it, which is the correction the code review of PR #271 made to the first cut of this fix, and it is the reason `FinishSending` takes an `abortCause`.** `sendChunkIndex` advances at ISSUE time and `HandleAck` marks the acked chunk `"ok"` without advancing it, so from the ACK until the next issue (at least the 1.0s `INTER_CHUNK_GAP_FLOOR`, against a measured 0.2 to 0.5s wire-to-ACK) the indexed chunk is already settled and nothing is on the wire. Every abort path tags under an `outcome == "pending"` guard, so through the majority of each chunk cycle it tags nothing, and a BUSY landing there would have printed `+ 0 busy +` under a `Send complete` heading, which is the by-construction zero again in a new costume. So the histogram stays a count of CHUNKS and the session's own verdict is a separate clause on the same line, `session complete` or `session ended by <cause> at chunk N/M`, passed in by the caller at all six `FinishSending` sites (`busy`, `combat`, `ack timeout`, `peer offline` twice, `send stalled`). Note what this means for old captures: a `+ 0 combat +` or `+ 0 zone +` on a session that visibly aborted is the same blind spot, not evidence the cause was absent. **The six-field leak the first cut claimed does not exist and the claim was withdrawn**: four of them (`lastSendIssuedAt`, `sendChunkTransmittedAt`, `nacksForCurrentChunk`, `chunkOutcomes`) are reset at the start of every send in the final prep stage, and `chunkOutcomes` again at the accept, while the remaining two are unobservable (`sendChunkSentAt` is written before every chunk and read only after it, and `lastChunkBytes` is read through `math.max(CTL_BANDWIDTH_MIN, ...)` and through a fragment estimate taken after it is rewritten). The inline teardown was a divergent subset with no consequence anyone could see; it is still worth not having, and it is one site of the hand-copied teardown #122 covers. Three things to keep. The abort line is emitted **before** `FinishSending`, as `OnCombatStart` orders its own, so a capture reads the block as the consequence of the abort. `FinishSending` schedules the bidirectional check 0.5s out at a peer that has just declined, and **the branch it reaches is the superset one, not the behind one**, which the first cut had backwards: we were serving that peer because it was behind, so we still hold more 0.5s later and the `IsPeerBusy` arm is never reached. Unguarded that whispers a HELLO reply at a peer which just said it was busy and stamps `lastSupersetNudge`, and `SUPERSET_NUDGE_THROTTLE` (60s) outlives `BUSY_COOLDOWN` (30s), so the peer goes eligible at 30s with the `HandleHello` re-nudge suppressed for another 30 and starves longer than if nothing had been sent. The nudge is gated on `IsPeerBusy` now and says so in the log. `OnCombatStart` was never exposed to this, but only incidentally: it sets `combatPaused` before its own `FinishSending`, so the callback returns at `isSyncPaused()`. `HandleBusy` sets no such flag, which is why the gate has to be at the nudge. And the **mid-prep** branch above stays silent and must never reach `FinishSending`, or a preparation that never put a byte on the wire writes a full `Send complete 0/0 chunks` block plus four statistics lines; `assertChainIsDead` in `spec/sync_request_spec.lua` pins that for every mid-prep teardown at once, and a mutation that lets a mid-prep BUSY fall through to the live-send path is killed by it. **`retryReasons`** is a per-chunk array of `"ackTimeout"` / `"nack"` tags; only these two count toward the wire-loss `chunkFail` metric. Combat/zone/busy/offline aborts are bucketed separately, because mixing them into a single "aborted" count loses the ability to tell a noisy test session from a reliability issue.
- **`sortAccess` rides HELLO like `accessControl` (v0.32.10).** The two-tier sort-access policy (`guildData.sortAccess`: write/sort tiers with rank thresholds + delegate lists) is attached to both HELLO builders in `src/Sync.lua`, gated on `(sortAccess.updatedAt or 0) > 0` so unconfigured guilds keep HELLO lean. `HandleHello` accepts a newer remote copy (last-writer-wins on `updatedAt`), normalizes it via `GBL:MigrateSortAccessShape`, and fires `GBL_ACCESS_CONTROL_CHANGED`; `SaveSortAccess` forces a HELLO and signals the same message. This propagation is what makes a GM's grant reach the granted member's client (before it, `sortAccess` was Core-only and never synced). Watch the delegate name-form edge: delegate keys are stored verbatim from the LayoutEditor input but matched against `normalizedPlayerName()` (space-stripped realm), so a multi-word-realm delegate typed with a space will not match.
- **Bank layout syncs via advertise-and-pull, NOT by riding HELLO (v0.32.11).** Unlike `accessControl`/`sortAccess` (small scalars that ride the HELLO body), the bank layout template is several KB, so putting it on every broadcast would regress the one-fragment HELLO the v0.28.x reliability arc fought for. Instead HELLO carries only `layoutUpdatedAt` (one timestamp, gated on `bankLayout.version > 0`). A receiver requests the full template via `LAYOUT_REQUEST` only when it both `HasSortAccess()` AND sees a newer cursor; the holder replies with `LAYOUT_DATA` (full template + `stockReserves`) over a whisper. The layout block in `HandleHello` sits AFTER the `sortAccess` merge, so a grant and its layout pull converge in a single HELLO round. There is NO ACK: every HELLO re-advertises the cursor, so a dropped `LAYOUT_DATA` is re-pulled on the next ping until cursors match (convergence, not per-message proof); `syncState.lastLayoutRequestAt` + `LAYOUT_REQUEST_THROTTLE` keep one request in flight. `GBL:AdoptRemoteBankLayout` validates via `BankLayout.Validate`, applies last-writer-wins on `updatedAt`, and bypasses the `HasLayoutWrite` gate (sync intake, not a local edit), then fires `GBL_LAYOUT_CHANGED` → `OnBankLayoutChanged` refreshes an open Layout/Sort tab. `SaveBankLayout` and a cursor-bumping `SetStockReserve` (only when `version > 0`, preserving the "version > 0 ⇒ valid layout" invariant) force a HELLO so the change advertises promptly. Serving is NOT access-gated (any holder serves, for epidemic spread); only requesting is gated. Watch: `LAYOUT_DATA` is a single whisper; if a real layout compresses above `WHISPER_SAFE_BYTES` it logs a `SyncWarn` (chunking is the unbuilt fix; the `nchunks`/`chunk` envelope fields reserve room for it). The mock serializer is pass-through, so payload size and numeric-key survival are not exercised in tests — verify in-game.

### Chunk sizing — observed reality

- **Every compression figure in this section is compressed size as a percentage of raw**, which is also what `chunkOutcomes.ratio`, the per-chunk send line and the `Compression for <peer>` summary all report. Lower is better. The per-chunk line printed the complement (percent reduction) until v0.37.12, so a capture taken before that reads 31% where this section would say 69%; invert it before comparing.
- **Compression ratio is 23–49%, not 23–26%.** v0.28.6 assumed ~18% and missed; v0.28.7 assumed 26% worst case and also missed. Measured across every capture: 23–26% (v0.28.5/28.6, item-heavy), 27–49% (v0.28.7 Roxeau), 30–42% (2026-08-10 Aeglos). Money-heavy chunks compress worst. **Derive any byte budget from the max, never the median**: `raw_budget <= (N * 255) / max_ratio`. Three consecutive misses came from predicting ratios.
- **Per-fragment drop is ~18%.** Back-solved from v0.28.6's `p_frag_est=44.9%` with 3-fragment chunks: `1-(1-0.18)^3 ≈ 0.45`. Reconfirmed at 18.7% in the 2026-08-10 capture. Per-peer route variance is ~25x, so this is a mid-range figure, not a constant.
- **The 1-fragment target was never met before #92.** v0.28.7 shipped `MAX_RECORDS_PER_CHUNK = 4` with `CHUNK_BYTE_BUDGET = 900` and believed the budget was binding. It never was: 4 records estimate ~790, so the record cap always sealed first, and the budget never fired once in a 2,731-chunk send. Worse, it only ever weighed records. The eventCounts rider (10 entries, ~768 B) and the envelope (~133 B) attach at serialize time, after chunking. Measured on a real chunk: 1,637 raw bytes, of which 736 were counted and 901 were not. Every chunk shipped as 3 fragments for four months.
- **Shipped (#92):** `CHUNK_TARGET_BYTES = 510` governing the **whole serialized message**, with `MAX_RECORDS_PER_CHUNK = 4` kept as a backstop. `PrepareChunks` reserves the envelope estimate up front and fills records and eventCounts entries against what is left, opening carrier chunks for entries that have no record to ride with. Derivation: `255 / 0.50` at the worst measured ratio. **The order within that changed at #114**, which is a correctness fix rather than a sizing one: entries no longer all ride behind the records. See the interleaving invariant under Code invariants to preserve before touching the packer.
- **Density cost, measured:** at ~199 estimated bytes per record and a ~183-byte envelope allowance, the usable budget is ~327 bytes, which fits **one record per chunk** (two would need 398). A backfill therefore produces roughly one chunk per record instead of one per four. Per-record throughput is roughly a wash against the old 4-records-at-3-fragments arrangement; what improves is abort-resistance and the smoothness of partial progress. Do not expect a speedup from this change, and do not "fix" the density by raising the target without a compression measurement at the smaller size (see the open question below).
- **Open question — compression at small sizes.** Every ratio above was measured on ~1,600-byte messages. LibDeflate does worse on smaller inputs, and a 510-byte message may compress nearer 50–60% than 30–42%. That would put an encoded chunk back over 255 B. The runtime guard is the `over-255` counter in the FinishSending summary plus `syncState.lastChunkBytes`; read them on the first capture after this ships. This cannot be tested hermetically because LibDeflate is deliberately not vendored (see the wire-contract notes).
- **When a sync still aborts mid-stream:** the old advice ("do not shrink chunks, 1 fragment is the floor, raise `INTER_CHUNK_GAP_FLOOR` instead") assumed chunks were already 1 fragment. That precondition is only true from #92 on. Now that it holds, the gap floor is genuinely the next lever.
- **What NOT to do:** do not raise `CHUNK_TARGET_BYTES` without a fresh compression measurement at the new size, and do not re-derive it from a median ratio.

### Session cap — bounded slices (v0.37.7)

- **`SESSION_RECORD_CAP = 300`** (`src/Sync.lua`, exported as `GBL.SYNC_SESSION_RECORD_CAP`; specs must read the export, never the literal). A send stops at the first whole-bucket boundary at or past the cap. At the measured ~1 record per chunk and the 1.0s gap floor that is roughly 5 to 6 minutes per session, and about 2.5 minutes once the 708-byte budget (#96) lands. The number was chosen for session *length*, not byte count, so it moves when the per-chunk density does.
- **Whole buckets, never a partial one.** A half-sent 6-hour bucket hashes to something neither side holds, so it stays in the diff and comes back entire on the next request. Splitting a bucket to hit the cap exactly would mean a backfill that never converges. A single bucket larger than the whole cap still goes out whole, for the same reason.
- **`remaining` is how the receiver learns a session was capped.** Additive envelope field, final chunk only, omitted when zero, and attached in `SendNextChunk` at serialize time rather than baked into the chunk, so a NACK or ACK-timeout retransmit of the final chunk still carries it. `estimateEnvelopeBytes` reserves for it on **every** chunk: which chunk is final is not knowable while packing. An uncapped session therefore puts no new key on the wire at all, which is what keeps the wire-contract builder key-parity check green.
- **Tranche rotation is not partner selection.** `syncState.capLastTranche[peer]` records, per target, which buckets the last session carried and what their local hash was then. On the next request from that peer, buckets whose local hash has not moved since sort **last**. Without it, a receiver that already holds those buckets from a third peer pins the sender to the same all-duplicate tranche every session while older differing buckets starve. Session-only, self-expiring, and it does not choose who to sync with, so it is not the scored selection retired in v0.37.6. The bucket hashes are computed on **both** request paths for this: a request carrying no `bucketHashes` could otherwise never record a tranche and would loop on its first slice forever.
- **The continuation seam is the existing gossip, deliberately.** `FinishReceiving` reads `remaining` and `madeProgress` before teardown, logs "Partial session from `<peer>`: N bucket(s) remaining", and schedules nothing. The next request comes from the post-receive forced HELLO, the sender's superset nudge (60s throttle, shorter than a slice) and `shouldSync`. This is the ship-and-measure arm of a version-sequenced A/B, not an oversight: a spec pins that no continuation timer is scheduled. A direct 3s same-sender continuation is designed and held on file; build it only if a capture shows a median seam over ~30s or stalled backfills. Known edge: a zero-progress slice emits no forced HELLO and falls back to the 120s heartbeat, which tranche rotation should make rare. Measure it.

### Diagnosis discipline

- Do not lower a pacing constant without an independent reliability measurement — "more aggressive" is not the same as "better."
- Per-chunk audit outcomes (attempt count, wire-to-ACK latency, gap since prior chunk, estimated fragments) are the minimum signal needed to discriminate fragment loss from server throttle from callback-timing bugs. Add these before changing behavior.
- `sendChunkIndex` in the "Send complete X/Y chunks" line is the index of the **last attempted** chunk, not the count acknowledged. When writing future diagnostics or UI strings, prefer an explicit "N ok / M aborted" framing.
- **v0.28.7 FinishSending output is three per-peer lines:** `Sync outcomes for <peer>` (histogram + split abort causes), `Retry causes for <peer>` (ackTimeout / nack / chunkFail / p_frag with observed `n=` frags/chunk), `Compression for <peer>` (min/med/max compression percentage). `p_frag` is back-solved using observed average fragment count rather than `lastChunkBytes`, so A/B data across chunk-size changes is directly comparable. **Do not conflate `chunkFail` (raw retry rate) with `p_frag` (per-fragment loss)** — they are equal only at n=1 fragments.
- **Outcome vocabulary is load-bearing.** Any new abort/failure path should add a named outcome value, not reuse `"aborted"` — the split between wire-loss and environmental aborts is what makes the histogram interpretable.
- **v0.28.8 FinishReceiving emits a `Redundancy from <peer>` line** with total dupe rate + item-vs-money split (e.g. `78% duped (1023/1314 received) — items: 65% (412/635), money: 90% (611/679)`). Per-chunk audit also has a running `X% dup` annotation. This is the receiver-side complement to v0.28.7's three sender-side per-peer lines. Use it to decide whether bucket-granularity redundancy justifies designing a finer-grained exchange. Decision rule: `<30%` = bucket filter is doing most of the work, skip; `30–70%` = worth doing but not urgent; `>70%` = worth designing. **Note the cost moved:** that design used to be able to assume a periodic MANIFEST broadcast already existed to build on. It does not any more (see the free-agent pairing note below), so it now has to price in either reintroducing a broadcast or carrying the finer manifest inside the SYNC_REQUEST/SYNC_DATA session itself. This is a separate concern from partner selection, which is why removing MANIFEST did not retire the rule. Item-vs-money split tells you whether items, money, or both are the redundancy source — money-heavy redundancy may be addressable by smaller money-only buckets instead of full manifest. Suppression: line omitted on empty syncs; segments omitted when the corresponding record type is absent. **Do not conflate redundancy % with sender-side `chunkFail`** — redundancy measures dedup waste at the application layer, not wire-loss retries. **The figure is only trustworthy from v0.37.0 on.** Before it, a record rejected by `reconstructSyncRecord` incremented the dupe counter, so a peer sending nothing but corrupt records read as 100% duped, which this very decision rule reads as "the bucket filter is doing the work, skip". #68 gave rejects their own counter and their own `Rejected N record(s) from <peer>` line. Any redundancy reading from a capture taken before v0.37.0 carries that inflation and should not be compared against a later one. **A second inflation window opens at v0.37.11 and closes when the guild finishes updating.** A v0.37.11 client's request describes only its recent window in detail, and a pre-v0.37.11 server does not read `spans`, so it treats all of old history as missing and offers it. That converges (whole buckets, bounded per session by `SESSION_RECORD_CAP` on any server from v0.37.7 on) but it is nearly all duplicate, so a mixed-version capture reads high for a transitional reason rather than a structural one. Do not compare a reading taken during guild adoption against one from a settled guild, and do not read it as evidence for a finer-grained exchange.
- **v0.37.11 logs the two silent decode failures in `OnSyncMessage`**, at WARN, with sender, channel and the raw byte count. They used to be bare returns, which is what made a damaged arrival indistinguishable from a peer that never spoke. They are the direct measurement the erasure-coding question turns on: AceComm's reassembly has no sequence numbers and no completeness check, so a lost middle fragment is delivered as a truncated payload and lands here, and the surviving byte count says how much of the message made it. Payloads a few hundred bytes short mean independent single-fragment loss; payloads mostly missing, or silence, mean bursts. Those want different fixes, and forward error correction is only worth reconsidering for the first (see the spike on #108, which declined it for now). Read this before proposing any redundancy or coding scheme.
